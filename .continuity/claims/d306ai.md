User rejected existence-only tool matching as a schema-pinning substitute and flagged 5 more gaps (exec identity, scope-as-sandbox framing, invocation state granularity, audit adapter precedence, config integrity). Revised design adds: operator-pinned input_schema_sha256 per trusted tool (hard deny on mismatch, explicitly NOT full M6.5); PATH-resolve+canonicalize+log server.command with written disclosure of what's NOT verified (content, TOCTOU-at-spawn, interpreter-loaded modules); explicit non-sandbox language ban in all ScopeLimits-related output; AskApprovalRequired explicitly always-denies (no interactive prompt built); 4-state invocation model (DefinitelyNotSent/PossiblySent-is-ExternalSideEffectUnknown/ProtocolResultObserved) where absence of a terminal record for an invocation_id IS the documented unknown-outcome signal after a hard process kill; 3-way exit code convention (0=fully confirmed, 1=real operation failed/denied, 2=real operation succeeded but post-hoc audit write failed).

Two open forks blocking Phase 2, require explicit user choice: (a) executable identity - is path-resolve+canonicalize+disclosure sufficient, or pull binary-content hashing forward from M6.5/M6.6? (b) config file read strategy - reuse storage::handle_safety (new narrow pub surface in storage, stronger TOCTOU/symlink guarantee) vs plain trusted-local-file read (no new storage surface, weaker explicitly-documented guarantee).
