User caught a real gap in the prior design: stopping the delete/replace check at trust_boundary's immediate parent misses an ancestor further up (e.g. C:\Tools) granting FILE_DELETE_CHILD, which lets an attacker delete/rename an intermediate directory (Protected) and substitute it wholesale, orphaning everything below including a perfectly clean boundary+subtree. Corrected design: Check A (write-into-directory: FILE_ADD_FILE/FILE_WRITE_DATA/GENERIC_WRITE on the directory's own DACL) stays bounded at trust_boundary - legitimately boundable since adding content above the boundary can't alter anything inside it. Check B (delete/rename/replace: FILE_DELETE_CHILD on the parent, or DELETE/WRITE_DAC/WRITE_OWNER on the component itself) is now unbounded, runs from target's immediate parent to the filesystem root with no exception - there is no safe stopping point for this check since deleting any ancestor orphans everything beneath it regardless of depth. Both checks reuse the identical already-implemented ACE-scanning machinery with different masks, not two separate scanners. Not yet approved; no further code changes made this turn beyond prior unapproved windows_acl.rs draft.
