User rejected the "ordinary spawn then AssignProcessToJobObject" race and directed verifying PROC_THREAD_ATTRIBUTE_JOB_LIST before falling back to CREATE_SUSPENDED+ResumeThread. Confirmed viable: windows 0.62 (already a workspace dep) has CreateProcessW/STARTUPINFOEXW/InitializeProcThreadAttributeList/UpdateProcThreadAttribute/PROC_THREAD_ATTRIBUTE_JOB_LIST/PROC_THREAD_ATTRIBUTE_HANDLE_LIST, so creation-time job assignment was implemented without ever needing CREATE_SUSPENDED. New module crates/mcp-client/src/windows_job.rs (Windows-only) replaces tokio::process::Command::spawn() in registration.rs's connect_now with a raw CreateProcessW call; PROC_THREAD_ATTRIBUTE_HANDLE_LIST restricts child-inherited handles to exactly its 3 stdio pipe ends. Pipe-to-async bridge uses tokio::fs::File (AsyncRwTransport::new_client is generic over AsyncRead/AsyncWrite, not tokio::process-specific). Unix spawn path unchanged. Adversarial tests prove: process is a member of its own job; killing/dropping ContainedChild terminates a grandchild the direct child already exited from (tree-wide, not just direct child); a real job-assignment failure (injected invalid job handle, real code path) never executes the untrusted command, proven via a marker file that never appears. Real bug found+fixed during TDD: tokio::task::spawn_blocking called right after the CloseHandle-driven KILL_ON_JOB_CLOSE termination left tokio's blocking pool unable to join at runtime shutdown ("failed to join on thread: Handle non valido") even though the blocking closure itself always completed successfully - kill() now uses a plain std::thread::spawn + oneshot channel instead. 166 existing mcp-client/mcp-client-cli tests (unit+integration+acceptance) pass unchanged against the new spawn path, zero clippy warnings in the mcp-client family, zero changes outside mcp-client/Cargo.lock. M6.4/M6.5 frozen invariants (schema pinning, ACL trust boundary, audit ordering, single-server model) untouched and re-verified passing.
