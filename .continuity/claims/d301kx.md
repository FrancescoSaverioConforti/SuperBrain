Supersedes [[d299f2]]'s open-finding status. Investigated via systematic-debugging + TDD (RED confirmed by temporarily reverting just the fix with new tests in place -- both link tests failed with "got Ok(..)" against the vulnerable code, proving real exploitability, not a tautology).

Verdict: CONFIRMED EXPLOITABLE under the B5 threat model (unprivileged local process with write access to .audit/), not merely defense-in-depth. No arbitrary-content-write vector (lock file bytes are meaningless), but a planted symlink/hardlink at .audit/writer.lock could redirect the exclusive-lock anchor -- undermining single-writer exclusion (two legitimate writers could each believe they hold exclusive ownership) or causing denial of service.

Fixed at commit 6b61e21: acquire_writer_lock now opens writer.lock via handle_safety::open_verified (OpenMode::CreateOrOpenForWrite), the same primitive audit.log already used -- no new OpenMode variant, no check-then-open sequence. 4 new tests added (symlink/hardlink/directory-substitution rejection + a dual-writer regression guard). Full storage/workspace suites, build, Clippy all green. Not claiming Unix verification (tested on Windows only, same caveat as M5 Task 8A).

M5 closure tag (m5-durable-audit-closure @ 9a90891) unmoved -- this is additive hardening, not a reopening. Also pre-closes this gap for M6's own Option C (reusing Vault::open_audit_writer for a future MCP-client audit vault) before that work could have inherited it.
