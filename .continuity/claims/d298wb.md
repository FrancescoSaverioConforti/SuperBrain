User approved 6 directions from the M6.1 composition-root/trust-model proposal:
1. A separate, supervised, one-shot external MCP execution CLI, distinct from approve_cli.rs (not extending it -- rejected mixing brain-api's internal-write trust with mcp-client's external-tool trust in one process).
2. No modifications to InvocationLogEntry in this milestone unless a new explicit STOP decision is approved.
3. Independent MCP Client audit envelopes with correlation_id + invocation_id (new type, not reusing InvocationLogEntry).
4. Operator-owned TOML configuration, fail-closed, never based on server self-classification (DiscoveredTool fields are 100% server-controlled; ExternalToolMetadata fields must stay 100% operator-controlled).
5. Windows Job Objects approved as a FUTURE process-tree/resource-control mechanism (not yet scheduled this milestone) -- explicitly not a filesystem/network sandbox claim.
6. CONDITIONAL extraction of a minimal pure audit-chain-core crate (compute_record_hash/verify_link/scan_chain/record envelope, generalized over event payload type) out of brain-api's private audit_chain/audit_record modules -- condition: only if existing M5 semantics/serialized-byte/hash compatibility are preserved. Not yet unconditionally approved; a follow-up gate is in progress to verify this precisely before M6.2 begins.

Next immediate step (in progress): a focused architectural decision record on (a) secure audit-log filesystem persistence boundary for the new mcp-client-audit-worker crate (compared against storage::audit_writer's own symlink/junction/TOCTOU/locking discipline) and (b) mechanical audit-chain-core extraction feasibility (golden-vector byte/hash compatibility proof required before any extraction). M6.2 implementation is explicitly gated on this record being approved.
