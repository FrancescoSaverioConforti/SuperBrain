brain-api has zero tokio dependency and must stay that way (sync orchestration layer). New crate brain-api-audit-worker (tokio features: rt/sync/time only, no rt-multi-thread/macros — never creates its own runtime, spawns onto whatever the composition root already has) owns: bounded mpsc command channel, the dedicated single-owner writer task (no mutex — strict one-at-a-time processing is the serialization, per the M5 Task 2 finding that per-call-mutex-across-spawn_blocking is cancellation-unsafe), AuditWorkerHandle (cloneable, implements brain_api::AuditSink for best-effort + record_durable()/shutdown() for the durable path), and startup recovery via brain_api's facade.
brain_api::audit_chain stays private; only a narrow named set (GENESIS_HASH, ChainRecord, LineOutcome, scan_chain, ScanResult, ScanStopReason, ChainLinkError, may_resume_without_recovery) is re-exported from brain_api's own lib.rs facade — never audit_chain::*.
New brain_api::audit_record module (not audit_chain) owns the concrete versioned JSON line format; content_bytes hashed/verified is always the raw decoded event_json bytes, never a reparse-reserialize of the typed AuditEvent, to avoid canonicalization-based hash bypass. AuditEvent/AuditEventKind gained Deserialize (additive only, B5.12 variant/field freeze unaffected).
Each AuditWriterHandle::append call runs inside tokio::task::spawn_blocking (move handle in, get it back) so synchronous filesystem/DPAPI I/O never blocks a shared runtime worker thread.
