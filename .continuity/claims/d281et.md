Verified by direct reproduction during M5 Task 2 design: a design where record_durable holds a tokio::sync::Mutex across spawn_blocking().await is vulnerable to a real bug — if the CALLER's own task is aborted/cancelled while suspended at that await point, the mutex guard is dropped immediately (without waiting for the orphaned spawn_blocking to finish), letting a second caller acquire the mutex and start a conflicting append while the first write is still physically in flight. Reproduced: two concurrent record_durable calls, one aborted mid-write, produced a duplicate sequence number on disk. The corrected, verified-safe design: a single, dedicated long-lived background task owns the file handle and in-memory chain state exclusively; callers send requests via mpsc + a oneshot response channel. Cancelling the caller's await (dropping the oneshot receiver) never affects the writer task, which always finishes a dequeued request before looking at the next one. Reproduced clean with an aborted caller: writer task still completed A's write before processing B's, no duplicate/skipped sequence. How to apply: any future async durable-writer design in this codebase must use the dedicated-task/channel pattern for its serialization, never a mutex held across an externally-cancellable .await.
