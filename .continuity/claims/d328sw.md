Two real design forks surfaced, not resolved: (1) ExternalExecution mapping - extend AuditEventKind with new additive variants (ExternalExecutionAttempted/Outcome, mirroring M5 Task 5's own pattern) vs reuse the existing 2-field variant as a coarse synthesis event; (2) segment/rotation design - extend storage::audit_writer itself (touches a frozen, security-reviewed M5 module) vs segment above storage (each segment its own Vault-managed directory, cross-segment commitment handled in a layer storage never sees). Both forks require explicit user decision before M7.2/M7.5 design work proceeds. New stop condition found: any multi-segment audit format touches audit-chain-core's/storage's persisted envelope format, requiring approval before design, not just before implementation (stricter than originally scoped). Awaiting user's choice on both forks before M7.0 report is finalized into implementation.
