Real root cause of the windows_job.rs test concurrency flake found and fixed (commit 7930f11), superseding the earlier SPAWN_SERIALIZATION_LOCK mitigation which was confirmed via measurement to not actually explain or fix the flake (still ~5/15 failures with it in place). Root cause: test helper OwnedJobHandle::already_closed_for_test created a real job object then immediately closed it, returning the dangling handle VALUE; under heavy concurrent handle churn (host has 20 logical CPUs) a different thread's own legitimate CreatePipe/CreateJobObjectW call reliably reused that exact freed handle value for an unrelated real object before the first test's own spawn_contained_into call ran - confirmed via a mutex-protected thread-tagged diagnostic log (plain eprintln interleaves misleadingly under real concurrent process output and produced a misleading early read). Fixed by having already_closed_for_test return OwnedJobHandle::placeholder() (NULL handle, never allocated to real objects by the OS) instead of a real create-then-close round trip. SPAWN_SERIALIZATION_LOCK removed after confirming 20 clean runs with it and 20 more without it - contributed nothing once the real bug was fixed. Verified: 25 consecutive clean runs of windows_job:: at default (unbounded) parallelism, no --test-threads override; full workspace test suite run 4x consecutively clean.
