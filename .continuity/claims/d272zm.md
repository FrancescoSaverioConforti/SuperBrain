Why: rmcp dispatches each tools/call on a cloned server instance, so a non-shared semaphore would impose no real limit. Queue-without-timeout chosen over reject-on-saturation since the plan only said "queue or reject" with no numeric spec; a waiting task's own cancellation (not a semaphore timer) ends a queued wait. How to apply: any future concurrency-bounded resource in this codebase should follow the same Arc-shared-across-clones + RAII-held-permit pattern, not a per-clone or per-call semaphore.
