Real spawn site is mcp-client/src/registration.rs connect_now() (tokio::process::Command::spawn(), line ~299), NOT mcp-client-cli. windows crate 0.62 (already a workspace dependency in mcp-client-cli/storage/vault-security) has full Win32_System_JobObjects bindings (CreateJobObjectW/AssignProcessToJobObject/SetInformationJobObject/TerminateJobObject, JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE) and Win32_System_Threading has CREATE_SUSPENDED + ResumeThread. CommandExt::creation_flags is stable and tokio::process::Command forwards it. BUT: confirmed by reading tokio 1.54.1's process/windows.rs directly - tokio::process::Child::as_raw_handle() delegates to std::process::Child::as_raw_handle(), which exposes the PROCESS handle only. The THREAD handle (PROCESS_INFORMATION.hThread) that ResumeThread requires is created internally by std's Windows spawn implementation and closed there - never surfaced to any caller on stable Rust via std::process or tokio::process. Consequence: CREATE_SUSPENDED + current spawn stack would produce an unresumable suspended process (correctness-breaking). True assign-before-first-instruction containment requires replacing connect_now's spawn call with raw CreateProcessW via the windows crate - a substantial change to the already-frozen M6.4 spawn/env-isolation code path, not a narrow addition. Matches user's own M6.6 STOP condition 1 verbatim. No source/tests modified. Reported to user for decision before any implementation.
