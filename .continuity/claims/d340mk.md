Root cause, verified directly in code: mcp-audit-bridge::RunConfig has one static destination_vault_root/journal_path, zero awareness of audit-segmentation's manifest/SegmentLinkage/rotation (confirmed by grep: no cross-references in either direction). Two concrete breaks: (1) bridge dedup (scan_destination_for_imported_identities) only ever scans the one fixed destination path, so a SourceRecordIdentity whose McpBridgeEvent record lived in a segment that was rotated away and then retention-retired becomes permanently invisible to the bridge -- re-running the bridge would re-import and duplicate that fact, because RetentionReceipt/RetentionAuthorized commit only to (segment_id, final_sequence, final_record_hash) of the segment as a whole, never to the individual SourceRecordIdentity values the segment's content held. (2) registration::recover_from_destination_evidence scanning only the current segment's records: if the only McpBridgeEvent provenance for a SourceLogId lived in a now-retired segment, claimed_pairs is empty -> Ok(None) -> resolve_registration in run.rs treats this as a genuine first-ever run and silently mints a NEW SourceLogId rather than failing closed -- the exact silent-divergence failure mode the registration/checkpoint split was built to prevent. Mitigating fact: no composition root anywhere in the workspace wires rotate()/retire_segment()/run_once() together today (grep confirmed), so no real data is at risk yet -- this is a design gap to resolve before any real integration, not an active production bug. No code was changed during this review.
