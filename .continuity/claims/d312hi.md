Empirical finding during implementation: this dev host's C:\ genuinely has an Authenticated Users grant, so unconditional walk-to-drive-root rejects every path on this machine. User chose operator-configured boundary over abandoning the ancestor walk, with explicit anti-handwave requirements: boundary declaration alone proves nothing; must verify the boundary itself can't be deleted/renamed/replaced by an untrusted principal, and that the boundary's own parent doesn't grant replacement rights. Confirmed via direct bitwise check (PowerShell): [FileSystemRights]::Modify.value__ does NOT include DeleteSubdirectoriesAndFiles (FILE_DELETE_CHILD) - Modify=0x301BF, DeleteSubdirectoriesAndFiles=0x40, AND=0. This is the key fact enabling a narrower-but-still-correct design: a write-shaped grant on an ancestor ABOVE the boundary is irrelevant unless it specifically includes FILE_DELETE_CHILD targeting the right node; only the boundary's own immediate parent's delete-child grant, and DELETE/WRITE_DAC/WRITE_OWNER on every node from target to boundary inclusive, actually govern whether the boundary subtree can be substituted. New required config field: server.trust_boundary (no default, must be an ancestor of command/script, denylist of too-shallow paths like C:\, C:\Windows, C:\Users). Same-user attacker still explicitly out of scope. Not yet approved; implementation paused pending algorithm approval.
