Discovered during M6.1's security gate (read-only investigation, not yet acted on): storage::audit_writer::acquire_writer_lock (audit_writer.rs:404-417) opens .audit/writer.lock via plain std::fs::OpenOptions -- NOT through handle_safety::open_verified, unlike the audit log file itself (which does route through handle_safety::open_verified_dir/open_verified, confirmed at audit_writer.rs:352,356). Similarly, vault_security::DpapiTrustedReferenceStore::read/write (used for the DPAPI head reference) use plain std::fs::read / an atomic-write helper with no symlink verification, relying on DPAPI's own tamper-detection instead of path containment.

This is a genuine, previously-unflagged gap in already-shipped M5 code (commits 5b37ab9/a091965), not a new regression and not something M6 is scoped to fix. A symlink/hardlink planted at the lock-file or reference-file path before the writer first opens it would not be caught the way the log file itself is protected. Worth a narrow future storage/M5 follow-up task, separate from M6's own scope.
