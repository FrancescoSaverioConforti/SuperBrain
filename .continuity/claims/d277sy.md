Why: this exact sequence resolved a real case (B5 merge into main, 2026-11-19) where two untracked files on main had byte-identical content to files already committed on the incoming branch — Git refused the merge to protect them, and a naive working-tree hash check after merging showed a false mismatch purely from Windows CRLF checkout normalization, not real content loss. How to apply: reuse this exact sequence for any future merge blocked the same way; always verify post-merge integrity against the Git blob (git show HEAD:path), never the raw working-tree file, to avoid CRLF false alarms.
