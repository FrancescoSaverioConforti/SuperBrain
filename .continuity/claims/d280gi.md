Verified directly in approval.rs: reject_proposal only transitions proposal status and persists it (proposal_store::save_proposal) — it never calls execute()/propose_and_commit, never touches storage at all. Rejection is already fully represented by the existing PermissionDecision{operation:"RejectProposal", allowed:true}; no new AuditEventKind variant is needed or correct for it. The 8th variant (CommitOutcome) is scoped exclusively to approve_proposal's real commit path (Committed/GitPending/Failed). How to apply: never conflate rejection with a commit outcome in any future audit-schema work on this project.
