Empirically measured: full CLI invocation ~0.47s, with a non-trivial pre-spawn fraction (vault open + full audit-log read/scan + writer open + durable fsync'd RegistrationAttempted write) that grows with log size on every run - corrects M6.4's original "narrow (milliseconds)" disclosure. tokio::process::Command wraps std::process::Command directly; confirmed no Windows equivalent of fexecve exists (no spawn-from-open-handle primitive in std, windows crate, or NT public API without unstable internals). Job Objects confirmed NOT to help: they attach to an already-running process, have no visibility into which binary image CreateProcessW loaded. Recommended fix: staged-copy (reuse storage::write_verified_atomic via new thin pub wrapper, stage already-verified bytes into a fresh unpredictable per-run directory, spawn from the staged path) - narrows the window from "attacker-reachable long-lived path" to "near-unexploitable unpredictable-name race," explicitly NOT claimed as fully race-free. Not yet approved; no source/tests modified.
