Why: those signatures are frozen per B5.0/Task 7, and run_cli's exact (args, vault, now) signature is separately pinned by a compile-time test in brain-api/tests/layering.rs. Emission instead happens one layer up, at the two places that already build RequestContext and see each call's real Result: SuperBrainMcpServer (record_tool_call/record_write_tool_call, via an injectable AuditSink defaulting to NullAuditSink) and brain_api::run_cli_with_audit (a sibling of untouched run_cli).
How to apply: any future task adding audit coverage for a new capability, or wiring a real (non-Null) AuditSink destination, should follow this same wrap-the-caller pattern rather than touching brain-api's capability signatures. mcp-client's own InvocationLogEntry/InvocationLogSink (Task 29) stays separate and provisional -- never unified with brain_api::AuditEvent, since mcp-client has no dependency on brain-api (Task 30's separation tests enforce this structurally).
