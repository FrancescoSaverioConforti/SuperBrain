Supersedes/extends [[d296l5]]'s proposal-only status -- these 6 points are now user-APPROVED decisions, not just recommendations under review:

1. mcp-client stays independent from brain-api/storage/mcp-server and their audit workers (B5.10 isolation preserved).
2. A separate mcp-client-audit-worker crate (not a shared dependency) is the approved vehicle for durable audit orchestration/event envelopes.
3. InvocationLogEntry is NOT modified. Instead: evaluate a separate audit envelope with correlation_id + invocation_id, populated from real execution context (not inferred after the fact).
4. Windows Job Objects are approved as the first process-tree/resource-control mechanism -- but must NEVER be represented as filesystem/network sandboxing (ScopeLimits stays advisory-only; Job Objects don't change that).
5. No unsupervised agent execution capabilities -- everything stays human-supervised.
6. Previously-resolved R1-R3 (payload limits wired, client line-cap enforced, child env sanitized) must stay closed unless new source evidence shows a regression -- do not reopen speculatively.

User also named the next priority explicitly as FRAMING: mcp-client is an unwired leaf crate with no production composition root supplying trusted ExternalToolMetadata/ApprovalPolicy -- this is "the most important architectural finding" and must be addressed first, before any other M6 work. M6.1 (composition-root + trust-model design, read-only) was commissioned specifically to address this, with an explicit constraint: must NOT add external-tool execution as a 13th MCP Server capability alongside the existing 12.
