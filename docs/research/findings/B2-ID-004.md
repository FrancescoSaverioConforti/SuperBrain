# B2-ID-004: name-only call resolution lacked structural context, producing receiver-qualified and corpus-wide common-name false positives

**Discovered by:** [B2-EVAL-001](../evaluations/B2-EVAL-001.md)'s manual
analysis (Q3/Q6, the "19-for-19 false positive rate" finding), formally
root-caused and fixed under Task 9.5's Priority 5(A) authorization.

## Discovery context

B2-EVAL-001's deep-learning Q&A analysis against `pytorch/examples`
(https://github.com/pytorch/examples, BSD-3-Clause,
commit `001d493285083b54cacbc1334cb26338bdff2455`) manually confirmed two
distinct false-positive patterns in `resolve_calls`'s output, both
traced to the same underlying root cause — name-only matching with no
structural context — but manifesting through two different mechanisms.
Task 9.5's Priority 5(A) authorization required formally investigating
both before any fix, per the project's `Observed -> Reproduced -> Root
cause -> Alternatives -> Solution -> Validation` methodology, and
explicitly forbade any PyTorch-specific or name-specific (`size`,
`forward`, `encoder`, ...) patch.

## Observed evidence

**Case A — receiver-qualified call, cross-class/cross-language
collision (MEASURED):** `word_language_model/model.py`'s
`TransformerModel::forward` calls `self.src_mask.size(0)` — a method
call on `src_mask`, a real `Field` of `TransformerModel` (once
Priority 1 of this same task introduced `Field` extraction).
`resolve_calls`'s `callee_name` extraction correctly found the bare
method name `"size"`, but discarded the receiver (`src_mask`) entirely,
so name-based lookup matched it against two UNRELATED C++ `size()`
methods in `cpp/custom-dataset/custom-dataset.cpp` and
`cpp/transfer-learning/main.h` — manually confirmed unrelated to this
model in any way.

**Case B — unqualified common-name call, corpus-wide fan-out
(MEASURED, Manually validated):** asking "who calls this `forward`"
(following `incoming_edges`) on `TransformerModel::forward` returned 19
edges, every one confirmed by manual source inspection to be an
unrelated same-named `forward` method elsewhere in the 97-file corpus —
a 19-for-19 false-positive rate, described in B2-EVAL-001 as "the single
most important finding of this evaluation's manual analysis."

**Real tree-sitter shapes confirmed before any fix (Measured, not
assumed), across all 6 supported grammars** — `self.src_mask.size(0)`
(or its per-language equivalent) produces a NESTED attribute/member-
access node, never a flat list: an outer node (`self.src_mask.size`)
whose own first child is itself an attribute/member node
(`self.src_mask`), recursively, down to a `self`/`this`-bearing base:

| Language | Outer node kind | Inner (receiver) node kind | Base node |
|---|---|---|---|
| Python | `attribute` | `attribute` | `identifier` (text `"self"` — Python has NO dedicated `self` node kind) |
| Rust | `field_expression` | `field_expression` | `self` (dedicated node kind) |
| C# | `member_access_expression` | `member_access_expression` | `this` (dedicated node kind) |
| C++ | `field_expression` | `field_expression` | `this` (dedicated node kind, `->` or `.` form) |
| TypeScript/JavaScript | `member_expression` | `member_expression` | `this` (dedicated node kind) |

A SEPARATE, independently-confirmed pre-existing gap was found during
this same investigation: `callee_name`'s match arm was missing
`"member_access_expression"` (C#'s own node kind) entirely — a C#
receiver-qualified call (`this.srcMask.Size(0)`) extracted NO callee
name at all before this fix, silently, with no existing test exercising
that shape. Fixed alongside Case A as a directly adjacent, evidence-
grounded correction (not a speculative addition).

## Root cause

A single underlying defect with two distinct manifestations:
`resolve_calls` (and its `callee_name`/`call_names_in_tree` helpers)
resolved every call purely by the callee's bare final-segment name,
against the FULL corpus-wide candidate pool, with:

- **no receiver awareness** — a `recv.field.method()` call's receiver
  expression was extracted by `callee_name` only to find the final
  segment; the receiver itself was discarded before it ever reached
  `TargetLookup::find_by_name` (Case A);
- **no scope awareness** — an unqualified call's candidate pool was
  never narrowed by the caller's own enclosing class or file before
  being treated as ambiguous (Case B).

Both are instances of the same general problem — name-only resolution
lacks sufficient structural context — but Case A's fix (receiver
filtering) and Case B's fix (scope-hierarchy narrowing before deciding
ambiguity) are architecturally distinct, per the user's explicit
instruction not to force a single taxonomy where two different
mechanisms are actually at work.

## Impact

- **Severity: Important.** Neither case crashed the pipeline (unlike
  B2-ID-001/B2-ID-002) — both are precision defects in the `Calls`
  edge's own semantic correctness. Measured effect: in B2-EVAL-001's
  original run, 11,652 of 11,938 typed edges (97.6%) were
  `NameHeuristic` — overwhelmingly fan-out noise from exactly this
  defect, confirmed by the Q3/Q6 manual analysis to make the single most
  commonly-asked coding-agent question ("what does X call" / "who calls
  X" for a common method name) effectively unanswerable.

## Solution adopted

**Case A (receiver-aware filtering, CALL-RES-A3):** when a call's
callee is a receiver-qualified chain AND the receiver is literally
`self`/`this` (the caller's own instance — confirmed resolvable via the
node-kind/text rules in the table above, generalized across all 6
grammars, never Python-specific) AND the receiver names a real member
(`Field`/`Method`/`Function`) of the caller's own enclosing class
(determined via the same span-containment logic `resolve_contains`
already uses, re-derived locally rather than depending on that
resolver's `Edge` output, per `TargetLookup`'s own no-cross-resolver-
dependency rule): the candidate pool is restricted to members of THAT
SAME class. If the caller's own class has no matching member, "no edge"
is preferred over a cross-class/cross-language guess — the absence
itself is evidence the call targets an external/unresolvable type, not
a reason to search more broadly. A receiver that is not resolvably
`self`/`this` (a plain local, parameter, or alias) leaves resolution
completely unchanged — this pipeline has no type inference, so no
restriction is applied where the structural premise does not hold.

**Case B (scope-aware ambiguity narrowing, CALL-RES-A1+A2):** for an
ambiguous (more than one same-named candidate) unqualified call,
candidates are progressively narrowed: same enclosing class as the
caller, then same file as the caller. At the narrowest level that is
non-empty: exactly one candidate there is accepted as a scoped
`NameHeuristic` edge (never `StaticAnalysis` — it is still a name-based
guess, just a correctly-scoped one); more than one candidate, even at
that narrowest non-empty level, now produces **no edge at all** — a
deliberate reversal of the pre-existing policy (which emitted one
`Hypothesized` edge per ambiguous candidate, corpus-wide, unconditionally).
"Unresolved: no candidate" and "unresolved: ambiguity remains" are kept
as distinct outcomes, per the Evidence-before-claims Experimental
Policy — no arbitrary candidate-count threshold is used anywhere in
this logic; every narrowing step is a structural scope boundary (class
membership via span containment, or file identity), never a tuned
number.

**This whole change is recorded as an experimental configuration**
(CALL-RES-A1 + A2 + A3), not a proven-final answer — see
`docs/research/EXPERIMENTAL_POLICY.md`. It must eventually be compared
against the permissive baseline (CALL-RES-A0) and against precision-
first suppression without scoping (CALL-RES-A1 alone) once sufficient
ground truth exists across the multi-domain validation suite.

## Alternatives considered

### A. Type inference / full points-to analysis (rejected for this task)

Would resolve both cases more completely (e.g. correctly handling a
receiver that is a plain local variable of a known type), but is a
categorically larger undertaking explicitly out of this task's
evidence-driven scope — recorded in the Experimental Policy's backlog
(CALL-RES-A5/A6) as a future candidate, not attempted here.

### B. Suppress ALL ambiguous edges unconditionally, no scoping (considered, user-directed alternative to evaluate later)

Simpler than the adopted scoped narrowing, but discards the real,
stronger signal that a same-class or same-file ambiguity is already
much better evidence than a corpus-wide one. The user's explicit
decision was to try narrowing FIRST and only suppress once narrowing is
exhausted — this alternative (CALL-RES-A1 without A2) remains an
open comparison point for the future ablation study the Experimental
Policy requires, not adopted as this task's main behavior.

### C. Heuristics keyed on the common name itself, or on which
### directory/corpus the collision happens to occur in (rejected)

Explicitly the kind of overfit-to-this-corpus fix the task's own
authorization forbade — rejected outright, never implemented, not even
as a fallback.

## Validation

- 36 new/updated unit tests in `crates/codegraph-index/src/edges/calls.rs`
  covering: a receiver-qualified call restricted to the caller's own
  class even with a same-named method elsewhere; a receiver-qualified
  call that still resolves when the match genuinely belongs to the
  caller's class; two classes in the same file with their own same-
  named method not cross-resolving via receiver; an unqualified call
  unaffected by the receiver restriction; a `self`-qualified call whose
  field is not a known member falling back to unrestricted matching;
  deterministic behavior regardless of snapshot pool ordering; a repo-
  wide ambiguous call with no scope signal producing no edge; an
  ambiguous call narrowed to the caller's own file producing one scoped
  heuristic edge; two same-file candidates still producing no edge;
  class-level narrowing taking priority over file-level narrowing; and
  B2-ID-002-shaped dedup regressions re-verified under the new scoping
  logic (repeated occurrences of a now-resolved-or-still-ambiguous call
  never produce duplicate or spurious edges).
- Full workspace test suite: 318 tests in `codegraph-index` (up from
  308 before this fix), all passing; full workspace (`cargo test
  --workspace --locked`) green; `cargo clippy --workspace --locked -- -D
  warnings` clean; `cargo deny check` clean (advisories/bans/licenses/
  sources all ok).
- **Real-corpus reproduction (MEASURED):** re-ran the production
  pipeline against a freshly re-cloned `pytorch/examples` at the exact
  commit B2-EVAL-001 used (`001d493285083b54cacbc1334cb26338bdff2455`).
  Q3 (`TransformerModel::forward`'s outgoing calls) changed from 2
  confirmed false positives (`cpp/custom-dataset/custom-dataset.cpp::size`,
  `cpp/transfer-learning/main.h::size`) to 5 genuine `Field` calls
  (`input_emb`, `decoder`, `_generate_square_subsequent_mask`,
  `encoder`, `pos_encoder`) — 0 false positives, matching the forward-

  (incoming callers of `forward`) changed from 19 confirmed false
  positives to exactly 1 edge, a `Contains` edge (the class containing
  its own method, not a spurious `Calls` edge) — 0 false-positive
  `Calls` edges. B2-ID-003's own chained-call regression check
  (`TransformerModel::forward` resolving `_generate_square_subsequent_mask`)
  remained `true` across this re-run, confirming no interaction
  regression between B2-ID-003's fix and this one.

## Literature / authoritative evidence

Scope-aware and receiver-aware call resolution are standard, well-
established techniques in static call-graph construction (class-
hierarchy analysis and its refinements routinely use declared/receiver
type information to prune candidate call targets). No single paper is
cited as the specific source of this project's own narrowing rule
(span-containment-derived class membership, then file identity) — that
rule is this project's own engineering choice, grounded in what
structural information this pipeline already has (byte spans, Task 8/
9.5's own `Contains`-equivalent logic), not a direct implementation of
a named published algorithm. Per the Evidence-before-claims
Experimental Policy, this is recorded as a project hypothesis informed
by general literature-supported principles, not as literature-validated
in its specific form.

## Residual limitations

- Case A only resolves the `self`/`this`-qualified-receiver shape.
  A receiver that is a plain local variable, parameter, or module alias
  (e.g. `x = get_model(); x.forward()`) is NOT restricted by this fix —
  this pipeline has no type inference, so no honest restriction can be
  applied there yet. Recorded as a future candidate for CALL-RES-A5
  (type-aware resolution), not attempted here.
- Case B's scope hierarchy stops at "same file." Import/visibility-aware
  narrowing (CALL-RES-A4, Priority 6 and beyond) is a planned next level
  between "same file" and "no edge," not implemented in this finding.
- Neither case performs cross-class type inference for a `Field`'s own
  declared/inferred type — Case A relies entirely on the receiver NAME
  being a real member of the caller's OWN class, not on knowing what
  TYPE that member actually is. A `Field` whose constructor call
  resolved via `Instantiates` (Priority 3) is not yet cross-referenced
  here to further narrow Case A's candidate pool by the field's actual
  resolved type — a plausible future refinement, not implemented, since
  it was not required to fix the two confirmed false positives this
  finding addresses.
- This fix does not change `resolve_tests_for`, `resolve_imports`, or
  `resolve_extends_implements` — only `resolve_calls`. Each of those
  resolvers has its own separate name-matching logic and was not
  re-audited for the same class of defect as part of this finding (out
  of this task's scope; `resolve_tests_for` was already separately
  audited and found not vulnerable to the UNRELATED B2-ID-002 dedup
  defect, which is not the same question).
