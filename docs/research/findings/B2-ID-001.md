# B2-ID-001: `SymbolSnapshotId` collides for two distinct symbols with identical name and body in one file

## Discovery context

Real-repository smoke test checkpoint (B2, post-Task-9), running the
production pipeline (`RepositorySource` → parse → extract → promote →
lineage → edges → `CodeGraph`) against:

- **Repository:** `pytorch/examples` — https://github.com/pytorch/examples
- **License:** BSD 3-Clause (`LICENSE` at repo root, "Copyright (c) 2017,
  Pytorch contributors")
- **Commit:** `20955149ad6ea97a4f403e5a56c95a39e568ccbe` ("Bugfix in
  vision transformer example - change lr datatype to float (#1161)")
- **File:** `word_language_model/model.py`

## Observable evidence

**Observed:** `resolve_lineage(&[], &snapshots, &no_known_lineage)` (and,
equivalently, `CodeGraphIndexer::observe_commit`) returned
`Err(LineageResolutionError::DuplicateSnapshotId)` /
`Err(GraphError::DuplicateSnapshot)` when run against the real snapshot
pool extracted from this commit. A diagnostic pass isolating the exact
colliding group found:

```
word_language_model/model.py::init_weights [Function]
word_language_model/model.py::init_weights [Function]
```

Reading the actual source at that commit confirmed two SEPARATE method
declarations:

```python
class RNNModel(nn.Module):
    ...
    def init_weights(self):
        initrange = 0.1
        nn.init.uniform_(self.encoder.weight, -initrange, initrange)
        nn.init.zeros_(self.decoder.bias)
        nn.init.uniform_(self.decoder.weight, -initrange, initrange)
```

```python
class TransformerModel(nn.Module):
    ...
    def init_weights(self):
        initrange = 0.1
        nn.init.uniform_(self.encoder.weight, -initrange, initrange)
        nn.init.zeros_(self.decoder.bias)
        nn.init.uniform_(self.decoder.weight, -initrange, initrange)
```

Byte-for-byte identical bodies, identical name, same file, same
`SymbolKind` (the Task 4 Python extractor emits a bare method name with
no enclosing-class qualification — `name` is just `init_weights` in
both cases).

**Inferred:** this is not an artifact of this one repository. Any
language/codebase where two methods in different classes (or two
closures/nested functions) happen to share both name and body text in
the same file will hit the same collision, since nothing in the `v1`
identity scheme distinguishes them.

## Root cause

`SymbolSnapshotId::derive` (v1, Task 1/5) hashed exactly
`(RepositoryId, CommitHash, relative_path, SymbolKind, name,
signature)`. This implicitly assumed that tuple uniquely identifies a
declaration within one file at one commit. The assumption is false: it
has no notion of the symbol's enclosing scope (class/namespace) or its
position in the file, so two syntactically distinct declarations that
happen to share name, kind, and exact body text are indistinguishable
to the hash. This is a **data-model deficiency** — the identity
contract itself was under-specified, not a hash-algorithm weakness and
not a bug in any one extractor.

## Impact

- **Correctness:** Critical within its own scope — it causes
  `CodeGraph`/`resolve_lineage` to reject genuinely valid, non-colliding
  real-world input as a caller-invariant violation (`DuplicateSnapshotId`
  /`DuplicateSnapshot`), which is worse than silently merging two
  symbols: it crashes the pipeline outright on real code.
- **Robustness:** the smoke test could not proceed past the very first
  real repository tried, confirming this was not a rare edge case for
  real code (the specific shape — an `init_weights`/`forward`/`reset`-
  style boilerplate method repeated near-verbatim across sibling model
  classes — is common in ML codebases specifically).
- **Severity: Critical.** It is a correctness failure that blocks the
  pipeline entirely on realistic input, discovered by the very first
  real repository exercised, not a rare or synthetic corner case.

## Solution adopted

Added the symbol's own source `ByteSpan` (`span_start`, `span_end`,
zero-based end-exclusive byte offsets — Task 4's existing convention,
already carried on every `SymbolSnapshot`) to the canonical identity
tuple:

```
(RepositoryId, CommitHash, relative_path, SymbolKind, ValidatedName,
 BoundedSignature, span_start, span_end)
```

Bumped the domain/version separator from `superbrain-symbol-snapshot-v1`
to `superbrain-symbol-snapshot-v2` — the canonical field set changed,
not merely an encoding detail, so the version marker changed too, per
this project's own stated discipline ("don't pretend it's still v1").
`span_start`/`span_end` are each hashed as a fixed-width 8-byte
little-endian `u64`, consistent with every other fixed-width field in
the scheme (no length prefix needed, since their width never varies).

**Why this resolves the root cause, not just the symptom:** two distinct
syntactic occurrences in the same file necessarily occupy different
byte ranges (`ByteSpan`s cannot both start and end identically unless
they are literally the same occurrence of the same node). Adding the
span therefore makes a within-file collision from OUR OWN encoding
structurally impossible, closing the exact gap the real data exposed,
without touching anything about cross-commit continuity.

**Invariant introduced:** `SymbolSnapshotId` now additionally encodes
"where in the file," not just "what." A direct, explicit consequence:
moving a symbol within its own file (even with identical name/body)
now changes its `SymbolSnapshotId`. This is intentional, not a
regression — continuity across such a move is `SymbolLineageId`'s job
(Task 6), which already treats a move/rename as a `Hypothesized`
similarity-based link, never an identity-preserving no-op. The two
concerns (within-commit identity vs. cross-commit continuity) are now
cleanly separated, consistent with how the project already treated
them conceptually before this fix — this just makes `SymbolSnapshotId`
honest about not promising cross-position stability it was never meant
to provide.

## Alternatives considered

### A. Add `ByteSpan` to the Snapshot ID (adopted)

Pros: minimal, uses data already captured and validated by `promote`
(no new extraction work); closes the collision structurally; keeps
`SymbolSnapshotId` a pure function of already-available inputs.
Cons: a symbol's id now changes when it moves within its own file, even
with no other change — addressed above as an accepted, documented
property, not a defect.

### B. `QualifiedName` (scope-chain qualification)

Example: `RNNModel.init_weights` vs. `TransformerModel.init_weights`.
Semantically richer — the id would then also communicate "which class
this method belongs to," useful for `get_code_context` and for a human
reading an id. Rejected for THIS fix: Task 4 does not yet have a real
scope-chain resolver (no extractor currently threads "what class am I
nested inside" into a candidate's `name`), so building a true
`QualifiedName` now would mean either (a) a half-real qualification
that still cannot distinguish every case a real scope resolver would,
while *falsely implying* it is a trustworthy qualified name, or (b) a
larger, out-of-scope extractor redesign across all nine languages. The
project's own instruction was explicit: do not introduce a false
`QualifiedName` just to patch this bug. `ByteSpan` closes the actual
collision without requiring that larger redesign; `QualifiedName`
remains a legitimate, separate future enhancement (tracked as a
residual limitation below), not a replacement for this fix.

### C. Random UUID (no derivation)

Rejected: loses determinism. Task 9's incremental reindex and Task 6's
lineage resolver both depend on re-deriving the SAME id for the SAME
observed symbol without a separate persisted lookup table — a random id
would require exactly that lookup table to exist and never be lost,
which contradicts this pipeline's current in-memory-only, no-
persistence scope (Gate S1).

### D. Accept duplicate snapshot ids (relax the graph's invariant)

Rejected outright. `CodeGraph`'s duplicate-id rejection (Task 8) is
correct and load-bearing — relaxing it to tolerate two unrelated
snapshots sharing an id would not fix anything; it would silently merge
two genuinely distinct symbols' edges/lineage into one node, hiding a
real semantic collision behind a graph that still "works." The
collision needed to be prevented at the identity layer, not tolerated
at the storage layer.

## Validation

- **Regression tests added** (`crates/codegraph-domain/src/snapshot_id.rs`):
  1. identical input including span → same id (determinism preserved);
  2. different `span_start` alone, everything else equal → different id;
  3. different `span_end` alone, everything else equal → different id;
  4. direct regression reproduction of the real case: two `Method`
     snapshots named `init_weights` with byte-identical bodies in the
     same file, at two different (realistic) byte ranges → distinct
     ids;
  5. golden vector: an independently hand-written re-implementation of
     the v2 encoding (not calling `derive`'s own helpers) matching
     `derive`'s actual output bit-for-bit, pinning domain separator,
     field order, length-prefix width/endianness, kind discriminant,
     AND the new span field's width/endianness/position;
  6. explicit proof the domain separator actually changed (an
     independently-built v1-style digest differs from the real v2
     output for the same logical fields).
- All prior `v1`-era structural tests (collision-from-concatenation,
  different name/signature/kind/file/repo/commit → different id) kept
  and updated to the new six-parameter signature
  (`derive(file, kind, name, signature, span_start, span_end)`), still
  passing.
- **Full workspace test suite:** `cargo test --workspace --locked` —
  all green (`codegraph-domain` 69 passed, `codegraph-index` 282
  passed, 0 failed, across every crate).
- **Clippy:** `cargo clippy --workspace --locked -- -D warnings` —
  clean.
- **`cargo deny check`:** clean (advisories/bans/licenses/sources all
  ok).
- **Mutation testing:** targeted sweep on `crates/codegraph-domain/src/snapshot_id.rs`
  — 6 mutants, 5 caught, 1 unviable, **0 missed**.
- **Real-repository reproduction:** re-ran the exact smoke-test pipeline
  against `pytorch/examples` at the same commit — the
  `DuplicateSnapshotId`/`DuplicateSnapshot` failure no longer occurs; a
  diagnostic duplicate-group scan over the full 567-snapshot pool
  extracted from that commit found zero remaining collisions.
- **Independent review** (`agent-protocols:code-reviewer`, combined
  with B2-ID-002): **APPROVE**. No critical or important findings.
  Independently traced the v2 hash encoding field-by-field against the
  golden-vector test's own independent re-implementation, confirmed
  all 30 real call sites of `SymbolSnapshotId::derive` across the repo

## Literature / authoritative evidence

Searched for literature on (1) program entity identity / stable
identifiers for source-code elements, (2) source-code entity matching
across versions, (3) source-position-based identification, (4) code
differencing / AST-based entity matching.

- **Godfrey, M. W., & Zou, L. (2005).** "Using Origin Analysis to Detect
  Merging and Splitting of Source Code Entities." *IEEE Transactions on
  Software Engineering*, 31(2), 166–181.
  DOI: [10.1109/TSE.2005.28](https://doi.org/10.1109/TSE.2005.28).
  **Supports:** that identifying "the same" program entity — even just
  across versions, a related but distinct problem from this finding's
  within-one-commit identity question — is a genuinely hard, actively
  researched problem; their technique deliberately combines several
  weak signals (name similarity, declaration similarity, metrics,
  call-dependency similarity) precisely because no single signal,
  especially name alone, is sufficient. This supports the project's own
  separation of within-commit identity (`SymbolSnapshotId`) from
  cross-commit continuity (`SymbolLineageId`, itself similarity-based
  and explicitly never certain) as the right shape for the problem, not
  an accident of scope-splitting.
- **Falleri, J.-R., Morandat, F., Blanc, X., Martinez, M., & Monperrus, M.
  (2014).** "Fine-grained and Accurate Source Code Differencing."
  *Proceedings of ASE 2014*, pp. 313–324.
  DOI: [10.1145/2642937.2642982](https://doi.org/10.1145/2642937.2642982).
  **Supports:** the GumTree algorithm matches AST nodes between two
  versions using tree STRUCTURE and POSITION, not textual/name content
  alone — directly supporting the general principle that structural
  position is a recognized, literature-grounded disambiguating signal
  when name or textual content alone is ambiguous, which is the
  specific principle `ByteSpan`-as-identity-component relies on (though
  the specific engineering choice of "add byte-span to this particular
  hash" is this project's own decision, not a claim from the paper).
- Liu, B., et al. (2023), "Automated Software Entity Matching Between
  Successive Versions" (ASE 2023) was also found and corroborates the
  Godfrey & Zou point with current (2023) evidence that version-to-
  version entity matching remains an open, actively improved problem —
  cited here as secondary corroboration, not as independent primary
  support for a different claim.
- No single peer-reviewed source was found making, as its primary
  thesis, the specific converse claim "same name does not imply same
  entity" in exactly those terms — the clone-detection literature's own
  taxonomy (Type 1–4 clones) treats name and structure as separate axes
  implicitly, but no one paper was identified as the clean, on-point
  citation for that specific converse framing. Recorded honestly as:
  the Godfrey & Zou and Falleri et al. papers above are the strongest
  available adjacent support, not a perfect-fit citation for this exact
  phrasing.

## Residual limitations

- `SymbolSnapshotId` still carries no notion of enclosing scope/class.
  Two methods named `init_weights` in different classes now get
  DIFFERENT ids (because they occupy different byte ranges), which
  fixes the collision, but the id alone still cannot answer "which
  class is this method on" the way a true `QualifiedName` could. A
  human or a future `get_code_context` consumer reading a bare
  `SymbolSnapshot` still needs to combine `file()` + `span()` with
  external context to recover the enclosing class — this fix did not
  add scope-chain information to the snapshot itself, by design (see
  Alternative B above).
- A symbol's id now changes whenever its position in the file changes,
  even for a trivial, non-semantic edit far above it in the same file
  (e.g. adding a blank line before it shifts every byte offset after
  it). This was already implicitly true before this fix too (since
  `signature_text` capturing a shifted node's bytes would already
  change *something* relevant to the id in most real edits), but this
  fix makes the sensitivity to position explicit and unconditional.
  Lineage resolution (Task 6) is the layer responsible for recognizing
  "this is still logically the same symbol" across such a shift; this
  finding does not change or improve that resolver's own accuracy.
  Confirmed in this finding's own real-repository reproduction: the
  incremental A→B test (see B2-ID-002 / the smoke-test report) showed
  13 snapshots removed and 13 added for one file whose content changed,
  consistent with spans shifting for every symbol at or after the edit
  point within that file, with lineage edges linking several of them
  forward as `Hypothesized`.
- This fix only prevents collisions arising from OUR OWN encoding
  within one file. It is not, and was never claimed to be, cryptographic
  collision resistance against an adversarial input engineered to
  defeat SHA-256 itself — consistent with the same caveat already
  documented for the `v1` scheme.
