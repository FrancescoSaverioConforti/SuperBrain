# B2-ID-005: the original symbol-to-symbol `EdgeKind::Imports` model had the wrong semantic granularity and was removed, replaced by a file-level `ImportFact` model

**Discovered by:** [B2-EVAL-001](../evaluations/B2-EVAL-001.md)'s
quantitative measurement (0 of 589 real import statements captured),
formally root-caused and redesigned under Task 9.5's Priority 6
authorization.

## Discovery context

B2-EVAL-001 measured, against `pytorch/examples`
(https://github.com/pytorch/examples, BSD-3-Clause, commit
`001d493285083b54cacbc1334cb26338bdff2455`), that Task 7's original
`resolve_imports`/`EdgeKind::Imports` produced exactly 0 edges while the
corpus contained 589 real, line-counted import statements. That
evaluation recorded the gap as a "0% real-data capture" finding, but
explicitly deferred root-causing and redesigning it (per that
checkpoint's own "do not implement fixes during the smoke test"
instruction). Task 9.5's Priority 6 authorization required formally
investigating and redesigning it.

## Previous model

`resolve_imports` (in `edges/imports.rs`, now deleted) produced
`Edge { from: SymbolSnapshotId, to: SymbolSnapshotId, kind: EdgeKind::Imports, .. }`
— i.e. it claimed ONE SPECIFIC SYMBOL "imports" another, exactly
mirroring `resolve_calls`'s own shape. It worked by re-parsing each
`SymbolSnapshot`'s OWN `signature_text` (the same text every other Task
7 resolver re-parses) and walking it for import-shaped nodes.

## Why it was rejected

A granularity mismatch, not a fixable matching-logic bug:

- A real import statement (`import torch`, `from foo.bar import Baz`,
  `use crate::helper::run;`, `using System;`) is written ONCE, above or
  alongside every symbol in that file — it is a FILE/MODULE-level fact,
  never more "true" of one symbol in that file than of any other.
- Task 4's extractors capture a symbol's `signature_text` starting at
  that symbol's OWN construct (`fn`, `class`, `def`, ...). A file-level
  import statement written above a function or class is OUTSIDE that
  function's/class's own byte span — it is simply never present in the
  text the original resolver re-parsed. This is why the original design
  worked in its OWN unit tests (which artificially inlined the import
  statement into the fake `signature_text` fixture argument) but
  essentially never fired on genuinely extracted data.
- Even granting a design that somehow found the statement, "which ONE
  symbol in this file imports it" has no honest, non-arbitrary answer.
  Every alternative considered for "whose `from` should this edge use"
  either fabricates a false per-symbol dependency, picks an arbitrary
  unmotivated "representative" symbol, or prematurely decides the still-
  open `Module`/`File` structural-node question Priority 2 of this same
  task already deferred.

## Empirical evidence

B2-EVAL-001 (MEASURED): 589 real import statements (line-based count)
across the Python files in a 97-file real corpus; 0 `Imports` edges
produced by the original design on the exact same corpus/commit.

**Re-verification after this finding's fix (MEASURED, same repository/
commit, via the real `CodeGraphIndexer` production pipeline — not a
manually-reconstructed resolver call):** 691 `ImportFact`s extracted
(589 being the naive per-LINE heuristic count, 691 being the correct
per-STATEMENT count once a single `from X import a, b, c` line's
multiple imported names are each counted as their own fact — confirmed:
52 real lines in this corpus import more than one comma-separated name).
Of these 691 facts: 41 `Internal` (resolved to a real indexed snapshot),
621 `External` (correctly left unresolved, no invented target), 29
`Ambiguous` (correctly left unresolved, no arbitrary pick), 155 carrying
a captured alias.

**Incremental semantics (MEASURED, real A→B run on this corpus, 1 file
changed out of 97):** `raw_import_statements_extracted: 4` (only the one
changed file's own statements re-extracted), `raw_import_statements_reused:
687` (the other 96 untouched files' raw statements carried forward,
never re-parsed), `import_facts_resolved: 691` (resolution always
recomputed from the full current pool, per this finding's own
correctness-first incremental policy — see "Alternatives considered,"
option D).

## Root cause

Confirmed: a mismatch between a file/module-level visibility fact and a
symbol-to-symbol graph edge schema. The original design encoded an
import as if it were a relationship between two specific code
constructs (like a call or an inheritance relationship); it is actually
a relationship between a FILE and a module/symbol, with no single
code-construct endpoint on the importing side that is more correct than
any other in that same file.

## Alternatives considered

### A. Emit the Imports edge from EVERY symbol in the importing file (rejected)

Would make "file F imports X" artificially look like "every symbol in F
depends on X," a claim this pipeline cannot honestly make without real
symbol-level reference/data-flow analysis (confirmed: a file-level
import is routinely unused by many of that file's own symbols in real
code). Rejected for fabricating a false per-symbol dependency.

### B. Emit from one arbitrarily-chosen "representative" symbol per file (rejected)

Avoids the fan-out of option A but introduces an unmotivated "which
symbol represents the file" choice with no real semantic meaning —
precisely the shape of ambiguity-by-convenience this project rejected
in B2-ID-003 (an arbitrary pick among equally-plausible candidates).

### C. Introduce a real/synthetic `Module`/`File` structural node now (deferred, not rejected outright)

Would give `Imports` a genuinely correct, non-arbitrary `from` endpoint
(`Module/File --Imports--> target`). Deliberately NOT done in this
finding: Priority 2 of this same task already deferred introducing a
synthetic `Module`/`File` snapshot as out of evidence-driven scope, and
this finding does not reopen that decision prematurely. If the future
multi-domain validation suite shows a real `Module`/`File` node is
needed, `ImportFact` is designed to migrate cleanly into
`Module/File --Imports--> target` without re-deriving thousands of
semantically-false edges from scratch — the raw/resolved fact data
itself does not change, only which container object would eventually
own it.

### D. Separate file-level `ImportFact`, with import RESOLUTION recomputed from scratch on every commit (ADOPTED)

`ImportFact` is keyed directly by `FileIdentity` (`importing_file:
FileIdentity`), with no `SymbolSnapshotId` anywhere in its own shape,
and is NOT inserted into `CodeGraph` (no persistence, no API, no MCP) —
a separate in-memory structure (`CodeGraphIndexer`'s `RepositoryState`
now holds `raw_import_statements`/`import_facts` alongside its
`CodeGraph`, not inside it). Local SYNTAX EXTRACTION (which import
statements exist, and what they literally say) is kept incremental —
reused for every untouched file, re-extracted only for changed/new
files — but semantic RESOLUTION (what each statement's target actually
resolves to) is ALWAYS recomputed from the complete current snapshot
pool on every single `observe_commit` call, never incrementally reused,
even for an untouched file's own unchanged import text. This is a
deliberate correctness-first choice, not yet an optimized incremental
resolution: an untouched file's import statement can still have its
correct RESOLUTION change because some OTHER file's target symbol was
renamed, moved, added, or removed — confirmed by a dedicated regression
test (`an_import_facts_resolution_changes_when_its_target_is_added_even_though_the_importing_file_is_untouched`)
reproducing exactly this scenario. Chosen over silently serving a stale
resolution, and documented here as a residual limitation (see below),
not hidden.

## Solution adopted

1. **Deleted** `EdgeKind::Imports`, `resolve_imports`
   (`edges/imports.rs`), and all their wiring (`resolve_all_typed_edges`,
   the smoke-test harness's old imports, `edge_kind_rank`). Kept a
   documentation trail at each removal site (see `edges/mod.rs`'s own
   doc comment and `kind.rs`'s `EdgeKind::Implements` doc comment,
   immediately preceding where `Imports` used to sit) explaining why the
   variant is gone, rather than a silent disappearance.
2. **Added** `codegraph_index::imports`: `RawImportStatement` (pure
   syntax: module path, optional imported symbol, optional alias,
   source span — no resolution), `ImportFact` (a resolved raw statement:
   adds `importing_file: FileIdentity` and `resolution:
   ImportResolution`), and `ImportResolution` (`Internal(SymbolSnapshotId)`
   | `External` | `Ambiguous` — `Internal` is the ONLY variant carrying
   a real target; `External`/`Ambiguous` never invent one, mirroring
   every other resolver's "no edge beats a false edge" discipline).
3. **Split extraction from resolution architecturally**, per the user's
   explicit instruction: `extract_import_statements` (pure, pool-
   independent syntax walk reused by `incremental::pipeline::index_files`
   for exactly the files it parses) vs. `resolve_raw_import_statements`
   (the global semantic resolution phase, called by
   `incremental::indexer::CodeGraphIndexer` once the full current
   snapshot pool — untouched + freshly rebuilt — is assembled, the SAME
   requirement `edges::resolve_all_typed_edges` already has).
4. **Wired into the real production pipeline**: `PipelineOutput` now
   carries `raw_import_statements`; `CodeGraphIndexer`'s
   `RepositoryState` tracks both `raw_import_statements` (incrementally
   reused) and `import_facts` (always fully recomputed); `ObserveOutcome`
   exposes `import_facts: Arc<Vec<ImportFact>>` with the SAME atomic
   publication/race-safety discipline `graph` already had (a stale
   generation can never publish stale import facts, confirmed by a
   dedicated race test).
5. Extended `IndexMetrics` with `raw_import_statements_extracted`,
   `raw_import_statements_reused`, `import_facts_resolved`, so the
   incremental efficiency of extraction (vs. the deliberate full
   recomputation of resolution) is directly measurable, not just
   asserted.

## Literature / authoritative evidence

The distinction this finding formalizes — local syntax extraction vs.
global semantic (name/symbol) resolution — is standard practice in
compiler front-end and static-analysis pipeline design (a parser/
lexer's import-statement recognition is routinely a separate phase from
a linker's or module-resolver's symbol binding). No single paper is
cited as the specific source of this project's own `ImportFact`
data shape or its correctness-first re-resolution policy — both are
this project's own engineering choices, informed by that general
principle, not a direct implementation of a named published algorithm.
Per the Evidence-before-claims Experimental Policy, this is recorded as
a project hypothesis informed by a general literature-supported
principle, not as literature-validated in its specific form.

## Residual limitations

- Import RESOLUTION is recomputed from scratch on every single
  `observe_commit` call, never incrementally reused — a deliberate
  correctness-first choice (see "Alternatives considered," option D),
  not yet an optimization. On a large repository with many import
  statements, this is a real, measured cost (`import_facts_resolved`
  tracks it); a future incremental-resolution design (invalidating only
  the facts whose target's resolvability could plausibly have changed)
  is a candidate follow-up, not implemented here.
- `ImportFact` has no `Module`/`File` structural owner — it is queried
  directly by `FileIdentity`, not via a graph traversal from a
  `Module`/`File` node, because no such node exists yet (Priority 2's
  own deferred decision, not reopened here). `ImportFact`'s own shape
  is designed to migrate cleanly if that decision changes later (see
  "Alternatives considered," option C), but that migration itself is
  not implemented.
- This resolver (like every other in this crate) does not resolve a
  module PATH itself to a file (e.g. confirming `foo.bar` in `from
  foo.bar import Baz` actually corresponds to a real `foo/bar.py` file
  in the repository) — only the imported NAME is resolved against the
  snapshot pool, exactly mirroring the removed design's own matching
  convention (that part was never the defect). A path-to-file
  resolution step is a candidate future refinement, not attempted here.
- `ImportFact` is not exposed through any persistence/API/MCP layer —
  purely an in-memory structure returned from `CodeGraphIndexer::observe_commit`,
  per the task's explicit "no Task 10/API/MCP" scope boundary.
