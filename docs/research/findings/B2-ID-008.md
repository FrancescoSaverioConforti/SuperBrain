# B2-ID-008: Rust `impl` blocks are never extracted as symbols, so `Extends`/`Implements` coverage on Rust is structurally zero on any real repository

**Discovered by:** [B2-EVAL-005](../evaluations/B2-EVAL-005.md) (multi-codebase
validation, Rust/systems domain, `sharkdp/fd`), immediately upon observing
`extends_implements_edges: 0` on a real corpus containing 2 real traits
and 41 real `impl` blocks — the very first real-repository measurement
of this resolver against genuine Rust `impl` syntax (every prior B2
evaluation's own corpus was Python/C++/Backend-Python/Frontend-TS; this
is the first Rust-source-analyzing-Rust-source checkpoint).

## Discovery context

The user's explicit protocol for B2-EVAL-005 named trait/impl analysis
as "a specific priority" and asked, among other questions: "which
traits does this type implement?" and "which types implement this
trait?" Running the real production pipeline's own `resolve_extends_implements`
against `sharkdp/fd` (a real, MIT/Apache-2.0-licensed Rust CLI tool)
produced zero `Extends`/`Implements` edges, despite the corpus
containing `trait Matcher` (6 real implementors: `RegexSet`, `GlobSet`,
`GlobMatcher`, `FixedStrings`, `ExactStrings`, `MatchAll`) and
`trait SanitizeErr` (3 real implementors: `&str`, `io::Error`,
`ignore::Error`), both confirmed by direct source reading
(`src/patterns.rs`, `src/error.rs`).

## Observable evidence

**Observed (Measured, real repository, `sharkdp/fd` at commit
`23815624819c77ab665e19c8e6c28bddbcd96e1d`):**

| Metric | Value |
|---|---:|
| Real `trait` declarations in corpus | 2 (`Matcher`, `SanitizeErr`) |
| Real `impl` blocks in corpus | 41 |
| Real `impl Trait for Type` blocks (trait impls) | 23 |
| Real inherent `impl Type` blocks (no trait) | 18 |
| `extends_implements_edges` produced by the real pipeline | **0** |

**Observed (Measured, root-cause confirmation via direct source
reading):** `crates/codegraph-index/src/extract/rust.rs`'s own `walk`
function matches exactly five node kinds: `struct_item`, `enum_item`,
`trait_item`, `function_item`, `function_signature_item`. It does
**not** match `impl_item` at all — no `RawSymbolCandidate` is ever
produced for an `impl` block, inherent or trait, anywhere in this
extractor.

**Observed (Measured, direct reading of `edges/extends_implements.rs`):**
`resolve_extends_implements` iterates over `lookup.snapshots()` (every
EXISTING `SymbolSnapshot`), re-parses each one's own `signature()` text
standalone, and calls a per-language `collect_*` function
(`collect_rust_impl_trait` for Rust) that walks that re-parsed fragment
looking for an `impl_item` node. `collect_rust_impl_trait`'s own logic
is correct Rust syntax handling (confirmed, see "What already works"
below) — but it can only ever find an `impl_item` if ONE OF THE
SNAPSHOTS THE RESOLVER IS GIVEN happens to have an `impl_item` inside
its own signature span. Since `extract/rust.rs` never produces a
candidate whose span IS an `impl_item` (the prior paragraph), and no
`struct_item`/`enum_item`/`trait_item`/`function_item` node's own span
ever CONTAINS a sibling `impl_item` as a descendant (Rust's grammar
places `impl` blocks as top-level siblings of the type/trait they
reference, never nested inside either one), `collect_rust_impl_trait`
is **structurally unreachable** against any real Rust source — not
merely under-tested, genuinely dead code on the real-world code path.

**Observed (Measured, confirmed directly in this project's own test
suite, `edges/extends_implements.rs` lines ~825-841):** this was already
suspected and explicitly documented by a prior task
([B2-ID-007](B2-ID-007.md)'s own closing work): a test named
`rust_impl_trait_is_unaffected_by_the_boundary_fix` states in its own
comment: *"Rust's real Task 4 extractor never captures an `impl` block
as its own `RawSymbolCandidate` at all... never exercised against Rust
`impl` syntax in practice."* Every existing Rust-focused test in this
file constructs its `impl`-block snapshot via a **hand-written
placeholder signature string** (e.g. `test_snapshot("src/shape.rs",
"Shape", "struct_item", "impl Shape for Circle { ... }")` — note the
`kind_hint` is `"struct_item"`, a label chosen purely so the test
harness accepts it, not a real extraction outcome), exactly the same
synthetic-fixture blind spot [B2-ID-006](B2-ID-006.md) identified for
`resolve_calls`'s own container-origination defect: a test built from a
literal string can exercise logic a real extracted snapshot can never
actually trigger, and nothing in the existing suite would have caught
that gap before a real-repository checkpoint.

**What already works (confirmed, not assumed):** `resolve_calls` does
correctly extract and resolve calls made from WITHIN a trait method's
own body, including a default trait method with a real body
(`trait_item` containing a `function_item` with a body) —
[B2-ID-006](B2-ID-006.md)'s own regression suite includes exactly this
case (`rust_trait_default_method_...`) and it passes. **The gap is
isolated to the `Extends`/`Implements` RELATIONSHIP (which type
implements which trait), not to calls made inside an implementation's
own method bodies**, which are unaffected and already measured
correctly elsewhere in this same evaluation (confirmed: `calls_edges:
356` on this same corpus, a real, non-zero, non-trivial number).

Per explicit instruction, the real corpus was classified before any
fix design, to avoid a model that only works on the simple case:

| Shape | Count (Measured, `sharkdp/fd` @ `2381562`) | Example |
|---|---:|---|
| Total `impl` blocks | 41 | — |
| Inherent `impl Type { ... }` (no trait) | 18 | `impl DirEntry { pub fn normal(...) -> Self {...} ... }` |
| Trait `impl Trait for Type { ... }` | 23 | `impl Matcher for RegexSet { ... }` |
| Generic impls (`impl<...> ...`) | 4 | `impl<'a, W: Write> ReceiverBuffer<'a, W> { ... }` |
| Impls with lifetime parameters | 2 | `impl<'a> Display for SanitizedStr<'a>`, `impl<'a, W: Write> ReceiverBuffer<'a, W>` |
| Multiple impl blocks for the SAME type | Confirmed, e.g. `DirEntry`: 6 separate blocks (1 inherent + `PartialEq`/`Eq`/`PartialOrd`/`Ord`/`Colorable`) | `src/dir_entry.rs` lines 26/118/125/127/134/141 |
| Default trait methods (body in the trait itself, no override needed) | **0 in this corpus** — both real traits (`Matcher`, `SanitizeErr`) declare only signatures, no default bodies | Corpus limitation, not a resolver limitation — `resolve_calls`'s own B2-ID-006 regression suite confirms the mechanism works on a synthetic Rust trait-default-method case even though this specific corpus has none |
| Trait methods with no body (signature only) | Confirmed present (both real traits' sole methods) | `trait Matcher { fn matches_path(&self, path: &OsStr) -> bool; }` — already correctly extracted today as `SymbolKind::MethodSignature` (2 `MethodSignature` snapshots measured in this corpus) |
| Associated functions (no `self` receiver, factory-shaped) | Confirmed present and already correctly extracted as ordinary `Function` snapshots today (this part is NOT part of the gap) | `DirEntry::normal(e: ignore::DirEntry) -> Self`, `CommandSet::new<I, T, S>(input: I) -> Result<Self>` |
| Associated consts | **0 confirmed in this corpus** (one `const BRACE_LEN` found is a local function-body const, not a type-associated const) | Not yet evidenced either way by this corpus |

**Grammar fact directly relevant to fix design (Measured, confirmed by
a direct, throwaway tree-sitter probe against this workspace's own
`tree_sitter_rust` version, not assumed from documentation):**
`impl_item` exposes two NAMED fields, `trait` and `type`, directly via
`child_by_field_name` — `trait` is `None` for an inherent impl and a
`type_identifier` node for a trait impl; `type` is always present but
its OWN node kind varies: `type_identifier` for a plain type
(`DirEntry`), but `generic_type` for a parameterized type
(`ReceiverBuffer<'a, W>`, confirmed by direct probe). **This matters
for fix design:** the EXISTING (currently unreachable)
`collect_rust_impl_trait` function finds the trait name by searching
for A `type_identifier` CHILD positionally (`children.iter().find(|c|
c.kind() == "type_identifier")`), which happens to work for the
`trait` name in the simple case but would, if it were ever actually
invoked, **also fail to extract the generic `type` name correctly**
for any `impl<T> Trait for Generic<T>` shape, since it never reads the
named `type` field and the positional search for a bare
`type_identifier` would not match a `generic_type` node at all. This is
a SEPARATE, latent defect inside the already-dead code, worth fixing
together with reachability, not a reason to distrust the classification
above.

## Impact

- **Correctness/completeness (`Extends`/`Implements` coverage):**
  **Important.** Confirmed, on a real, non-trivial Rust repository, that
  this resolver's entire Rust-specific logic path is unreachable in
  practice — not a partial gap (e.g. "generic impls are missed") but a
  complete, 100% miss for every `impl` shape, on every Rust repository,
  structurally, independent of corpus choice. This is a stronger claim
  than any prior B2 finding about `Extends`/`Implements` (B2-ID-007
  found a real but PARTIAL defect in two OTHER languages' resolvers,
  both of which still produce SOME correct edges most of the time; this
  finding is a complete absence for one entire language).
- **Agent usefulness / trait-based impact analysis:** every one of this
  evaluation's own trait/impl-focused Q&A questions ("which traits does
  this type implement?", "which types implement this trait?") is
  **Not answerable** on Rust today, even though both the trait and the
  implementing type each individually exist as real, correctly-extracted
  symbols in the graph — the graph has the two endpoints but no edge
  connecting them. This is a materially worse outcome than a resolver
  that gets SOME answers wrong; it gets ALL of them silently absent.
- **Research validity:** no prior B2 evaluation ever exercised this
  code path against a real Rust-dominant repository (B2-EVAL-001/002's
  corpus mixed Python/C++; the C++ side of that corpus's own
  `resolve_extends_implements` test coverage is unaffected by this
  finding, which is Rust-specific). No prior published evaluation's own
  `Extends`/`Implements` numbers need an erratum, because no prior
  evaluation reported a Rust-specific `Extends`/`Implements` figure at
  all — this is a newly surfaced gap, not a retroactive correction.
- **Severity: Important, not Critical.** It does not crash, corrupt
  data, or produce a wrong/spurious edge (the resolver fails CLOSED:
  "no edge beats a false edge" holds here by accident of unreachability,
  not by design intent for this specific case) — it is a complete,
  silent, false-negative gap in exactly the domain priority this
  evaluation was asked to stress. Classified the same severity tier as
  B2-ID-006/007 (both Important), consistent with this project's own
  precedent that "a real, confirmed, non-trivial coverage/correctness
  gap, without a crash or data-corruption dimension" sits at Important,
  not Critical.

## Literature / state-of-the-art comparison (requested before any design decision)

- **rustc's own HIR** (`rustc_hir::hir::Impl`,
  https://doc.rust-lang.org/nightly/nightly-rustc/rustc_hir/hir/struct.Impl.html,
  official rustc compiler internals documentation) models an `impl`
  block as a first-class node with an explicit, OPTIONAL `of_trait`
  field (present for a trait impl, absent for an inherent impl), a
  `self_ty` field (the implementing type), and a separate `items` list
  (the impl's own associated items, each its own `ImplItem` node) —
  i.e., the compiler's own semantic model treats "this impl block,"
  "the trait it implements (if any)," and "the type it applies to" as
  three distinct, independently-identified things, not as a derived
  relationship computed after the fact from two OTHER symbols' own
  text. This directly supports Alternative A (`impl` as its own
  first-class node) as the model closest to the language's own
  semantic ground truth, though it does not by itself dictate HOW
  closely this pipeline's own `SymbolKind`/`EdgeKind` model should
  mirror rustc's internal representation (a lighter-weight model can
  still be evidence-aligned without importing rustc's full field set,
  e.g. `constness`/`safety`/`polarity`/`defaultness`, which have no
  clear present use case in this pipeline).
- **tree-sitter-rust's own grammar** (confirmed by this finding's own
  direct probe, not secondhand) exposes `impl_item.trait` and
  `impl_item.type` as NAMED fields, mirroring rustc HIR's own
  `of_trait`/`self_ty` split at the SYNTAX level already, before any
  semantic analysis — meaning extracting `impl` information at the
  tree-sitter layer does not require inventing a model from scratch;
  the grammar already carries the exact distinction rustc's own
  semantic model needs.
- **No peer-reviewed academic paper specific to this exact
  implementation pattern** (impl-block-as-a-symbol vs.
  impl-block-as-a-derived-fact, specifically for Rust) was found as
  genuinely on-point; this finding does not force a citation of
  convenience here. Three real, publicly-documented open-source tools
  were found that face the same design question in practice (not cited
  as authoritative precedent to copy, but as evidence this is a known,
  recurring design fork other real tools have had to make):
  - `ferrograph` (a real Rust code-graph tool) uses a two-phase
    approach: emit PLACEHOLDER `ImplementsTrait` edges directly from the
    tree-sitter pass, then resolve them in a later pass — structurally
    closer to this finding's Alternative B (fact/relation, not a new
    symbol node), with trait resolution explicitly deferred/future-work
    in its own published state.
  - `tldr-core` extracts trait definitions and impl blocks via
    tree-sitter directly, reading `impl_item`'s own `trait`/`type`
    fields (the same fields this finding's own probe confirmed exist) —
    confirms the field-based extraction approach is a real, working
    pattern elsewhere, not a theoretical possibility.
  - `codegraph-rust` (an unrelated, differently-named project despite
    the similar name) lists trait implementations and trait inheritance
    as first-class extracted relationships, without published detail on
    its own internal node/edge model — noted for completeness, not as
    an architecture reference, since no design detail was available
    to compare against.
- **rust-analyzer's own internal `hir` crate semantic model** was
  sought specifically (per the instruction to consult it as a semantic
  reference) but no public documentation of its own `Impl`/trait-impl
  representation was found via this finding's own search — flagged
  honestly as NOT established evidence rather than assumed or
  guessed at. This is a real gap in this finding's own literature
  review, not a silent omission: if a future design pass has access to
  rust-analyzer's own source (`ra_hir`/`hir-def` crates) directly, that
  remains the more authoritative reference than this finding was able
  to establish from search alone.

## Alternative design directions (per explicit instruction: presented for a future decision, NOT decided or implemented here)

### A. `impl` block as its own first-class `SymbolSnapshot`/`SymbolKind` (e.g. `ImplBlock`)

**Shape:** a new `SymbolKind::ImplBlock` (or similarly named) variant,
extracted directly from `impl_item` nodes in `extract/rust.rs`, carrying
edges: `ImplBlock --Contains--> Method/Function` (its own associated
items), `ImplBlock --Implements--> Trait` (only for a trait impl, via
the confirmed `trait` named field), `ImplBlock --???--> Type` (the
implementing type — needs its own edge kind or reuse of an existing
one; see "Open question" below).

- **Pro:** closest alignment to rustc HIR's own semantic model
  (confirmed above); gives the impl block itself a navigable identity
  (useful for "where is this exact impl, as opposed to the trait or the
  type abstractly" — directly relevant to this evaluation's own Q3,
  which asked "which methods belong to THIS impl" as a question about
  the impl block specifically, not the type in general); naturally
  handles MULTIPLE impl blocks for the same type (confirmed real in
  this corpus: `DirEntry`'s 6 separate blocks) as 6 separate, individually
  addressable nodes, rather than needing to merge or distinguish them
  under one shared `Type` symbol.
- **Con:** requires a new `SymbolKind` variant (a cross-cutting change
  touching `codegraph-domain`, `kind_mapping.rs`, every exhaustive match
  over `SymbolKind` elsewhere in the codebase); needs its own identity/
  lineage story (what makes two `ImplBlock`s across commits "the same"
  impl block, especially for an anonymous-feeling construct with no
  name of its own beyond "impl X for Y at this span"); needs a `Contains`
  semantics decision (does `ImplBlock` CONTAIN its methods the same way
  `Class` contains members today, or does the method's "real" container
  stay the TYPE it's logically part of, with `ImplBlock` as a separate,
  parallel grouping?); the query model gets one more hop for the common
  case ("which trait does X implement" becomes `Type -> ImplBlock ->
  Trait` instead of a direct `Type -> Trait` edge, unless a redundant
  direct edge is ALSO added, which then raises its own
  consistency-with-the-indirect-path question); persistence/future
  schema implications not yet evaluated.

### B. `impl` as a structural fact, not a symbol (e.g. `ImplFact`)

**Shape:** analogous to this pipeline's own existing `ImportFact` model
(a non-symbol structural fact table, already precedented in this
codebase per [B2-ID-005](B2-ID-005.md)'s own Imports redesign) — extract
an `ImplFact { implementing_type: SymbolSnapshotId, trait_name: Option<SymbolSnapshotId>, methods: Vec<SymbolSnapshotId>, span }` per real `impl` block, without
creating a new `SymbolSnapshot`/`SymbolKind` at all, and generate
`Type --Implements--> Trait` edges directly from these facts (closer to
`ferrograph`'s own published two-phase approach, found in the
literature comparison above).

- **Pro:** reuses this project's own already-precedented
  "fact table, not a symbol" pattern instead of introducing a second one
  alongside it; simpler identity story (an `ImplFact` does not need
  cross-commit lineage the way a user-meaningful named symbol does,
  the same way `ImportFact` today does not); directly produces the
  relationship this evaluation's own Q1/Q2/Q5 actually asked for
  (`Type -> Trait`) without an extra hop.
- **Con:** loses the impl block as an independently NAVIGABLE entity —
  "which methods belong to THIS SPECIFIC impl, as opposed to another
  impl of the same trait for the same type" (not observed as a real
  shape in this corpus, but not provably impossible in Rust generally)
  would have no natural node to attach to; representing MULTIPLE
  inherent impls for the same type (not observed here, but syntactically
  legal in Rust) as "two facts for the same type, with no shared
  node between them" may be harder to query cleanly than Alternative
  A's naturally-separate nodes.

### C. File/module-level resolver, no dedicated snapshot or fact type

**Shape:** extract `impl_item` occurrences directly during the file's
own parse pass (not as a `RawSymbolCandidate`, not as a new structural
fact type either) and resolve `Implements` edges in a dedicated
file-scoped pass that runs alongside (not instead of) the existing
candidate-extraction pipeline, writing directly to the final edge set
without any new intermediate representation.

- **Pro:** minimal change to the existing `SymbolKind`/fact-type
  surface — no new persisted concept at all; avoids inventing either a
  "fake symbol" (Alternative A's own risk if `ImplBlock` ends up
  modeling something that isn't really a first-class named entity in
  the way `Class`/`Function` are) or a second fact-table pattern
  alongside `ImportFact` (Alternative B's own risk of pattern
  proliferation).
- **Con:** introduces a THIRD architectural category (symbol vs. fact
  vs. "file-level resolved relation, persisted nowhere as an
  intermediate value") that still needs its own well-defined integration
  point in the incremental-indexing pipeline (today's
  `CodeGraphIndexer::observe_commit` has a clear "recompute typed edges
  against the full snapshot pool" step per [B2-ID-006](B2-ID-006.md)'s
  own independent-review-confirmed design; a resolver that reads raw
  file text directly, bypassing the snapshot pool entirely, would need
  its own explicit place in that same incremental contract, not
  assumed to simply work by analogy).

### D. Other evidence-driven model

Not proposed here, per instruction, beyond noting that Alternative A
and Alternative B are not mutually exclusive in principle (e.g. an
`ImplFact` per B2-ID-005's own precedent COULD coexist with a thin,
separate `ImplBlock` identity for cross-commit lineage purposes only,
if a future evaluation's own real-repository evidence shows that
distinguishing "this exact impl survived from commit A to commit B" is
a question worth answering) — flagged as a possible hybrid worth
real-evidence-driven reconsideration later, not decided or recommended
here.

## Open questions for the eventual fix decision (not resolved by this finding)

1. **Does `Type --Implements--> Trait` need the impl block itself as an
   intermediate hop, or should it be a direct edge regardless of which
   of A/B/C is chosen?** This evaluation's own Q1/Q2/Q5 all asked for
   the DIRECT relationship ("which trait does X implement," not "which
   impl block connects X to a trait") — any chosen design should be
   checked against this real query shape specifically, not assumed.
2. **How should multiple impl blocks for the same type
   (confirmed real: `DirEntry`'s 6 blocks) interact with `Contains`?**
   Does each method still belong to the TYPE for `Contains` purposes
   (current `Class`-like semantics), or to its own specific impl block,
   or both (a method genuinely belongs to its impl block syntactically,
   AND is reachable "from" its type semantically)?
3. **Generic impls' own type-identity:** `impl<'a, W: Write>
   ReceiverBuffer<'a, W>` — does the `Implements`/`Contains` target
   resolve to the base type `ReceiverBuffer` (ignoring the generic
   parameters, the same way this pipeline's OTHER languages' generic
   handling already does, if any precedent exists) or does genericity
   need its own explicit handling? Not evidenced either way by this
   finding; flagged for the eventual design pass.
4. **Should the already-latent, currently-unreachable
   `collect_rust_impl_trait` bug (using a positional `type_identifier`
   search instead of the confirmed-available named `trait`/`type`
   fields, which would silently mis-extract any generic trait-impl's
   own type name) be fixed as part of reachability, or is the function
   being replaced entirely by whichever of A/B/C is chosen, making the
   positional-search bug moot?** Not decided here.
