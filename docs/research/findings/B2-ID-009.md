# B2-ID-009: C# `method_declaration` name extraction misnames any method whose return type is a simple non-generic named type

**Severity:** Critical.

**Discovered by:** B2-EVAL-008 (C#/C++ domain multi-codebase validation),
during Section C2's overload ground-truth measurement against
`App-vNext/Polly`'s `Policy.HandleSyntax.cs`. B2-EVAL-008 is PAUSED as of
this finding; see its own evaluation document for the measurements
already collected before the pause and which of them this bug may have
contaminated.

## Discovery context

B2-EVAL-008's harness queried the real `CodeGraph` for every snapshot
named exactly `"Handle"`, expecting 4 (the real overload count
confirmed by direct source reading: `Handle<TException>()` and
`Handle<TException>(Func<TException,bool>)`, each once on
`Policy`/`PolicyBuilder` and once on `Policy<TResult>`/`PolicyBuilder<TResult>`).
Only 2 were found. A dedicated extraction-only probe (bypassing the
full indexer) against the real file showed 14 total candidates
extracted with zero rejections — so the missing 2 `Handle` snapshots
were not dropped by `SignatureTooLong` or any other rejection path.
Printing every candidate's name and span revealed the real cause: the
two methods expected to be named `"Handle"` inside the file's first
`partial class Policy { ... }` block were extracted with name
`"PolicyBuilder"` instead — their own return type.

## Real-repository reproduction

File: `src/Polly/Policy.HandleSyntax.cs` (App-vNext/Polly, commit
`1f232caf9672e515751ba2df76d82bfbbb62e016`).

```csharp
public partial class Policy
{
    public static PolicyBuilder Handle<TException>()
        where TException : Exception
        => new(exception => exception is TException ? exception : null);

    public static PolicyBuilder Handle<TException>(Func<TException, bool> exceptionPredicate)
        where TException : Exception
        => new(...);
    ...
}
```

Direct extraction probe (`extract_symbols_reporting_rejections` called
directly against this file's real bytes, not assumed) printed, among
14 total candidates, 0 rejections and:

```
PolicyBuilder [method_declaration] span=(332,501) sig_len=169
PolicyBuilder [method_declaration] span=(949,1204) sig_len=255
...
Handle [method_declaration] span=(4417,4595) sig_len=178
Handle [method_declaration] span=(5022,5286) sig_len=264
```

The first two spans are the two `Handle<TException>` overloads inside
`partial class Policy` (non-generic `PolicyBuilder` return type) —
extracted with name `"PolicyBuilder"`. The second two spans are the
two `Handle<TException>` overloads inside `partial class Policy<TResult>`
(return type `PolicyBuilder<TResult>`, a `generic_name`-shaped node,
not a bare `identifier`) — extracted correctly as `"Handle"`.

## Minimal reproduction

```csharp
class Policy {
    public static PolicyBuilder Handle<TException>(int x) => null;
}
```

Direct AST inspection (this workspace's real compiled
`tree-sitter-c-sharp` grammar, not assumed from documentation) of the
resulting `method_declaration` node's **direct children**:

```
method_declaration: "public static PolicyBuilder Handle<TExce..."
  modifier: "public"
  modifier: "static"
  identifier: "PolicyBuilder"      <- return type, ALSO a bare identifier
  identifier: "Handle"             <- the real method name
  type_parameter_list: "<TException>"
  parameter_list: "(int x)"
  arrow_expression_clause: "=> null"
```

`method_declaration` has **two direct children of kind `identifier`**
whenever its return type is a simple (non-generic, non-`predefined_type`)
named type: the return type, then the method name, in that order.

## Root cause

`crates/codegraph-index/src/extract/csharp.rs`'s `named_by_child_kind`
(shared by `interface_declaration`/`class_declaration`/`method_declaration`
extraction) finds the construct's name via:

```rust
let name_node = node.children(&mut cursor).find(|c| c.kind() == name_kind && !c.is_missing())?;
```

— i.e. "the FIRST direct child whose kind is `identifier`." For
`class_declaration`/`interface_declaration` this is safe (the type
name is the only direct `identifier` child). For `method_declaration`
it is unsafe: the return-type position and the name position are BOTH
bare `identifier` nodes whenever the return type is non-void,
non-generic, and not a `predefined_type` keyword (`int`, `string`,
`void`, `bool`, ...) — which covers exactly the common "returns one of
my own classes/interfaces" shape (builder/factory APIs, fluent
interfaces, anything returning a project-defined type by non-generic
name). `.find()` returns the first match: the return type, not the
method name.

**This is not a missing feature — the grammar already disambiguates
it correctly.** Direct `child_by_field_name` inspection of the real
compiled grammar confirms `method_declaration` exposes two distinct
NAMED fields:

```
method_declaration field("name")    = identifier -> "Handle"
method_declaration field("returns") = identifier -> "PolicyBuilder"
```

confirmed identically inside both a `class_declaration` and an
`interface_declaration` body (e.g. `interface IFoo { PolicyBuilder N(); }`
→ `field("name") = "N"`, `field("returns") = "PolicyBuilder"`). The
extractor simply does not use this field and instead falls back to a
positional/kind-based scan that the grammar's own two same-kind
siblings defeat. This is the same class of defect
[B2-ID-008](B2-ID-008.md)'s own closing lesson already named — "prefer
named-field access over positional child search" — recurring here in
a different extractor that predates that lesson.

## Impact / identity analysis

- **Symbol name corruption, not identity loss:** `SymbolSnapshotId::derive`
  hashes `(file, kind, name, signature_text, span)`. Since
  `signature_text` and `span` are each captured correctly and are
  unique per overload, the two misnamed snapshots get distinct,
  stable, non-colliding `SymbolSnapshotId`s — there is no
  duplicate-ID collision and no snapshot silently disappears. The
  corruption is confined to the `name` field itself.
- **Downstream contamination is real but narrow and explainable,
  confirmed by direct measurement, not assumed:**
  - **Symbol coverage counts** (`SymbolKind::Method` totals) are
    unaffected — the candidate is still promoted as exactly one
    `Method` snapshot; only its name string is wrong.
  - **`Calls` edges:** `resolve_calls` matches callee text against
    snapshot names by string equality. A misnamed snapshot named
    `"PolicyBuilder"` will falsely appear as a valid `Calls` target
    for any call site whose callee text is literally `PolicyBuilder`
    (e.g. a constructor-style invocation written as a plain call, or
    any other method coincidentally also named `PolicyBuilder`) and
    will never be found by any call site that correctly calls
    `Handle(...)`. Net effect: false negatives for real calls to
    these two methods, and a narrow false-positive surface against
    any unrelated same-named caller. Not exhaustively re-measured
    corpus-wide in this finding (out of scope for a pause-and-report);
    flagged for the fix's own regression-impact pass.
  - **`Contains` edges:** unaffected in kind/count (the method is
    still contained by `Policy`), only the printed/queried name of
    the "contained" endpoint is wrong.
  - **`Extends`/`Implements`:** not applicable to methods directly;
    no evidence this contaminates class/interface-level edges.
  - **Lineage:** `signature_text` (used for lineage similarity scoring)
    is correct and uncorrupted, so lineage continuity across commits
    is not expected to be affected by the NAME corruption itself,
    though this was not separately re-verified here.
- **Not corpus-specific:** the triggering shape (`ReturnType MethodName(...)`
  with a simple non-generic named `ReturnType`) is a common, ordinary
  C# idiom, not a Polly peculiarity — any C#-domain measurement in
  this pipeline is at risk wherever it does.

## Cross-language audit (requested before any fix)

Performed via direct, minimal, real-grammar probes (not assumed) for
every extractor sharing the same "first direct child of kind X"
pattern (`csharp.rs`, `rust.rs`, `python.rs`, `javascript.rs`; `cpp.rs`
already uses a structurally different, narrower search — see below):

| Language | Name-search kind | Return-type node kind (simple named type) | Same kind as name-search? | Collision possible? |
|---|---|---|---|---|
| C# (`method_declaration`) | `identifier` | `identifier` (non-generic) / `generic_name` (generic) | **Yes, when non-generic** | **Yes — this finding** |
| Rust (`function_item`) | `identifier` | `type_identifier` | No | No |
| Python (`function_definition`) | `identifier` | wrapped in a dedicated `type` node (never a bare direct-child `identifier` of `function_definition`) | No | No |
| TypeScript (`method_definition`) | `property_identifier` | wrapped in a dedicated `type_annotation` node | No | No |
| JavaScript (`method_definition`) | `property_identifier` | N/A — no type annotations exist in this grammar | No | No |
| C++ (`function_definition`) | search is scoped INSIDE `function_declarator` only (`identifier`/`field_identifier`), never among the function's own direct children | `type`/`returns` field sits as a direct child of `function_definition` itself, one level further OUT than where the name search looks | No (structurally, by construction — the search never even looks at the sibling level the return type occupies) | No |

**Conclusion: this is a C#-specific grammar property, not a shared
cross-language anti-pattern.** Every other current extractor is
structurally immune, each for a different, confirmed-by-probe reason
— not by coincidence requiring a fix of its own. No companion finding
is opened for Rust/Python/JS/TS/C++ extraction on this specific defect.

`class_declaration`/`interface_declaration`/`constructor_declaration`
in C# were also probed directly and confirmed NOT affected:
`class_declaration`/`interface_declaration` have exactly one direct
`identifier` child (the type name; a base/heritage list's names live
inside a separate `base_list` child, not as bare siblings);
`constructor_declaration` correctly exposes `field("name")` matching
its one unambiguous `identifier` child (a constructor has no return
type at all). `field_declaration` was also checked: its own name does
NOT live as a direct `identifier` child of `field_declaration` itself
(it is one level deeper, on `variable_declarator`) — `field_declaration`
is not currently walked by `extract/csharp.rs` at all (a separate,
already-flagged extraction-coverage gap, not this bug).

## Scope within C#'s own grammar (per the requested audit)

Checked and NOT separately probed as part of this finding's own
minimal-repro set, but relevant to the fix's own test list per the
user's explicit instruction:

- **Generic methods with a generic return type** (`PolicyBuilder<TResult> Handle<TException>()`):
  confirmed SAFE in the real corpus evidence above — the return type
  is `generic_name`, not `identifier`, so no collision; this is
  exactly why 2 of the 4 real overloads extracted correctly already.
- **`async Task<T> Foo()`**: not yet probed directly; `Task<T>` is
  itself a generic return type (`generic_name`-shaped), predicted safe
  by the same mechanism as the point above, but not confirmed by a
  dedicated probe in this finding.
- **Nullable return types (`MyType? Foo()`)**, **array return types
  (`MyType[] Foo()`)**, **tuple return types (`(int, int) Foo()`)**:
  not probed; each wraps the base type in a different node kind
  (`nullable_type`/`array_type`/`tuple_type` are plausible grammar
  node names by analogy with other C# constructs already seen, but
  this is NOT confirmed against the real grammar and must not be
  assumed before the fix's own test-writing step).
- **Explicit interface implementation names**
  (`PolicyBuilder IFoo.Handle()`), **operator declarations**,
  **conversion operators**: not probed; plausible additional
  collision or omission risks given this grammar's apparent habit of
  exposing multiple same-kind direct children, but not confirmed.
- **A method whose return type's name string equals another REAL
  symbol's name** (e.g. a method returning `PolicyBuilder` in a file
  that also defines a type named `PolicyBuilder`): not probed as a
  distinct case; this is the same underlying defect, just with an
  extra downstream consequence (the misnamed snapshot would then
  share a name with a real, unrelated, correctly-named symbol,
  widening the `Calls`/ambiguity surface described above). Call out
  explicitly for the fix's own test list, not resolved here.

## Recommended fix direction (not implemented — reported per protocol)

Confirmed via direct grammar probe: `method_declaration` exposes a
named `name` field (and a named `returns` field) reliably, inside both
`class_declaration` and `interface_declaration` bodies. The fix should
read the name via `node.child_by_field_name("name")`, not via a
positional/kind-based scan — mirroring the exact lesson B2-ID-008
already recorded for `impls.rs`. This also removes any dependency on
return-type shape entirely (generic or not), rather than special-casing
around it.

This finding does **not** implement that fix. Per the user's explicit
ruling, B2-EVAL-008 stays PAUSED, and C# semantic metrics collected by
B2-EVAL-008's harness before this finding was opened must be treated
as potentially contaminated wherever a method's own identity (its
name) matters — flagged per-section in B2-EVAL-008.md itself, not
silently reused as valid.

## Fix status: FIXED (commit `c09c34d`), independently reviewed

Per explicit user authorization, the fix described above was
implemented exactly as recommended
(`named_by_name_field`/`child_by_field_name("name")` for
`method_declaration`; `class_declaration`/`interface_declaration` left
on the positional path, confirmed safe), covered by 14 regression
tests, mutation-tested (`cargo mutants` scoped to this file: 15
mutants, 11 caught, 4 unviable, 0 missed, 0 timeout), and measured
before/after on the real `App-vNext/Polly` corpus: 1535 of 4543
`method_declaration` nodes (33.8%) were misnamed before the fix, 937
of them collapsed under the single bogus name `"Task"` (every
`async Task Foo()` method — the dominant real-world trigger shape,
far more common than the originally-discovered `PolicyBuilder Handle()`
case). `calls_edges` +224, `extends_implements_edges` +11 after the
fix; `snapshots_promoted`/total `Method` count unchanged (0 delta),
confirming the fix corrects names only. Full detail in
[B2-EVAL-008.md](../evaluations/B2-EVAL-008.md)'s own "B2-ID-009 fix:
before/after" section.

An independent review (a fresh reviewer, uninvolved in writing the
fix) verified the fix's correctness, the `class_declaration`/
`interface_declaration` scope-safety claim, out-of-scope compliance,
and re-ran the mutation testing and full test suite independently —
all claims matched exactly. **Verdict: APPROVE**, no Critical or
Important issues. The reviewer additionally probed, beyond this
finding's own 14 required cases: `ref`-returning methods, explicit
interface implementations, and partial method declarations — all
confirmed correctly handled by the same fix, no collision. The
reviewer also confirmed `operator_declaration`,
`conversion_operator_declaration`, `record_declaration`, and local
functions (nested inside a method body) are simply NOT walked by
`extract/csharp.rs`'s `walk()` at all — a pre-existing extraction-
coverage gap, unrelated to and unaffected by this fix (not a
misnaming; these constructs are never extracted as candidates at all,
identically before and after). Left as a separate, not-yet-tracked
backlog item, consistent with the fix's own explicit scope discipline
(do not expand into constructor/property/local-function/delegate/
operator extraction without the same demonstrated root cause).

**Residual limitation, confirmed NOT a regression:** a method name
reduced to a true zero-width (but not tree-sitter-`MISSING`-flagged)
identifier node (e.g. a malformed `void <T>() => null;`) yields an
empty-string name rather than `None`. This blind spot is byte-
identical in the old and new code (same `!c.is_missing()` guard) and
is not exploitable downstream: `ValidatedName::parse`
(`crates/codegraph-index/src/snapshot/name.rs`) rejects empty names at
promotion time, so no bogus symbol is ever promoted, before or after
this fix.
