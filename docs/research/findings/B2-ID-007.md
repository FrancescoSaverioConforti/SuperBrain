# B2-ID-007: nested semantic ownership / source-span overreach is a defect family, not a `resolve_calls`-only bug — systematic resolver-ownership audit

**Discovered by:** verification work for [B2-ID-006](B2-ID-006.md)'s own
fix, specifically while confirming the fix did not need to also touch
`resolve_extends_implements`. Per explicit instruction, this finding was
opened and the fix work paused the moment a second resolver was found
affected, rather than folding it silently into B2-ID-006's own scope.

## Discovery context

While validating B2-ID-006's two-mechanism fix (`SymbolKind::can_originate_calls`
plus a nested-scope span boundary in `resolve_calls`), a check of whether
`resolve_extends_implements` shared the identical implementation
pattern (re-parse a snapshot's full `signature_text`, recurse
unconditionally into every child node) found that it does, and a
synthetic, real-parse reproduction confirmed a second, independently
real instance of the same defect family — a nested Python class's own
base clause attributed to BOTH itself (correct) and its outer,
unrelated container class (spurious). This prompted the systematic,
resolver-by-resolver ownership audit below, covering every resolver
that re-parses a snapshot's own `signature_text`.

### Summary

- **Affected, confirmed:** `resolve_calls` (B2-ID-006, already being
  fixed), `resolve_extends_implements` (this finding, not yet fixed),
  `resolve_tests_for` (this finding, not yet fixed, narrower trigger).
- **Not affected, confirmed by direct reproduction:** `resolve_instantiates`,
  `resolve_contains`.
- **Not applicable:** lineage.

## Root cause

A shared STRUCTURAL pattern — re-parsing a snapshot's full
`signature_text` and recursing into every descendant AST node with no
boundary at a nested symbol's own declaration — produces a shared
FAILURE MODE (an ancestor snapshot's own re-parse rediscovers a
relationship that actually belongs to a more specific, nested
descendant), but the correct OWNERSHIP RULE differs per relation and
must not be unified into one blanket fix:

> A semantic relation must be attributed to the AST/symbol scope that
> syntactically and semantically owns the construct expressing that
> relation, not merely to every ancestor snapshot whose source span
> contains it.

Concretely, per relation:

- **`Calls`** — owned by the **nearest executable enclosing scope**
  (B2-ID-006's own invariant; a call site is "inside" whichever
  function/method body textually contains it, and that function/method
  — not any further-out ancestor — is the real caller).
- **`Extends`/`Implements`** — owned by the **specific type declaration
  whose own header/base-clause syntax names the base**. This is NOT the
  same rule as `Calls`: inheritance has no "executable scope" concept
  at all — a base clause is a property of ONE declaration's own header,
  full stop. The fix here is "stop walking into a NESTED type
  declaration's own base clause once the current declaration's own
  header has already been read," not "find the nearest executable
  scope" (there is no executable scope in an inheritance clause to
  find).
- **`TestsFor`** — owned by the **specific test function/method whose
  own body contains the real call to the implied target** — closer in
  shape to `Calls`'s own rule (nearest enclosing scope that directly,
  textually contains the relevant call), but gated by an additional,
  separate naming-convention check this resolver already has.
- **`Instantiates`** — already correctly owned by the specific `Field`
  whose RHS is the instantiation, because the resolver's own kind
  filter never lets anything else compete for "from" in the first
  place; no fix needed.
- **`Contains`** — already correctly owned by the innermost structural
  container, by explicit design (minimizing span length among valid
  candidates); no fix needed.

## Impact

- **Correctness (`Extends`/`Implements` edge quality):** Important.
  Confirmed on two independent languages (Python, C#) that a nested
  type declaration's own base clause can be spuriously attributed to
  an unrelated outer container — this is a 1:1 structural claim
  (`resolve_extends_implements`'s own doc comment: "inheritance is a
  1:1 structural claim about THIS declaration's one actual base"), so
  a spurious edge here is a more direct violation of that resolver's
  own stated invariant than `Calls`'s corresponding issue (which is at
  least honestly ambiguous/heuristic in the ambiguous case; `Extends`
  edges are always `StaticAnalysis`, asserted as certain).
- **Correctness (`TestsFor` edge quality):** Important, narrower
  real-world surface than the other two — requires an outer
  container's own name to itself match the `test_X`/`TestX` convention
  AND something nested inside it to call the exact implied target name.
  Plausible in real code (nested test-helper classes inside a test
  suite class are a real pytest/unittest shape), not purely
  theoretical, but rarer than the unconditional `Calls`/`Extends`
  triggers.
- **Research validity:** this finding's existence — that a careful,
  systematic audit was performed BEFORE generalizing B2-ID-006's own
  fix to every resolver — is itself evidence supporting the Research-
  grade Findings Policy's own discipline: a plausible-sounding
  "the same fix surely applies everywhere" assumption would have been
  wrong twice over in this exact case (`resolve_instantiates` and
  `resolve_contains` need NO fix at all, and `resolve_extends_implements`/
  `resolve_tests_for` need a DIFFERENT ownership rule than `Calls`'s
  own, not the identical span-boundary mechanism copy-pasted).
- **Severity: Important**, not Critical — no crash, no corruption of
  already-closed B2 production data beyond what B2-ID-006 already
  disclosed for `Calls`; this finding adds two more affected
  relations to the same disclosure, not a new category of harm.

## Solution adopted

**Implemented**, as two separate, relation-specific fixes — neither
reuses the other's mechanism, confirming this finding's own "Decision
needed" question below in favor of separate fixes:

### `resolve_extends_implements` — implemented

A new, parse-tree-LOCAL, node-kind-based boundary
(`for_each_node_not_inside_a_nested_boundary`,
`codegraph-index::edges::extends_implements`): visits the outermost
declaration a `collect_*` function is walking (always visited,
regardless of its own node kind — the fragment's root is a language
wrapper node, e.g. Python's `module`, never a declaration itself), then
recurses into its body, but stops immediately upon encountering a
SECOND node of the same boundary kind (`class_definition`/
`class_declaration`/`class_specifier`/`struct_specifier`/`impl_item`/
`interface_declaration`, depending on language/collector) — visiting
neither that nested declaration nor anything beneath it. That nested
declaration's own base/heritage clause is picked up correctly and
independently when `resolve_extends_implements`'s own outer loop
reaches ITS specific snapshot on a later iteration. Applied to all six
per-language collectors (Python, Rust, C#, C++, JavaScript, TypeScript/Tsx).

**Design note (an intermediate, incorrect version was caught and
corrected before landing):** a first implementation attempt threaded
the "have we entered a boundary" state by re-deriving it fresh from
each recursion step's own immediate parent (`child.kind()` checked
against `boundary_kinds` at each call). This was empirically found
wrong — Python's own `class_definition -> block -> class_definition`
shape (an intermediate `block` wrapper node sits between an outer
class and a nested one, and is not itself a boundary kind) let the
nested class through unprotected, because the locally-recomputed check
reset at that non-boundary wrapper step. Caught by the very first
regression-test run (9 of 10 new tests failed, plus the PRE-EXISTING
basic single-class test also failed — a strong signal the first
attempt was wrong, not merely incomplete), diagnosed, and corrected to
thread the "already entered one boundary" flag explicitly through the
recursion instead of re-deriving it. Recorded here because it is
exactly the kind of implementation subtlety a reviewer should scrutinize
closely, and because catching it via test failure — rather than ship
and hope — is the validation discipline this policy is for.

### `resolve_tests_for` — implemented

A cross-snapshot span-boundary check
(`call_site_belongs_to_a_more_nested_snapshot`,
`codegraph-index::edges::tests_for`), closer in shape to B2-ID-006's
own `resolve_calls` mechanism, but NOT a verbatim reuse: it does not
filter by `SymbolKind::can_originate_calls()`, because `TestsFor`'s own
naming-convention gate (`test_naming_convention_target`) is what
already does the real eligibility filtering here — a `Class` nested
inside another `Class` is excluded from ever claiming the relation not
because it is caller-ineligible in a `Calls` sense, but because
`resolve_tests_for`'s own outer loop only ever considers a snapshot
whose OWN NAME fits the convention. The fix: for each call site found
while re-parsing a candidate snapshot's own body that matches the
implied target name, check whether some OTHER, more deeply nested
snapshot in the same file ALSO contains that exact call site — if so,
this snapshot's own claim is rejected (it genuinely belongs to the
nested one, which will correctly claim it independently on its own
iteration IF its own name also matches the convention; if not, no edge
exists at all — conservative, per this module's own "no edge beats a
false edge" discipline).

### `resolve_instantiates`, `resolve_contains` — no fix, confirmed not affected

Unchanged. Each now carries its own documented immunity rationale
directly in its module doc comment (see B2-ID-006's own "Status
update" for the exact cross-reference).

### Decision resolved

The "separate fixes per resolver, not a single shared mechanism" design
direction this finding originally recommended was followed exactly:
`resolve_extends_implements`'s fix is parse-tree-local and
node-kind-based (reflecting that inheritance has no executable-scope
concept); `resolve_tests_for`'s fix is cross-snapshot and span-based
(reflecting that it IS, in effect, asking a `Calls`-shaped question —
"which snapshot's body really contains this call" — just gated by an
additional naming-convention check `Calls` itself does not have). The
two fixes share a PRINCIPLE (ownership attributed to the construct that
actually owns it, never to every ancestor whose span/subtree merely
contains it), not an implementation.

## Alternatives considered

### A. Assume B2-ID-006's exact fix generalizes to every resolver (rejected)

This finding's own audit disproves the assumption directly:
`resolve_instantiates` and `resolve_contains` need no fix at all (a
blanket re-application would be wasted, risky churn on resolvers that
are already correct), and `resolve_extends_implements`'s correct
ownership rule is NOT "nearest executable scope" (inheritance clauses
have no executable-scope concept), so copying B2-ID-006's mechanism
verbatim would either not compile against a meaningful predicate or
would silently encode a wrong semantic rule under a right-looking
name.

### B. Treat this as part of B2-ID-006 itself (rejected, per explicit instruction)

Keeping this as its own ID, linked to B2-ID-006 as the same defect
FAMILY but a distinct finding, preserves the fact that these are
different resolvers, different relations, different impact, and
(critically) a NOT-yet-demonstrated-identical fix — exactly the
reasoning the instruction gave for opening a separate ID rather than
merging.

### C. Fix everything found so far immediately, in the same pass (rejected, per explicit instruction)

Rejected because the ownership rule for `Extends`/`Implements` and
`TestsFor` has not yet been through its own design/approval step —
implementing now would repeat the exact mistake Alternative A
describes, just one level removed (assuming without designing).

## Literature / authoritative evidence

The general principle this finding (and B2-ID-006) rests on — that a
name/relationship's correct "owner" is determined by lexical/semantic
scope structure, not by arbitrary AST ancestor containment — has real
literature support:

- Néron, P., Tolmach, A., Visser, E., & Wachsmuth, G. (2015). *A Theory
  of Name Resolution*. In ESOP 2015 (European Symposium on
  Programming), LNCS 9032. Introduces scope graphs: a language-
  independent model where declarations and references are resolved via
  explicit lexical-nesting edges between scopes, not by arbitrary
  source-span containment — directly supports the general principle
  that "which scope owns this construct" must be determined by an
  explicit nesting/ownership relation, not assumed from raw span
  containment alone. Cited as literature SUPPORT for the general
  principle; this project's own specific resolvers, span-boundary
  checks, and per-relation ownership rules are this project's own
  engineering choices, not a direct implementation of scope graphs
  (no scope-graph data structure is introduced here).
- The ACER framework (Sun, Y. et al., 2023, arXiv:2308.15669, *ACER: An
  AST-based Call Graph Generator Framework*) separately confirms that
  AST-based (rather than IR-based) call-graph/relationship extraction
  is an established, legitimate approach in the literature — relevant
  context for why this project's AST-re-parse-based resolvers are a
  reasonable design choice in the first place, even though they need
  this specific ownership-boundary fix.

Neither source is cited as prescribing this project's own specific
fix mechanism (a `SymbolKind` capability predicate, a cross-snapshot
span check, or a parse-tree-local node-kind boundary) — those remain
this project's own engineering choices, validated by this project's
own real-repository evidence and tests, per the Evidence-before-claims
Experimental Policy's own discipline on this point.

## Residual limitations

- `resolve_extends_implements`'s Rust/C++/JS/TS collectors are
  Inferred-affected (identical code pattern, confirmed by direct source
  reading) but not yet empirically reproduced per-language — only
  Python and C# were actually run against real nested-declaration
  source in this audit.
- `resolve_tests_for`'s affected case requires a specific real-world
  shape (an outer container itself named per the test-naming
  convention, containing a nested symbol that calls the exact implied
  target name) — not yet assessed for how common this shape actually
  is in real repositories; B2-EVAL-003's own backend corpus did not
  happen to contain a case shaped this way (its own `TestsFor` = 0
  finding has an unrelated root cause — the test names there are
  descriptive, not `test_<exact-target-name>`-shaped at all).
- No fix is implemented for either affected resolver in this finding —
  by explicit instruction, this is the audit only; B2-ID-006 itself
  also remains open (not closed) pending this audit's own completion
  and the user's next decision on how to sequence the two resolvers'
  fixes relative to B2-ID-006's own closure.
- `resolve_instantiates`/`resolve_contains`'s "not affected" conclusion
  is specific to Python in this audit (the only language checked for
  either) — not yet re-verified for every other language each resolver
  covers, though both conclusions rest on a STRUCTURAL argument (a
  kind-filter that excludes containers outright; an explicit innermost-
  candidate selection) that is language-independent by construction,
  not on a per-language empirical coincidence the way the AFFECTED
  classifications are.
