# B2-ID-002: typed-edge resolvers conflate syntactic call-site occurrences with semantic graph relations, producing literal duplicate edges

## Discovery context

Real-repository smoke test checkpoint (B2, post-Task-9), immediately
following the fix for [B2-ID-001](B2-ID-001.md), while re-running the
same pipeline against the same target:

- **Repository:** `pytorch/examples` — https://github.com/pytorch/examples
- **License:** BSD 3-Clause
- **Commit:** `20955149ad6ea97a4f403e5a56c95a39e568ccbe`

After B2-ID-001's fix removed the `DuplicateSnapshotId` failure, the
very same `observe_commit`/`build_graph` call failed again with a
DIFFERENT error: `GraphError::DuplicateEdge`.

## Observable evidence

**Observed:** a duplicate-triple diagnostic over the full real edge set
(13,876 `Calls`/`Extends` edges produced by `resolve_calls`,
`resolve_imports`, `resolve_extends_implements`, `resolve_tests_for`
combined, before this fix) found **827 distinct `(from, to, kind)`
triples that appeared more than once**, with multiplicities up to 5.
Representative examples:

```
x5: cpp/mnist/mnist.cpp::Net -> fx/custom_tracer.py::forward [Calls]
x4: mnist_forward_forward/main.py::train -> fx/custom_tracer.py::forward [Calls]
x2: legacy/snli/model.py::Bottle -> legacy/snli/model.py::forward [Calls]
```

Almost all duplicates are `Calls` edges, and almost all involve common
short names (`forward`, `train`, `test`, `size`, `main`) that match many
candidates across the 97-file pool — i.e., the ambiguous/heuristic
branch of `resolve_calls`.

**Inferred:** the duplication is not caused by two unrelated resolvers
both emitting the same edge. Reading `resolve_calls`'s own loop
structure confirmed the real mechanism: `call_names_in_tree` returns
ONE entry per SYNTACTIC call-site occurrence it finds while walking a
caller's body (e.g. `self.forward(x); self.forward(y)` yields two
entries, `"forward"` and `"forward"`), and the per-occurrence loop then
pushes a fresh `Edge` for every occurrence — once for the
exact-resolved case, and once PER AMBIGUOUS CANDIDATE for the ambiguous
case. A caller invoking the same (resolved or ambiguous) name more than
once in its own body therefore produces the literal same `(from, to,
kind)` `Edge` value multiple times.

## Root cause

A semantic/data-model mismatch between two layers that were never
reconciled: `resolve_calls` (and, by the same shape, `resolve_imports`
and `resolve_extends_implements`) operates over **syntactic call-site
occurrences** (one entry per place in the source text a construct
appears), while `CodeGraph` represents **semantic/topological relations**
— at most one edge per `(from, to, EdgeKind)`, by Task 8's own explicit,
correct invariant. Nothing in any of the three resolvers ever collapsed
"N occurrences of the same relation" into "one relation" before
returning its edge list; each occurrence was treated as if it
independently justified its own `Edge` value, with no deduplication
step at all.

This was not visible in any prior unit test because every existing
fixture, across Tasks 7-9, happened to construct each caller/importer/
heritage-declarer calling or naming any given target AT MOST ONCE. The
real repository was the first input where a function legitimately
called the same thing — or an ambiguous same-named thing — more than
once in its own body, which is an extremely common real-code shape
(e.g. several calls to the same helper, or several calls to a common
name like `forward` that happens to be ambiguous in the given pool).

## Impact

- **Correctness / robustness:** Critical for the same reason as
  B2-ID-001 — it crashes the real pipeline (`observe_commit`/
  `build_graph`) on realistic input, not a rare corner case. `forward`
  being called more than once inside a training loop or inside another
  `forward` is routine in real PyTorch code.
- **Test coverage:** this is also a coverage gap finding in its own
  right — every prior test suite (Task 7's edge resolvers, Task 8's
  graph, Task 9's indexer) exercised only single-occurrence callers, so
  the gap was structural in the test design, not just bad luck.
- **Severity: Critical** (blocks the pipeline on realistic, common input,
  found on the first real repository tried — same bar as B2-ID-001).

## Solution adopted

Deduplicate at the point each resolver's own loop would otherwise push
a second occurrence of an already-seen relation, NOT by relaxing
`CodeGraph`'s duplicate-edge rejection (that invariant stays exactly as
strict as Task 8 defined it) and NOT by a generic silent dedup at
insertion time into `CodeGraph` (which would hide a genuine bug from
any OTHER resolver that might introduce one in the future, by quietly
absorbing it instead of surfacing it as a loud `GraphError`).

Per resolver:

- **`resolve_calls`** (`crates/codegraph-index/src/edges/calls.rs`):
  per caller, every occurrence's candidate `Edge` is upserted into a
  `HashMap<SymbolSnapshotId, Edge>` keyed by `to`, via
  `upsert_preferring_stronger_evidence`/`prefer_edge` — a DETERMINISTIC
  tie-break (never insertion/iteration order): `StaticAnalysis` always
  outranks a heuristic method; when both sides share the same method,
  the choice falls back to a stable, explicit comparison of the
  evidence note text itself, never "whichever happened to be inserted
  first." The per-caller map is flushed to the output, sorted by target
  id bytes, after that caller's own occurrence loop finishes. This never
  merges two DISTINCT targets — only repeated occurrences resolving to
  the exact same target.
- **`resolve_imports`** (`imports.rs`): every edge this resolver ever
  produces is `StaticAnalysis` (an ambiguous import already produces no
  edge at all, per its existing conservative design), so there is no
  evidence-strength tie-break to make — a `HashSet<SymbolSnapshotId>` of
  already-seen targets per snapshot is enough; a second occurrence
  resolving to an already-seen target is simply skipped.
- **`resolve_extends_implements`** (`extends_implements.rs`): same
  all-`StaticAnalysis` reasoning, deduplicated by `(target_id,
  EdgeKind)` rather than just `target_id` — strictly safer, matching
  `CodeGraph`'s own duplicate key exactly, in case a future language
  shape could ever legitimately produce two different `EdgeKind`s for
  the same base/interface name (not observed today, but the dedup key
  costs nothing extra to make exact).
- **`resolve_tests_for`** audited and found NOT vulnerable: it already
  produces at most one edge per snapshot structurally (a `.any()` check,
  never a loop that pushes per match) — no change needed.

**Why this resolves the root cause, not just the symptom:** the fix
does not change WHAT is detected (every occurrence is still walked, so
no real call/import/base-mention is ever missed) — it changes WHEN
multiple occurrences of the SAME relation collapse into the one
`Edge` value the graph's data model actually represents, which is
exactly the semantic/syntactic mismatch identified as the root cause.
Doing this inside each resolver (which knows its own domain's
evidence-strength semantics) rather than generically inside
`CodeGraph::insert_edge` keeps `CodeGraph`'s own invariant meaningful as
a genuine bug detector for any OTHER, not-yet-audited source of
duplicate edges.

## Alternatives considered

### A. Dedup inside each resolver before returning (adopted)

Each resolver understands its own evidence semantics (which method
should win a tie), so the dedup rule can be meaningful rather than
generic. Cost: three near-identical dedup blocks instead of one shared
one — accepted because the three resolvers' evidence-preference rules
are not actually identical in general (only identical in practice today
because `resolve_imports`/`resolve_extends_implements` happen to be
all-`StaticAlysis`), so factoring them into one shared function now
would either be a no-op abstraction or would need to carry a
tie-break policy parameter — not justified by three call sites with
today's actual logic.

### B. Silent dedup at `CodeGraph::insert_edge` (rejected)

Would hide a real bug in ANY future resolver (or Task 10+ API caller)
behind a graph that "just works," defeating the entire purpose of
`DuplicateEdge` as a loud, typed invariant violation. `CodeGraph`'s own
test suite (Task 8) explicitly exercises `DuplicateEdge` as a signal a
caller should never see unless something upstream is wrong — this fix
preserves that signal's value for every future caller, by making sure
the only remaining way to trigger it is a genuine new bug, not an
already-known, already-fixed one.

### C. Represent occurrence multiplicity explicitly (deferred, not adopted now)

A future `CallSite`/`EdgeOccurrence` concept (source span + multiplicity
per occurrence) could preserve "this relation was observed N times, at
these N locations" instead of collapsing to one edge with one evidence
note. Rejected for THIS fix because it would require extending `Edge`'s
own shape (not just this bug's scope) and was explicitly out of scope
per the task's own instruction not to widen `Edge` beyond what fixing
the bug strictly requires. Recorded as a residual limitation below.

## Scope audit

Audited all four typed-edge resolvers for the same occurrence-vs-
relation mismatch, per the task's explicit instruction to check rather
than assume or speculatively patch:

| Resolver | Loop shape | Vulnerable? | Confirmed by test | Fixed |
|---|---|---|---|---|
| `resolve_calls` | one iteration per call-site occurrence, pushes per occurrence (resolved: 1 push; ambiguous: 1 push per candidate) | Yes | `b2_id_002_regression_a_caller_calling_the_same_ambiguous_name_many_times_does_not_panic_on_graph_insertion` and others | Yes |
| `resolve_imports` | one iteration per import statement found, pushes per occurrence when resolved | Yes (confirmed empirically — a test with the same `use` item written twice produced 2 edges before the fix) | `b2_id_002_scope_audit_a_duplicate_import_of_the_same_name_does_not_produce_a_duplicate_edge` | Yes |
| `resolve_extends_implements` | one iteration per base/heritage-clause name found, pushes per occurrence when resolved | Yes (confirmed empirically — `class C(A, A)` produced 2 edges before the fix) | `b2_id_002_scope_audit_the_same_base_named_twice_does_not_produce_a_duplicate_edge` | Yes |
| `resolve_tests_for` | single `.any()` check per snapshot, at most one push total | No — structurally immune | (no regression needed; existing coverage already proves at most one edge per snapshot) | N/A |

No speculative changes were made to `resolve_tests_for` — it was
audited, found not to share the mismatch, and left untouched.

## Tests obbligatori / added

In `edges/calls.rs`:
1. same caller calls the same target twice → 1 edge;
2. same caller calls the same target 5 times → 1 edge;
3. same caller calls two distinct targets → 2 edges;
4. two distinct callers calling the same target → 2 edges, neither
   caller's edge deduplicated against the other's;
5. an ambiguous name called twice by one caller → zero duplicate
   `(from, to, kind)` triples, AND both genuinely distinct ambiguous
   candidates still each get their own edge (dedup never merges
   distinct targets);
6. evidence-selection determinism: two callers with the identical
   repeated-occurrence shape, written in the same order, resolve to
   byte-identical evidence notes — proving the tie-break is not
   order-dependent;
7. direct regression reproducing the real failure mode (a caller
   calling the same ambiguous name 5 times against two real candidates)
   through an ACTUAL `CodeGraph::insert_edge` call, confirming no panic
   / no `GraphError`.

In `edges/imports.rs` and `edges/extends_implements.rs`: one scope-audit
regression test each, proving the specific vulnerable shape (duplicated
`use`/import statement; `class C(A, A)`) now collapses to one edge.

`CodeGraph`'s own direct-duplicate-edge rejection test
(`inserting_the_same_typed_edge_twice_is_rejected_as_duplicate`, Task 8)
was confirmed still present and still passing — this fix does not touch
or weaken that invariant.

## Literature / authoritative evidence

Searched specifically for literature distinguishing call SITES from
call-graph EDGES in program analysis (the general principle behind this
fix — that multiple syntactic occurrences of a relation legitimately
collapse to one edge in a call-graph representation, with occurrence
count/location as separate, optional metadata rather than graph
multiplicity).

No directly applicable authoritative source identified. The
call-site-vs-call-graph-edge distinction is standard, textbook practice
in static call-graph construction (a call graph is conventionally
defined as a graph over PROCEDURES/functions with at most one edge per
caller-callee pair, regardless of how many call sites realize it), but
no specific paper was searched for and confirmed as the primary,
on-point citation for this exact framing within this finding's own
literature pass. This is recorded honestly rather than forcing a
citation; a future finding or documentation pass may add a proper
citation (e.g. to a standard program-analysis/compilers reference on
call-graph construction) if one is found to genuinely support this
specific point.

## Residual limitations

- **Call-site multiplicity is lost.** The fix deliberately collapses N
  occurrences of the same relation into one `Edge` with one evidence
  note — it does not currently preserve "this call happened at these N
  specific source locations." A future `CallSite`/`EdgeOccurrence`
  concept (see Alternative C) would be needed to recover that
  information for debugging or code-navigation use cases that care
  about EVERY call site, not just the existence of the relation. This is
  an explicit, accepted scope boundary for this fix, not an oversight.
- **The evidence-preference tie-break is intentionally minimal.** When
  two occurrences of the same `(from, to)` pair would produce DIFFERENT
  evidence (today: only possible if the same callee name resolved
  uniquely on one occurrence and ambiguously on another within the same
  caller — not actually reachable given `find_by_name`'s candidate set
  is stable within one `resolve_calls` call, but handled explicitly
  rather than left as an unreachable, unproven assumption), the current
  rule picks `StaticAnalysis` over heuristic, and otherwise breaks ties
  by comparing evidence note text. This is deterministic and tested,
  but it is a narrow, ad hoc rule specific to today's two
  `ResolutionMethod`s actually in play here, not a general "confidence
  ranking" framework — a future edge kind or resolver with a richer
  evidence model may need its own, separately-designed tie-break rule
  rather than reusing this one as-is.
- **This fix does not change what `resolve_calls`/etc. detect** — only
  how many times a detected relation is recorded. The known Task 7 gaps
  (Rust macro-invisible calls, `Imports` rarely firing on real
  extracted data) remain exactly as they were; this finding neither
  worsens nor improves them.
