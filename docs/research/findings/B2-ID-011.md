# B2-ID-011: C#/C++ generic/template method calls via member access (`receiver.Method<T>(...)`) are entirely invisible to `resolve_calls`

**Severity:** Important.
**Status:** FIXED, tested, mutation-verified, real-corpus remeasured, pending independent review. Discovered during B2-EVAL-008's resumed final measurement pass. Per explicit user instruction, Important/Critical findings STOP the evaluation and get reported, not auto-fixed — then, on separate explicit authorization, this circumscribed fix was implemented.

**Discovered by:** B2-EVAL-008 (C#/C++ domain multi-codebase
validation), while investigating why `resolve_calls` found **zero**
Calls edges targeting any of the 4 real `Handle<TException>()`
overloads in `Policy.HandleSyntax.cs`, despite the real corpus
containing hundreds of real call sites invoking them.

## Real-repository reproduction

`App-vNext/Polly`, commit `1f232caf9672e515751ba2df76d82bfbbb62e016`.

```csharp
Policy.Handle<DivideByZeroException>()
    .Retry();
```

— a real, extremely common pattern across the test suite. Direct
measurement: **875 real `.Handle<...>()` call sites** in
`test/Polly.Specs/` alone (`grep -rc "\.Handle<" test/Polly.Specs/`).
`resolve_calls` produces **zero** `Calls` edges toward any `Handle`
snapshot anywhere in the corpus (confirmed directly: 6 snapshots
named exactly `"Handle"` exist in the full pool, 0 incoming `Calls`
edges target any of them).

## Root cause

`crates/codegraph-index/src/edges/calls.rs`'s `callee_name` function,
for a receiver-qualified call (`callee.kind() ==
"member_access_expression"`), finds the callee's own name by
filtering that node's direct children for kind
`"identifier"`/`"property_identifier"`/`"field_identifier"` and
taking the LAST match:

```rust
"attribute" | "field_expression" | "member_expression" | "member_access_expression" => {
    let mut cursor = callee.walk();
    let last_name_child = callee
        .children(&mut cursor)
        .filter(|c| matches!(c.kind(), "identifier" | "property_identifier" | "field_identifier"))
        .last()?;
    Some(text_of(last_name_child, source))
}
```

Direct grammar probe (minimal fixture
`Policy.Handle<DivideByZeroException>().Retry();`, this workspace's
real compiled `tree-sitter-c-sharp` grammar, not assumed) shows the
real AST shape:

```
member_access_expression: "Policy.Handle<DivideByZeroException>"
  identifier: "Policy"
  .
  generic_name: "Handle<DivideByZeroException>"
    identifier: "Handle"
    type_argument_list: "<DivideByZeroException>"
```

The method name `Handle` is NOT a direct child of
`member_access_expression` at all when the method call carries a
type-argument list — it is wrapped one level deeper inside a
`generic_name` node, which is the only direct child matching none of
`identifier`/`property_identifier`/`field_identifier`. The filter
therefore finds **zero** matching children, `.last()` returns `None`,
`callee_name` returns `None`, and `walk_for_calls` (`calls.rs`,
`is_call_node` branch) silently **drops the entire call site** —
never recording it even as unresolved or ambiguous. This is NOT the
same defect as B2-ID-009 (a return-type/name collision inside
`method_declaration`'s own two `identifier` children) — this is a
callee-name EXTRACTION gap on the `Calls`-resolution side, in a
completely different function, for a completely different node shape.

## Scope (measured, not assumed)

Direct corpus-wide measurement, walking every real `invocation_expression`
node in every `.cs` file at commit B:

```
total invocation_expression nodes in corpus:                    26,508
receiver.Method<T>(...) shaped calls (generic_name inside
  member_access_expression) -- INVISIBLE to resolve_calls:        4,977  (18.8% of all call sites)
bare Method<T>(...) shaped calls (generic_name as direct
  callee, no receiver) -- CONFIRMED by independent review to be
  the SAME defect: `callee_name`'s own `"identifier" => ...` arm
  does not match `generic_name` either, so a bare generic call's
  own callee node (e.g. `Handle<DivideByZeroException>();` with
  no receiver) is dropped by the same `_ => None` fallthrough:     166
```

**18.8% of every call site in this real corpus is a generic method
call via member access** — this is not a rare edge case. Any C#
codebase using fluent/generic APIs (a common, idiomatic style —
LINQ's own `.Select<T>()`/`.Where<T>()`, Polly's own
`.Handle<T>()`/`.HandleResult<T>()`, any `.Cast<T>()`/`.OfType<T>()`,
and countless user-defined generic extension methods) will trigger
this gap pervasively. This is a false negative at the
call-site-collection stage itself — the call is never even considered
a candidate, so it cannot show up as `Unresolved` or `Ambiguous`
either; it is simply absent from the edge set with no trace.

**Interaction with the domain's own central research question**:
this gap is the DIRECT reason Section C2's own overload-ground-truth
measurement in B2-EVAL-008 found 0 `Calls` edges toward any `Handle`
overload — not because the 4 overloads were ambiguously collapsed (a
name-resolution question), but because the call sites that would
resolve to them were never extracted as call sites at all (an
extraction question, upstream of name resolution entirely). This
means B2-EVAL-008's own CALL-RES-A4/A5 overload-resolution research
question cannot be answered cleanly from this corpus's `Handle`
example until this extraction gap is fixed — the absence of evidence
for overload ambiguity here is not evidence that overloads are
unambiguous; it is an artifact of this gap.

## Fix implemented

`callee_name` (`crates/codegraph-index/src/edges/calls.rs`) now
recognizes a generic/template-wrapped callee in BOTH positions it can
appear: as a direct callee (`"generic_name" | "template_function"`,
the bare, no-receiver shape) and as the last child of a
member-access-shaped callee (`"generic_name" | "template_method"`
added to the existing receiver-qualified filter). A new helper,
`wrapped_callee_simple_name`, extracts the wrapper node's own first
`identifier`/`field_identifier` child — confirmed via direct grammar
probe to be the bare method name in every shape tested, with no
competing same-kind sibling at that position (so, unlike
`method_declaration`'s return-type/name collision B2-ID-009 fixed, a
positional "first matching-kind child" search is safe here).

**Cross-language scope audit finding**: contrary to this finding's
own original "plausibly NOT affected — not yet confirmed" note on
C++, a direct grammar probe performed as part of implementing the fix
found that **C++ has the identical structural defect** under
different node-kind names: a bare template call (`Foo<int>()`) wraps
its callee in a `template_function` node, and a receiver-qualified
template call (`obj.Foo<int>()`) wraps it in a `template_method` node
— neither was recognized before this fix, for the exact same
mechanism as C#'s `generic_name`. Rust/Python/JS/TS have no such
wrapper-node construct at all (confirmed by the absence of any
analogous shape in their own grammars, consistent with how neither
language syntax supports this exact "generic/template method call"
form at the call site in the same way) — fixing C++ alongside C# was
judged to be within this fix's own "minimal extension of the existing
pattern" scope (the SAME two match arms, two more node-kind names),
not a redesign or a new policy, so it was included rather than
deferred to a separate finding.

**Generic arity**: deliberately NOT extracted or used by this fix, per
explicit scope. `wrapped_callee_simple_name` reads only the wrapper
node's own name child, never inspecting `type_argument_list`/
`template_argument_list`'s own contents — a generic call with 1 vs. 2
type arguments extracts identically (confirmed by a dedicated test),
and a generic/non-generic overload pair sharing one bare name produces
the SAME ambiguity outcome any other same-named candidate pair would
(confirmed by a dedicated test asserting no edge, not an arbitrary
pick) — this fix does not attempt arity-aware disambiguation.

**Tests**: 18 new `#[test]` functions in `calls.rs`'s own
`b2_id_011_generic_method_calls` module (bare/receiver-qualified/
nested-receiver/`this`-qualified/chained/nested-in-argument generic
calls, multiple type arguments, same-name generic+non-generic
overloads, repeated-occurrence dedup, ordinary non-generic call
non-regression, plus 4 C++ template-call tests mirroring the C#
coverage — corrected here from an earlier miscount of 23, which
counted 3 non-test helper functions alongside the real tests; caught
by independent review, not self-caught), plus 5 new tests in
`incremental::indexer`'s own
`b2_id_011_csharp_generic_calls_through_the_real_indexer` module (full
reindex, incremental-advance parity, zero effect on
Extends/Implements, zero snapshot-identity change) — **23 real
regression tests total**, not 28. Full suite:
482/482 passing, zero regressions — including every other language's
own pre-existing call-resolution tests, confirming no cross-language
impact beyond the deliberate C++ extension.

**Mutation testing** (`cargo mutants`, scoped to the whole
`calls.rs` file — this fix's own new code plus every pre-existing
function in the same file): 118 mutants — 110 caught, 7 unviable, 1
missed. The one missed mutant (`calls.rs:397`, `delete match arm 0 in
narrow_by_scope`) is PRE-EXISTING and already explicitly documented
as an EQUIVALENT mutant in that function's own doc comment, from
Task 9.5's own closing mutation gate — predating this fix entirely,
in code this fix never touched. Deleting that `0` match arm falls
through to the identical `_ => None` arm, so no input can ever
distinguish the two as written; this is not a genuine
correctness-relevant gap introduced by B2-ID-011. **Zero genuine
missed correctness-relevant mutants in this fix's own new code.**

**The `Handle` case, precisely separated**: 931 real generic `Handle`
call sites exist in caller-eligible signatures; before this fix, 0 of
them were even extracted (reached candidate status) — not ambiguous,
not unresolved, simply invisible. After this fix, they ARE extracted,
and resolution finds 6 real `Handle`-named snapshots in the pool
(confirmed, separately, by B2-ID-009's own fix — 4 real overloads
correctly named, plus whatever other `Handle`-named symbols exist
elsewhere in the corpus): exactly **one** `Calls` edge to a `Handle`
snapshot resolves, via `NameHeuristic` (scoped to the caller's own
file, per the pre-existing CALL-RES-A2 scoping rule) — never
`StaticAnalysis`, since more than one same-named candidate exists.
This cleanly separates the two previously-conflated questions: the
call sites are no longer invisible (this fix's own job, done), and
the remaining overload/generic-arity ambiguity among same-named
`Handle` candidates is untouched, exactly as scoped — a SEPARATE,
still-open question for any future CALL-RES-A5-style work.

**No new false positives found**: the +46 `Calls` edges and the

**Residual limitation found by independent review (pre-existing, NOT
a regression, NOT fixed here)**: a C++ namespace-qualified call,
`ns::Foo<int>()`, produces `qualified_identifier` as `call_expression`'s
own first child (wrapping `template_function` one level deeper) — a
third shape `callee_name` does not match, so this specific call site
remains silently dropped even after this fix. Confirmed by the
reviewer's own direct grammar probe that this is NOT a generics-specific
gap this fix introduced or missed: a plain, NON-generic
`ns::Foo()` already hits the identical unhandled `qualified_identifier`
shape before this fix existed at all. Left unfixed, as a separately
tracked, orthogonal limitation of `callee_name`'s own C++
namespace-qualified-call coverage — out of this fix's own scope
(B2-ID-011 is about generic/template wrapper nodes specifically, not
namespace-qualification).

## Independent review

**Verdict: APPROVE WITH NOTES.** A fresh, independent reviewer
confirmed every grammar-shape claim via their own direct probes
(including several shapes beyond this fix's own test coverage:
namespace-qualified type arguments, array-type arguments, 3+-segment
receiver chains, doubly-chained generics, multi-type-argument calls,
and several C++-specific variants), confirmed the arithmetic in both
evidence files traces cleanly to the numbers cited here, confirmed
the one missed mutant is genuinely pre-existing and already documented
as equivalent from Task 9.5's own mutation gate (verified via
`git log --follow` that the doc comment predates this fix), confirmed
`cargo test -p codegraph-index` independently at 482/482, and
confirmed the repository was left in a clean, correct state after the
mid-flight git-swap maneuver (no stray probe/backup files, `calls.rs`
as committed contains the fix not the temporarily-restored pre-fix
content). The reviewer judged the C++ scope expansion to be within
the originally authorized "quick cross-language audit" language,
since it reused the identical two match arms and the identical helper
function rather than introducing any new mechanism — a judgment call
a stricter reviewer could reasonably have decided differently on, but
not a correctness problem. One Important factual error was found and
corrected (the test-count claim above) and one new, pre-existing,
NOT-a-regression C++ limitation was found and documented (the
`qualified_identifier` namespace-qualified-call gap above).
