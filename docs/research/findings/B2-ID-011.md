# B2-ID-011: C# generic method calls via member access (`receiver.Method<T>(...)`) are entirely invisible to `resolve_calls`

**Severity:** Important.
**Status:** OPEN, not fixed. Discovered during B2-EVAL-008's resumed final measurement pass. Per explicit user instruction, Important/Critical findings STOP the evaluation and get reported, not auto-fixed.

**Discovered by:** B2-EVAL-008 (C#/C++ domain multi-codebase
validation), while investigating why `resolve_calls` found **zero**
Calls edges targeting any of the 4 real `Handle<TException>()`
overloads in `Policy.HandleSyntax.cs`, despite the real corpus
containing hundreds of real call sites invoking them.

## Real-repository reproduction

`App-vNext/Polly`, commit `1f232caf9672e515751ba2df76d82bfbbb62e016`.

```csharp
Policy.Handle<DivideByZeroException>()
    .Retry();
```

— a real, extremely common pattern across the test suite. Direct
measurement: **875 real `.Handle<...>()` call sites** in
`test/Polly.Specs/` alone (`grep -rc "\.Handle<" test/Polly.Specs/`).
`resolve_calls` produces **zero** `Calls` edges toward any `Handle`
snapshot anywhere in the corpus (confirmed directly: 6 snapshots
named exactly `"Handle"` exist in the full pool, 0 incoming `Calls`
edges target any of them).

## Root cause

`crates/codegraph-index/src/edges/calls.rs`'s `callee_name` function,
for a receiver-qualified call (`callee.kind() ==
"member_access_expression"`), finds the callee's own name by
filtering that node's direct children for kind
`"identifier"`/`"property_identifier"`/`"field_identifier"` and
taking the LAST match:

```rust
"attribute" | "field_expression" | "member_expression" | "member_access_expression" => {
    let mut cursor = callee.walk();
    let last_name_child = callee
        .children(&mut cursor)
        .filter(|c| matches!(c.kind(), "identifier" | "property_identifier" | "field_identifier"))
        .last()?;
    Some(text_of(last_name_child, source))
}
```

Direct grammar probe (minimal fixture
`Policy.Handle<DivideByZeroException>().Retry();`, this workspace's
real compiled `tree-sitter-c-sharp` grammar, not assumed) shows the
real AST shape:

```
member_access_expression: "Policy.Handle<DivideByZeroException>"
  identifier: "Policy"
  .
  generic_name: "Handle<DivideByZeroException>"
    identifier: "Handle"
    type_argument_list: "<DivideByZeroException>"
```

The method name `Handle` is NOT a direct child of
`member_access_expression` at all when the method call carries a
type-argument list — it is wrapped one level deeper inside a
`generic_name` node, which is the only direct child matching none of
`identifier`/`property_identifier`/`field_identifier`. The filter
therefore finds **zero** matching children, `.last()` returns `None`,
`callee_name` returns `None`, and `walk_for_calls` (`calls.rs`,
`is_call_node` branch) silently **drops the entire call site** —
never recording it even as unresolved or ambiguous. This is NOT the
same defect as B2-ID-009 (a return-type/name collision inside
`method_declaration`'s own two `identifier` children) — this is a
callee-name EXTRACTION gap on the `Calls`-resolution side, in a
completely different function, for a completely different node shape.

## Scope (measured, not assumed)

Direct corpus-wide measurement, walking every real `invocation_expression`
node in every `.cs` file at commit B:

```
total invocation_expression nodes in corpus:                    26,508
receiver.Method<T>(...) shaped calls (generic_name inside
  member_access_expression) -- INVISIBLE to resolve_calls:        4,977  (18.8% of all call sites)
bare Method<T>(...) shaped calls (generic_name as direct
  callee, no receiver) -- NOT yet separately confirmed broken
  or working; same risk, not measured in this pass:                 166
```

**18.8% of every call site in this real corpus is a generic method
call via member access** — this is not a rare edge case. Any C#
codebase using fluent/generic APIs (a common, idiomatic style —
LINQ's own `.Select<T>()`/`.Where<T>()`, Polly's own
`.Handle<T>()`/`.HandleResult<T>()`, any `.Cast<T>()`/`.OfType<T>()`,
and countless user-defined generic extension methods) will trigger
this gap pervasively. This is a false negative at the
call-site-collection stage itself — the call is never even considered
a candidate, so it cannot show up as `Unresolved` or `Ambiguous`
either; it is simply absent from the edge set with no trace.

**Interaction with the domain's own central research question**:
this gap is the DIRECT reason Section C2's own overload-ground-truth
measurement in B2-EVAL-008 found 0 `Calls` edges toward any `Handle`
overload — not because the 4 overloads were ambiguously collapsed (a
name-resolution question), but because the call sites that would
resolve to them were never extracted as call sites at all (an
extraction question, upstream of name resolution entirely). This
means B2-EVAL-008's own CALL-RES-A4/A5 overload-resolution research
question cannot be answered cleanly from this corpus's `Handle`
example until this extraction gap is fixed — the absence of evidence
for overload ambiguity here is not evidence that overloads are
unambiguous; it is an artifact of this gap.

## Impact on this evaluation's other sections

- **Calls quality manual sample**: any manual TP/FP/FN sample drawn
  from this corpus's current `Calls` edge set will systematically
  undercount true positives for every generic-method-call pattern —
  not a representative sample of what this corpus's real call graph
  looks like.
- **Coding-agent usefulness Q&A** ("which overload gets invoked?",
  "who calls this method?" for any generic method): answers drawn
  from the current graph will incorrectly report "no callers" for
  methods that ARE called, exclusively via this invisible pattern.
- **C#/C++ domain's own overload research question**: cannot be
  cleanly answered until this is fixed or worked around, per the
  interaction noted above.

## Not implemented

Per instruction, no fix is implemented as part of this finding. A
plausible fix direction (not committed to, not verified for side
effects): extend `callee_name`'s `member_access_expression` filter to
also recognize a `generic_name` child, extracting ITS OWN inner
`identifier` field (confirmed by the same grammar probe:
`generic_name`'s own `identifier` child holds the bare method name,
mirroring exactly how `generic_name` is already unwrapped elsewhere
in this codebase for base-clause types, e.g.
`edges/extends_implements.rs`'s own C++ base-type handling and
`impls.rs`'s Rust generic-type unwrapping). Whether the SAME gap
exists for the `bare Method<T>(...)` (no-receiver) call shape, and
whether C++'s own template call syntax has an analogous gap, are
explicitly NOT checked in this finding — left for the fix's own scope
audit, per the same discipline B2-ID-009's own cross-language audit
used.
