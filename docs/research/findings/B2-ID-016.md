# B2-ID-016: `Foo.X = function(){...}` where `Foo` is a plain local identifier (not `exports`/`module.exports`/`.prototype`) is still invisible

**Severity:** Moderate (coverage gap, not correctness). Confirmed honest
silent drop — not a defect in the B2-ID-014/B2-ID-015 fixes, a
distinct, real CommonJS idiom outside this checkpoint's own
authorized scope.
**Status:** DOCUMENTED, confirmed on real corpus data. NOT implemented
— out of the CommonJS Extraction Checkpoint's explicitly authorized
scope (the checkpoint's own directive named exactly four shapes:
`require(...)`, `exports.X = ...`, `module.exports.X = ...`, and
`Foo.prototype.X = ...`; this is a fifth, real shape not among them).

**Discovered by:** CommonJS Extraction Checkpoint (the B2-ID-013/014/015
closeout checkpoint), during real-corpus remeasurement on
`request/request`@`3c0cddc7c8eb60b470e9519da85896ed7ee0081e`.

## The gap

`request/request`'s own `index.js` declares a plain local function
(`function request(uri, options, callback) {...}`), then attaches
properties directly onto it before exporting the function itself as
the module's own value:

```js
request.jar = function (store) {
  return cookies.jar(store)
}

request.cookie = function (str) {
  return cookies.parse(str)
}

module.exports = request
```

This is a real, distinct CommonJS idiom — attaching named exports as
properties on the function/object that IS the module's own export
value, as opposed to `exports`/`module.exports` (the special
CommonJS binding names) or `Foo.prototype` (the ES5 class-method
idiom). `commonjs_property_function_assignment`'s own
`is_exports_receiver`/`is_prototype_receiver` checks both correctly
reject this receiver (`request` is neither literally `exports`/
`module.exports` nor does it have a `.prototype` segment) — this is
the extractor working exactly as scoped, not a bug in B2-ID-014/015's
own fixes.

## Effect measured

Two real call sites in this corpus are affected: `index.js:76`'s
`cookies.jar(store)` (inside `request.jar`'s own body — the CALLER
itself is invisible, so this call site is never visited at all) and
`index.js:80`'s `cookies.parse(str)` (inside `request.cookie`, same
mechanism). Both are honest silent drops — zero false edges confirmed.

## Why this is NOT fixed in this checkpoint

The checkpoint's own directive named exactly four shapes to implement,
and explicitly forbade "new unrelated JS features." Recognizing
`Foo.X = function(){}` for an ARBITRARY identifier `Foo` would require
either (a) treating every single-segment property assignment to a
function expression as a candidate regardless of receiver — a much
broader, qualitatively different rule than the three scoped exactly to
`exports`/`module.exports`/`.prototype`, with real risk of false
positives on unrelated property assignments that are not export
patterns at all — or (b) specifically detecting "this identifier is
later passed to `module.exports =`," which is a genuine data-flow
question (explicitly out of scope: no data-flow authorized this
checkpoint). Neither was authorized.
