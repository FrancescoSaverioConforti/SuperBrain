# B2-ID-003: the chained-call "false negative" in B2-EVAL-001 was an evaluation-harness bug, not a production pipeline defect

**Discovered by:** Task 9.5's own root-cause investigation into
[B2-EVAL-001](../evaluations/B2-EVAL-001.md)'s reported chained-call
false negative, conducted per that task's explicit instruction to
formally diagnose root cause before any fix.

## Discovery context

Task 9.5 (evidence-driven semantic coverage expansion) required
formally root-causing two call-resolution quality issues B2-EVAL-001
reported: a common-name false positive and a chained-call false
negative. Investigating the chained-call case led to re-cloning
`pytorch/examples` (https://github.com/pytorch/examples, BSD-3-Clause)
at commit `001d493285083b54cacbc1334cb26338bdff2455` and reproducing
the exact scenario directly against the current pipeline.

## Observable evidence

**Observed (B2-EVAL-001's original claim):** `word_language_model/model.py`'s
`TransformerModel::forward` calls `self._generate_square_subsequent_mask(len(src)).to(device)`
— a chained call — and this call was reported as never resolving to a
`Calls` edge, with the root cause left explicitly undiagnosed in that
evaluation.

**Observed (this investigation, MEASURED/directly confirmed):**

1. A real-parse dump of the exact chained-call source confirms
   `calls::call_names_in_tree` (and its own `walk_for_calls`/
   `callee_name` helpers) correctly extract ALL THREE call names
   present — `"to"`, `"_generate_square_subsequent_mask"`, and `"len"`
   — from this statement. The recursive AST walk does reach the inner,
   chained call node; nothing in extraction drops it.
2. An isolated, minimal reproduction (`resolve_calls` given exactly a
   `forward` snapshot with this body and a `_generate_square_subsequent_mask`
   snapshot) produces the expected `Calls` edge correctly, on the first
   attempt, with no code changes.
3. A reproduction using the FULL real bodies of `TransformerModel::forward`
   and `TransformerModel::_generate_square_subsequent_mask` (copied
   verbatim from the real repository) ALSO produces the correct edge.
4. Re-running the full real pipeline against the actual repository
   (97 real files, 567+ real snapshots) confirmed the edge is produced
   in the real `CodeGraph` too: `incoming_edges` on the CURRENT
   `_generate_square_subsequent_mask` snapshot includes an edge from
   `word_language_model/model.py::forward` with `EdgeKind::Calls`.
5. The actual bug was in the EVALUATION HARNESS's own query logic
   (`crates/codegraph-index/examples/b2_smoke_test.rs`, the throwaway
   investigative tool B2-EVAL-001 was produced with): it selected "the
   current snapshot named `forward` in `word_language_model/model.py`"
   by filtering on local name plus "has no outgoing lineage edge"
   alone. `word_language_model/model.py` contains TWO classes with a
   `forward` method — `RNNModel.forward` and `TransformerModel.forward`
   — and across one A→B incremental update, this produced **three**
   simultaneously-"current" (no-outgoing-lineage) `forward`-named
   snapshots in that one file (confirmed by direct enumeration: ids
   with signature lengths 564, 300, and 423 bytes, all three with
   `has_outgoing_lineage=false`). The harness's `.find()` call picked
   whichever one happened to come first in that iteration, which was
   sometimes `RNNModel.forward`, which genuinely does NOT call
   `_generate_square_subsequent_mask` — producing an apparent, but
   spurious, "no callees found" result.

## Root cause

A data-model mismatch inside the EVALUATION HARNESS, not the production
pipeline: the harness identified its query SUBJECT ("the current
`forward`") using only `(local_name, no-outgoing-lineage)`, a
disambiguation rule that is only sufficient when at most one
current-generation snapshot shares that local name in the scope being
queried. Once more than one class in the same file has a method with
that name — a common, unremarkable real-code shape, and in fact the
EXACT shape this corpus has (`RNNModel`/`TransformerModel` both define
`forward`) — that rule silently picks an arbitrary one of several
equally-"current" candidates, with no signal to the caller that the
selection was ambiguous.

This is squarely a measurement/evaluation-methodology defect, not a
correctness defect in `calls.rs`, `CodeGraph`, or the incremental
indexer — every one of those was independently, repeatedly confirmed
correct in this investigation.

## Impact

- **Evaluation correctness / research validity:** Important. A wrong
  subject-selection in a validation harness can produce a false
  negative (or, in principle, a false positive) in a measurement that
  then gets written up as a finding about the PRODUCT, when the defect
  is actually in the MEASURING APPARATUS. This is exactly the failure
  mode the Evaluation & Paper Evidence Policy's Measured/Manually
  validated/Inferred/Estimated discipline exists to catch, and it was
  caught here — one turn late (the original claim was published in
  B2-EVAL-001 before this re-investigation), but caught and corrected
  rather than left standing.
- **Coding-agent measurement accuracy:** any future evaluation that
  asks "what does symbol X call" for a commonly-named symbol in a
  file/project with more than one class defining a same-named method
  needs a genuinely scope-aware subject selector, or it will
  systematically misreport results for exactly the kind of real-code
  shape (overloaded method names across sibling classes) this project
  cares most about getting right.
- **Severity: Important**, not Critical — it did not affect the
  production pipeline's own correctness (no code outside the
  evaluation harness needed to change), but it DID affect the validity
  of a previously-published research claim, which the project's own
  policy treats seriously.

## Solution adopted

Fixed the harness's subject-selection logic to be genuinely scope-aware,
reusing Task 9.5's own `Contains` edge (Priority 2) rather than
inventing anything PyTorch-specific: `find_current_member_of_class(class_name,
member_name)` looks up the CURRENT snapshot named `class_name`, follows
its outgoing `Contains` edges to find the CURRENT member named
`member_name` among its actual children, and returns that one
specific, disambiguated snapshot. This generalizes to ANY file/project
with same-named members across different classes — nothing in the fix
names `RNNModel`, `TransformerModel`, or `word_language_model` in its
own logic; those names are passed in as ordinary arguments by the
evaluation code that calls it, exactly like any other lookup.

**Why this resolves the root cause, not just the symptom:** the
previous rule's blind spot was using a NAME-based heuristic where a
STRUCTURAL one (which class actually contains this member, per the
AST-grounded `Contains` edge) was available and unambiguous. The fix
replaces the name-based guess with the structural fact, closing the
ambiguity entirely rather than picking a different, still-fragile
heuristic.

## Alternatives considered

### A. Scope-aware lookup via `Contains` (adopted)

Directly reuses an edge kind this same task (9.5) already added for an
unrelated reason (reconstructing class structure), with no new graph
primitive needed. Generalizes to any language/file shape that already
produces `Contains` edges.

### B. Fully qualified names (`Priority 4` of this same task)

Priority 4 (scope-aware qualified names, e.g. `RNNModel.forward` vs.
`TransformerModel.forward` as distinct, directly-nameable identifiers)
would also resolve this specific harness bug, and is a more general,
longer-term answer to the same underlying "local name is not a unique
key" problem. Not used for THIS specific fix because `Contains`-based
lookup was already available and sufficient, and tying the harness fix
to Priority 4's own design (which needed its own separate, careful
design work) would have coupled an urgent correctness fix to a larger,
still-in-progress piece of work. Once Priority 4 lands, a qualified-name
lookup may be a cleaner, more direct way to express the same query —
recorded as a candidate future simplification, not a requirement.

### C. Disambiguate by picking the snapshot with the longest/shortest
### signature text, or by file position (rejected)

Both are heuristics that happen to work for THIS corpus by coincidence
(e.g. `TransformerModel::forward`'s body happens to be a different
length than `RNNModel::forward`'s) but generalize to nothing — a
future file where two same-named methods happen to have similarly-
sized bodies would silently reintroduce the exact same bug. Rejected
for being exactly the kind of overfit-to-this-corpus fix Task 9.5 was
explicitly instructed to avoid.

## Validation

- Direct, isolated reproduction of the chained-call resolution (a
  2-snapshot minimal case) confirms `resolve_calls` was already correct
  before any fix in this finding.
- A second reproduction using the exact, full real method bodies
  (copied verbatim from the real repository) also confirms correctness
  independently of the first, smaller reproduction.
- Re-running the real pipeline against a freshly re-cloned copy of
  `pytorch/examples` at the exact original commit, 5 times in
  succession, with the FIXED harness: the diagnostic check "does
  `TransformerModel::forward` resolve its chained call to
  `_generate_square_subsequent_mask`" reports `true` on every single
  run (previously, using the OLD harness logic, the equivalent
  observation varied depending on which of three same-named "current"
  candidates the unfixed `.find()` happened to select first).
- No `DuplicateEdge`/`DuplicateSnapshot` or other panic occurred across
  any of the 5 repeated runs.
- Full workspace test suite, clippy, and `cargo deny check`: see this
  finding's closing validation alongside the rest of Task 9.5's own
  changes (recorded in the task's closing report, not duplicated here).

## Literature / authoritative evidence

No directly applicable authoritative source identified for this
specific finding. The general principle — that an evaluation/
measurement apparatus can itself be a source of error independent of
the system under test, and that this must be checked rather than
assumed away — is foundational to experimental methodology broadly
(measurement validity, construct validity), but no specific paper on
program-analysis-tool evaluation methodology was identified as
genuinely on-point during this finding's literature pass, and none is
forced here as a citation of convenience.

## Residual limitations

- This fix repairs the EVALUATION HARNESS, which is throwaway
  investigative tooling (per its own module doc comment), not a
  permanent library feature. The general problem it exposes — "a local
  name alone is not a unique key once more than one scope defines a
  symbol with that name" — is exactly what Priority 4 (scope-aware
  qualified names) of this same task addresses at the PRODUCT level;
  this finding's fix is scoped to making THIS evaluation tool correct,
  not to retrofitting every possible future caller of this pipeline
  against the same class of bug.
- `find_current_member_of_class`'s own "current" determination (no
  outgoing lineage edge) still assumes a two-generation-or-fewer world
  implicitly in spirit, even though it now correctly scopes by class —
  if a THIRD generation of the same class existed with multiple
  "current" (no-outgoing-lineage) members sharing a name within that
  one class (e.g. via some other ambiguity this task's investigation
  did not anticipate), the same class of bug could in principle
  recur one level deeper. Not observed in this investigation, not
  fixed speculatively — recorded as a boundary condition worth
  revisiting if a future evaluation surfaces it concretely.
