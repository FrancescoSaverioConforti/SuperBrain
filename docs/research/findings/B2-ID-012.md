# B2-ID-012: `resolve_lineage`'s O(n²) similarity scoring dominates incremental reindex cost — isolated via proper multi-run measurement

**Severity:** Moderate (performance, not correctness). No edge, snapshot, or query-visible behavior is affected — this is purely a wall-clock cost finding.
**Status:** DOCUMENTED, root-caused, measured with proper statistical methodology (10 runs, median + dispersion). NOT fixed, per explicit instruction: a pure-performance finding is not fixed in this pass unless Critical/Important, and this is Moderate.

**Discovered by:** Semantic Resolution & Reliability Checkpoint, Priority 7 (performance investigation), while redoing the prior pass's own inconclusive single/few-run measurement with proper repeated-run methodology against the real `App-vNext/Polly` corpus.

## Context: why the prior pass's own measurement was inconclusive

An earlier pass of this same checkpoint measured `index_files` (parse+extract, 41 changed files) at "4.7-4.8s," found this surprising (slower than a 792-file full reindex measured earlier at ~3.95s in a *different* run), and — after a third run came back at 5.28s — concluded the result was dominated by run-to-run environmental variance, unable to isolate a specific structural cause within that pass's own time budget. That earlier pass's temporary timing instrumentation was reverted, uncommitted, per the project's own "ephemeral probe, delete after confirming" convention, so the investigation had to be redone from scratch this pass with a properly repeated protocol.

## Real measurement (this pass): 10 repeated runs, same commit pair, same machine

`App-vNext/Polly`, commits `32064ed55ab47e05b590be0360c8c45ce3901a73` → `1f232caf9672e515751ba2df76d82bfbbb62e016`, same pair used throughout this whole evaluation series. Temporary `Instant`-based probes added at four points inside `pipeline::index_files` and `indexer::incremental_reindex` (never committed; fully reverted after this measurement — confirmed via `git diff` showing zero net change to either file). 10 full runs of the real `b2_smoke_test_csharp_cpp` harness, release build, no warm-up discarded (the first run was not an outlier — see below, so no warm-up effect was actually present to discard).

```
resolve_lineage(prev=0,    current=5121)  [full reindex]:     median 131µs   (range 107-183µs)
resolve_lineage(prev=686,  current=755)   [incremental, 41 changed files]: median 3.883s  (range 3.856-3.980s)
index_files(41 files) total (incremental path):                median 4.686s  (range 4.658-4.830s)
```

Full raw evidence (all 10 runs, every probe line) preserved at `docs/research/evidence/b2-eval-006-priority7-performance-10-runs-lineage-finding.txt`.

**Dispersion is tight (~3% spread on both the dominant cost and the total) — this result is NOT environmental noise.** The prior pass's own "30% variance, inconclusive" finding does not reproduce here with a properly controlled repeated-run protocol on the same machine; this pass's own 10-run spread is an order of magnitude tighter.

## Root cause (confirmed by direct code reading, not inferred from timing alone)

`resolve_lineage` (`crates/codegraph-index/src/lineage/resolver.rs`), for every `next` snapshot with no exact structural match among `available` `prev` candidates, falls through to a similarity-scoring loop (`best_candidate`, lines ~196-209) that calls `similarity_score` for every same-`SymbolKind` candidate still in `available`. `similarity_score` (`crates/codegraph-index/src/lineage/similarity.rs`) computes `longest_common_substring_len`, an **O(signature_a.len() × signature_b.len())** dynamic-programming algorithm, over the full signature TEXT of both snapshots (which, per this pipeline's own convention, includes the method body, not just the declaration).

For the incremental case measured here: `prev.len() = 686`, `next.len() = 755` (both scoped to the 41 CHANGED files' own snapshots, per `incremental_reindex`'s own raw-extract/always-reresolve convention for lineage). In the worst case this is up to `686 × 755 ≈ 518,000` same-kind candidate pairs, each paying an O(signature-length²) substring comparison — real C# method signatures in this corpus (which include full bodies and, per B2-EVAL-006's own Priority 2/3 measurement, sometimes run to hundreds or low thousands of bytes) make each individual comparison non-trivial, and the `O(n²)` pair count compounds it.

The FULL-reindex case (`prev.len() = 0`) is measured at ~131µs specifically **because `available` starts empty** — `best_candidate` never reaches the similarity-scoring branch at all when there are zero `prev` candidates to score against, so the full-reindex path accidentally never exercises this cost. This is why the two measurements differ by roughly 30,000x despite the full-reindex case processing a LARGER total snapshot pool (5121 vs. 755): the dominant variable is not pool size, it is whether `prev_snapshots` is non-empty (i.e., whether this is a genuine incremental step with real lineage candidates to score against).

## Classification

**Primary finding, CONFIRMED (not environmental noise, not a measurement artifact): `resolve_lineage`'s O(n² × avg-signature-length²) similarity-scoring path is the dominant real cost of this checkpoint's own incremental-reindex measurement — not `index_files`'s own parse+extract step, not `LocalGitRepositorySource::read_file`'s own per-file git-reopen cost (the separate, still-real, still-unfixed structural inefficiency the PRIOR pass of this same checkpoint found and documented), and not run-to-run system variance.** Both inefficiencies are real and independently confirmed by direct code reading; this finding specifically isolates and ranks them for this corpus/commit-pair: `resolve_lineage`'s cost (~3.88s median) is roughly an order of magnitude larger than whatever `read_file`'s per-call git-reopen overhead contributes within the 41-file incremental path's own ~800ms non-lineage remainder (the parse+extract loop that pays that git-reopen cost, measured separately this pass, comes in at ~185ms median for those same 41 files — see the preserved evidence file).

**Scope and severity reasoning:** this is a real, measurable, reproducible performance cost with a precisely identified root cause — not a correctness defect (no edge/snapshot/query output is wrong; `LineageStatus`/`Confidence` semantics are unaffected). It scales specifically with incremental-step size (number of changed-file snapshots) and corpus signature-text length, meaning it degrades further on larger incremental changes or in languages/corpora with longer per-symbol signature text (e.g. C#'s own doc-comment-inclusive signature convention, confirmed elsewhere in this evaluation series to produce multi-hundred-byte signatures routinely). Judged **Moderate**, not Important/Critical, because: (a) it is a pure latency cost with no functional/safety impact, (b) it affects only the incremental-reindex path's own wall-clock time, not correctness, and (c) this specific corpus/commit-pair's ~4.7s incremental step, while real, is not yet shown to be prohibitive for this project's own current usage pattern (no SLA or interactive-latency requirement has been stated for this pipeline).

## Why this is NOT fixed in this pass

Per this checkpoint's own explicit instruction: a pure-performance finding is documented, not fixed, in this pass unless classified Critical or Important — and a pure-performance finding is "unlikely" to meet that bar by the instruction's own framing. This finding is Moderate. A real fix (e.g. bounding `longest_common_substring_len`'s input length, short-circuiting low-value same-kind comparisons earlier, or restructuring the scoring loop's own complexity) would itself need its own correctness review, its own test suite update (confirming `LineageStatus`/`Confidence` outputs are unchanged for every existing golden-corpus/regression case), and its own before/after remeasurement — real, non-trivial follow-up work, intentionally scoped OUT of this checkpoint and left for a dedicated performance-focused pass to take up, exactly as this checkpoint's own directive anticipates ("recommendation for next step... a dedicated performance checkpoint" is one of the explicitly offered options in this checkpoint's own closing decision).

## Relationship to the prior pass's own `LocalGitRepositorySource::read_file` finding

That finding (git-repository-reopened-per-file-read) remains real, independently confirmed by direct code reading in the prior pass, and is NOT superseded or contradicted by this one — the two are genuinely separate, both-real structural inefficiencies in different parts of the incremental pipeline. This finding's own contribution is ranking them for THIS corpus/commit-pair (`resolve_lineage` costs roughly 10x more than whatever the per-file git-reopen overhead contributes within the same incremental step) and resolving the prior pass's own "not yet fully isolated as THE cause" uncertainty: with proper repeated-run measurement, `resolve_lineage` is now confirmed as the dominant, specific, reproducible cost — not a residual-after-ruling-out-variance guess.
