# B2-ID-010: C# `partial class` fragmentation silently defeats `Extends`/`Implements` base-name resolution

**Severity:** Important.
**Status:** FIXED, tested, mutation-verified, real-corpus remeasured, pending independent review.

**Discovered by:** B2-EVAL-008 (C#/C++ domain multi-codebase
validation), Section C1 (inheritance/interface ground truth), while
investigating why `BulkheadPolicy : Policy, IBulkheadPolicy` — the
evaluation's own headline, protocol-prioritized inheritance example —
produced zero `Extends` edges toward `Policy`. Separated out from
[B2-ID-009](B2-ID-009.md) per explicit instruction: this is a
different mechanism with a different owning resolver, not the same
root cause, and must not be folded into that fix.

## Real-repository reproduction

`App-vNext/Polly`, commit `1f232caf9672e515751ba2df76d82bfbbb62e016`.
`src/Polly/Bulkhead/BulkheadPolicy.cs` declares
`public class BulkheadPolicy : Policy, IBulkheadPolicy`. Ground truth
(ignoring B2-ID-009 entirely — this reproduction holds independent of
that bug, confirmed by re-running after B2-ID-009's own fix landed):

```
extends_implements_edges touching BulkheadPolicy/IBulkheadPolicy/Policy
  (MEASURED, post-B2-ID-009-fix): 2 found
    IBulkheadPolicy -[Implements]-> IBulkheadPolicy   (see note below)
    IBulkheadPolicy -[Implements]-> IsPolicy
```

No `BulkheadPolicy -> Policy` `Extends` edge and no
`BulkheadPolicy -> IBulkheadPolicy` `Implements` edge exist anywhere
in the corpus — the two real relationships this evaluation's own
protocol asked to prioritize are both silently absent.

## Root cause

`Policy` is declared as a C# `partial class`, split across **8
separate files** in this corpus:
`Policy.cs`, `Policy.TResult.cs`, `Policy.HandleSyntax.cs`,
`Policy.ExecuteOverloads.cs`, `Policy.ContextAndKeys.cs`,
`Policy.SyncGenericImplementation.cs`,
`Policy.SyncNonGenericImplementation.cs`,
`Policy.TResult.ExecuteOverloads.cs`. This pipeline's extraction has
no concept of `partial` — each `partial class Policy { ... }`
fragment is extracted as its OWN, independent `SymbolSnapshot`, all
sharing the bare name `"Policy"`. `IBulkheadPolicy` is likewise
declared non-generic and generic (`IBulkheadPolicy`,
`IBulkheadPolicy<TResult>`), both sharing the bare name
`"IBulkheadPolicy"`.

`resolve_extends_implements`'s own base-name lookup
(`crates/codegraph-index/src/edges/extends_implements.rs`) requires
EXACTLY ONE candidate matching a base/interface name to produce an
edge — by explicit, documented design (`candidates.len() != 1` ->
no edge), since inheritance is treated as a 1:1 structural claim that
must never be guessed among ambiguous same-named candidates. This
rule is correct and was not written with `partial class` in mind, but
is defeated BY `partial class`: `BulkheadPolicy`'s lookup for
`"Policy"` finds 8+ matches (one per partial fragment), and its lookup
for `"IBulkheadPolicy"` finds 2 (non-generic + generic variant) — both
counts are `!= 1`, so both edges are silently, deliberately dropped,
exactly as the resolver's own "ambiguous match -> no edge" rule is
supposed to do for a GENUINELY ambiguous name. The defect is not in
that rule's logic; it is that `partial class`/multiple same-named
declarations of the SAME logical type are not actually ambiguous in
the way two unrelated same-named classes in different files are, and
this resolver has no way to tell the two situations apart.

(The one edge that DID resolve, `IBulkheadPolicy -> IsPolicy`,
resolved because `IsPolicy` is declared as a single, non-partial,
non-generic type — its own lookup is genuinely unambiguous. The
`IBulkheadPolicy -> IBulkheadPolicy` self-edge visible in the
post-fix run is the generic variant `IBulkheadPolicy<TResult> :
IBulkheadPolicy` resolving against the non-generic `IBulkheadPolicy`
— both share the bare name `"IBulkheadPolicy"`, so this is the SAME
generic-arity collision mechanism described in a separate note below,
not a new root cause.)

## Scope

Confirmed specific to this evaluation's two headline cases
(`Policy`, `IBulkheadPolicy`), not re-measured across the WHOLE
Polly corpus for every `partial class`/generic-arity-duplicated base
name in this pause-and-report step. `partial class` has no equivalent
in Rust/Python/JS/TS (none of those languages allow splitting one
logical type's declaration across multiple files), so this is
C#-specific, consistent with B2-ID-009's own cross-language audit
conclusion that this domain surfaces real, language-specific
structural gaps not visible in any prior domain.

## Fix implemented (Option B: declaration context extracted once during indexing)

Per explicit user authorization, implemented via a NEW, C#-specific,
non-symbol structural fact — `CSharpTypeDeclarationContext`
(`crates/codegraph-index/src/csharp_declarations.rs`), mirroring the
exact architectural pattern `ImportFact`/`ImplFact` already
established — rather than Option A (passing the full file/tree into
the resolver itself, rejected for breaking the resolver's own
purity and requiring either re-parsing or keeping every `ParseTree`
alive for the whole indexing pass).

Each `class_declaration`/`interface_declaration` is extracted, from
its own file's FULL `ParseTree` (never a single snapshot's isolated
`signature_text` — the namespace information does not exist inside
that span), into a context carrying: canonicalized `namespace`
(handling global/file-scoped/block-scoped/nested-block-scoped forms,
all confirmed by direct grammar probe), `simple_name`,
`generic_arity`, `type_kind` (Class/Interface), and `is_partial` (read
via the grammar's own `modifier` node, never inferred from text).
Resolved against the real snapshot pool by `(file, span)` — never by
name alone, which is the whole point.

`resolve_extends_implements_with_csharp_contexts` (a new function;
the original `resolve_extends_implements` is now a thin compatibility
wrapper calling it with empty contexts, byte-for-byte unchanged for
all ~30 pre-existing call sites) reconciles an ambiguous base-name
lookup into ONE logical target — never merging the underlying
snapshots — only when:

1. the UNION of every context group sharing that bare name exactly
   accounts for every candidate the ambiguous lookup found (no
   leftover, unexplained candidate);
2. exactly one of those groups has `generic_arity == 0` (what a C#
   base clause's own bare name always means — `: Policy` never
   carries `<T>`);
3. that arity-0 group has 2+ members (a group of 1 is not a partial
   split at all — nothing to reconcile, so a bare-name clash against
   an unrelated generic sibling, e.g. `Policy` vs. `Policy<TResult>`,
   correctly stays ambiguous);
4. every member of that group is `is_partial: true` (one non-partial
   member anywhere in the group means these are genuinely distinct
   types that merely share a name — stays ambiguous).

On success, the edge points to the deterministic, lowest-span-start
fragment — a stable, order-independent tie-break, never an arbitrary
pick. Wired into the real production pipeline
(`incremental::pipeline::index_files`,
`incremental::indexer::incremental_reindex`/`full_reindex`) with the
exact same raw-extract/always-reresolve incremental-reuse convention
`raw_import_statements`/`raw_impl_statements` already use.

**Correction during implementation:** an earlier version of this fix
grouped contexts by `(namespace, simple_name)` only, which merged
`Policy` (arity 0, 8 partial fragments) and `Policy<TResult>` (arity
1, 2 partial fragments) — both declared side by side in several of
the same files — into ONE group whose own arity values disagreed,
blocking reconciliation entirely (re-measuring the real Polly corpus
after the first fix attempt still showed ZERO `BulkheadPolicy ->
Policy` edges). Root-caused directly against the real corpus, not
assumed; corrected by grouping on the FULL `(namespace, simple_name,
generic_arity, type_kind)` key, then explicitly checking that the
union of ALL groups for a bare name exactly accounts for the
ambiguous candidate set (point 1 above) before selecting the one
qualifying arity-0 group.

**Tests:** 19 new regression tests (10 in `extends_implements.rs`'s
own `b2_id_010_partial_class_reconciliation` module: same-file split,
cross-file split, the real multi-fragment Polly shape, mixed
partial/non-partial, cross-namespace clash, cross-arity clash, partial
generics, ordinary non-partial duplicates, determinism, identity
non-mutation, no-duplicate-edge; 5 in `incremental::indexer`'s own
`b2_id_010_csharp_partial_class_through_the_real_indexer` module:
full reindex, incremental-advance parity, editing one fragment,
deleting one fragment, no-duplicate-through-the-real-indexer; plus
4 in `csharp_declarations.rs` covering namespace canonicalization
edge cases). Full suite: 459/459 passing, zero regressions.

**Mutation testing** (`cargo mutants`, scoped to
`csharp_declarations.rs` + `extends_implements.rs`): 87 mutants — 74
caught, 10 unviable, 3 confirmed EQUIVALENT (documented inline in the
source: the combined `kind == "partial" && text == "partial"` check
can never diverge because `partial` is a fixed lexical terminal in
the grammar; the `<`/`>` comparisons in the namespace fallback's own
tie-break can never diverge because two distinct AST sibling nodes
can never share the same `start_byte`) — **zero genuine missed
correctness-relevant mutants**.

**Real-corpus before/after** (`App-vNext/Polly`, same repo/commit
pair as B2-ID-009): `extends_implements_edges` 76 -> **103** (+27),
`Extends` edges 54 -> **81** (+27). The headline case itself now
resolves: `BulkheadPolicy -[Extends]-> Policy` (pointing to the
`Policy.ContextAndKeys.cs` fragment, the deterministic lowest-span
representative among `Policy`'s 8 partial fragments), confirmed via
direct re-run of the Section H usefulness Q&A
(`Q1 ... -> Extends: ["src/Polly/Policy.ContextAndKeys.cs::Policy"]`).
7 other real classes extending `Policy` across the corpus
(`TimeoutPolicy`, `RateLimitPolicy`, `CircuitBreakerPolicy`,
`NoOpPolicy`, `FallbackPolicy`, `PolicyWrap`, `CachePolicy`,
`RetryPolicy`, and a couple of test-helper policies) also newly
resolve — none of these relationships were specific to
`BulkheadPolicy`; all were silently dropped by the same mechanism.

**Confirmed still correctly NOT reconciled, by design:**
`BulkheadPolicy -> IBulkheadPolicy` (`Implements`) remains absent —
root-caused directly: `IBulkheadPolicy`/`IBulkheadPolicy<TResult>` are
both declared NON-partial in the real corpus, so this is the
SEPARATE, Moderate generic-arity-collision gap (already documented,
explicitly out of this fix's scope per instruction), not a B2-ID-010
symptom. `snapshots_promoted`/total `Method`/`Class`/`Interface`
counts are unchanged (0 delta — confirms the fix adds edges only,
never touches snapshot identity or count).
