# B2-ID-006: `resolve_calls` attributes call sites to every enclosing container snapshot, not only the nearest real executable caller

**Discovered by:** [B2-EVAL-003](../evaluations/B2-EVAL-003.md) (multi-codebase
validation, Backend/API domain, `nsidnev/fastapi-realworld-example-app`),
during manual validation of a deterministic 30-edge `Calls` sample.
Confirmed general (not Python/Class-specific) by a dedicated follow-up
audit before this finding was written, per explicit user instruction not
to special-case one language/kind without first checking the cross-
`SymbolKind`/cross-language model.

## Discovery context

B2-EVAL-003 is the first multi-codebase validation checkpoint run after
[B2-EVAL-002](../evaluations/B2-EVAL-002.md)'s GO decision, against a
real-repository domain B2's own corpus had never covered before
(backend/API, FastAPI + PostgreSQL + a repository/service-layer
architecture, MIT license). Manually validating a deterministic sample
of `Calls` edges against the real source (`app/db/repositories/comments.py`
at commit `fa56dbac0cdc7014cc51608702e3d370d73249b3`) found a real call
site attributed to TWO different "callers" simultaneously — one correct,
one spurious.

## Observable evidence

**Observed (Measured, real repository, `app/db/repositories/comments.py`
at commit `fa56dbac0cdc7014cc51608702e3d370d73249b3`):** the single real
call `Comment(id_=comment_row["id"], ...)` at line 94, lexically inside
method `CommentsRepository._get_comment_from_db_record` (lines 87-101),
produced two `Calls` edges in the real pipeline's own output:

1. `app/db/repositories/comments.py::_get_comment_from_db_record ->
   app/models/domain/comments.py::Comment` [`StaticAnalysis`] — correct.
2. `app/db/repositories/comments.py::CommentsRepository ->
   app/models/domain/comments.py::Comment` [`StaticAnalysis`] — spurious;
   the class itself never "calls" anything, a call inside one of its
   methods is not a call made by the class.

The same doubled pattern was independently confirmed for
`EntityDoesNotExist` (real call site inside `get_comment_by_id`, same
file).

**Observed (Measured, root-cause confirmation via direct source
reading):** `codegraph-index/src/extract/python.rs`'s `named_by_child_kind`
(used for `class_definition` candidates) sets `signature_text =
node_text(&node, source)` — the ENTIRE class body, including every
nested method's own body — not just the class header/signature line.
Every other language extractor (`cpp.rs`, `csharp.rs`, `javascript.rs`,
`rust.rs`) does the exact same thing for its own container-shaped node
kinds (`class_specifier`/`struct_specifier`, `class_declaration`/
`interface_declaration`, `class_declaration`, `struct_item`/`enum_item`/
`trait_item`): `signature_text` is always the full node span's text,
for every `SymbolKind`, with no distinction between "this node IS an
executable body" and "this node CONTAINS nested executable bodies."

`codegraph-index/src/edges/calls.rs::resolve_calls` iterates over
`lookup.snapshots()` — EVERY snapshot in the given pool, with no
`SymbolKind` filter — and, for each one, re-parses `caller.signature()`
and walks it (`call_sites_in_tree` / `walk_for_calls`) recursively with
**no scope-boundary check at all**: `walk_for_calls` recurses into every
child node unconditionally, so when invoked on a container's full-body
text it necessarily re-discovers every call nested inside every child
method/function too.

**Observed (Measured, minimal synthetic reproduction, no placeholder
bodies, via a throwaway diagnostic harness —
`crates/codegraph-index/examples/b2_id_006_audit.rs`, raw output
preserved at `docs/research/evidence/b2-id-006-contamination-audit.txt`):**

- Python class, one method, one call → 2 edges (`Class->target` spurious,
  `Function->target` correct) — reproduces the real-repository shape
  exactly.
- **Python nested function** (`outer` defines `inner`; only `inner`
  calls `target`) → 2 edges (`outer->target` SPURIOUS, `inner->target`
  correct). **This confirms the root cause is not Class-specific**: a
  plain `Function` snapshot whose own span happens to nest another
  function exhibits the identical duplication.
- **Rust trait with a default method body** (`Greeter::greet` calls
  `helper()`) → 2 edges (`Greeter[Interface]->helper` SPURIOUS,
  `greet->helper` correct). **Confirms the root cause is not
  Python-specific** either.
- Python class, two sibling methods both calling the same target → 3
  edges, not 4: the existing `per_target` per-caller dedup (`calls.rs`,
  documented against B2-ID-002) correctly collapses the class's own TWO
  rediscoveries of the same target into ONE spurious `Class->target`
  edge, and separately leaves each sibling method's own correct edge
  intact. This confirms the dedup mechanism works exactly as designed
  for its own stated purpose (collapsing repeated occurrences within one
  caller), but does nothing to prevent the cross-container duplication,
  since the class and each method are different `from` values to that
  dedup.

**Observed (Measured, full-corpus contamination count, same harness,
`contamination_count` mode, raw output preserved at
`docs/research/evidence/b2-id-006-contamination-audit.txt`):**

| Corpus | Commit | Total `Calls` edges | Container-originated (`Class`/`Struct`/`Interface`/`Enum` as caller) | Confirmed duplicate of a same-file edge to the same target | % of total |
|---|---|---:|---:|---:|---:|
| `nsidnev/fastapi-realworld-example-app` (B2-EVAL-003) | `fa56dbac0cdc7014cc51608702e3d370d73249b3` | 326 | 25 | 17 | 7.7% |
| `pytorch/examples` (B2-EVAL-001/002's own corpus) | `001d493285083b54cacbc1334cb26338bdff2455` | 878 | 256 | 227 | **29.2%** |

"Confirmed duplicate" uses a conservative same-file/same-target/
different-caller pairing test (documented in full, including its own
stated limitation, in the preserved evidence file) — the true spurious
count is this number or higher, never lower, since a container-
originated edge with no same-file pairing partner is still spurious on
its own terms (a class/struct/interface/enum is never a real caller),
just not captured by this particular conservative pairing check.

**Inferred:** this defect is present, in some measure, in every
previously-recorded B2 evaluation that used `resolve_calls` on any
corpus containing classes/structs/interfaces/traits with method bodies
containing calls — which is every real-repository evaluation run so
far ([B2-EVAL-001](../evaluations/B2-EVAL-001.md),
[B2-EVAL-002](../evaluations/B2-EVAL-002.md), and now
[B2-EVAL-003](../evaluations/B2-EVAL-003.md)). It was not detected
earlier because:

1. Every existing unit test exercising this shape (`calls.rs`, e.g. the
   `ClassA`/`forward`/`run` scope-narrowing test) constructs its class
   snapshot with a **literal placeholder body string**
   (`"class ClassA: ..."`), never the real nested source text — so the
   class snapshot's own `signature_text` structurally cannot contain a
   real nested call for `walk_for_calls` to rediscover. Synthetic
   fixtures could not have caught this by construction, independent of
   how thorough their assertions were.
2. B2-EVAL-001/002's manual-sample precision checks (`20/20 correct` on
   the AFTER configuration) validated **target correctness** ("does
   this edge point at the right symbol") on a deterministic sample, but
   never checked **caller-attribution correctness** ("is this snapshot
   a real caller at all") as a separate axis — the evidence-note text
   `calls.rs` emits is identical regardless of which `SymbolKind`
   produced it, so a correct-target, wrong-caller edge reads as
   "correct" under that specific check.
3. B2-EVAL-002's own specific Q3/Q6 answers happen to be insulated from
   this exact corruption, because that harness queries a scope-
   disambiguated MEMBER snapshot directly (`find_current_member_of_class`,
   itself the fix from [B2-ID-003](B2-ID-003.md)) rather than querying
   the class — so those two specific, previously-published answers are
   not themselves falsified. The aggregate edge counts and
   `StaticAnalysis` resolution-method counts those evaluations report
   ARE inflated by this defect, confirmed directly in this finding
   (29.2% of that exact corpus's `Calls` edges are container-originated).

## Root cause

A missing scope/executability invariant in `resolve_calls`: the resolver
treats "is a byte span whose text, when re-parsed, contains a call
expression" as sufficient to be "a caller," when the correct semantic
requirement is "is the NEAREST executable scope enclosing that specific
call site." Any snapshot whose own captured span transitively contains
another snapshot's span — not only `Class` containing `Method`, but
`Function` containing a nested `Function`, or `Interface`/`trait_item`
containing a default method body — will rediscover every call inside
every one of its nested descendants, because:

1. extraction (`extract/*.rs`, every language) always sets
   `signature_text` to the full node-text of the captured span, with no
   distinction between "this node's body IS the executable code" and
   "this node's body CONTAINS other symbols' own executable code"; and
2. `resolve_calls` (`edges/calls.rs`) has no concept of "nearest
   enclosing executable scope" — it treats every given snapshot as an
   independent, self-contained caller candidate and walks its full
   re-parsed body with no boundary at a nested symbol's own span.

This is the same class of defect family as [B2-ID-003](B2-ID-003.md)
(a local-name-only disambiguation rule silently picking an arbitrary
one of several valid candidates) in spirit — both are "the data model
expresses the real nesting/scope structure (byte spans; `Contains`
edges), but a specific resolver does not consult it" — but B2-ID-003
was an evaluation-HARNESS bug, while this is a **production-pipeline**
defect: `resolve_calls` itself, not any throwaway diagnostic tool, is
responsible for the corruption measured here.

## Impact

- **Correctness (`Calls` edge quality):** Important. Confirmed, on two
  real, independently-cloned repositories across two different
  domains and two different languages (Python classes;
  Rust trait default methods, synthetically confirmed but structurally
  certain to occur in any real Rust corpus with default trait method
  bodies), that a meaningful fraction of all `Calls` edges (7.7%-29.2%
  measured so far) have a spurious, non-executable "caller." This
  corrupts: raw `Calls`/`StaticAnalysis` edge counts in every
  real-repository evaluation to date; any "who calls X"
  (`callers_of`/`incoming_edges`) query that does not itself filter by
  caller `SymbolKind`; and graph fan-out measurements the
  Evidence-before-claims Experimental Policy explicitly tracks per
  configuration.
- **Agent usefulness / impact analysis:** a coding agent asking "if I
  change this function, what callers are affected" could be told a
  `Class`/`Struct`/`Interface` "calls" it, which is not an actionable or
  meaningful answer (you cannot "look at the class" the way you can
  look at a specific calling method) and dilutes/confuses a real
  impact-analysis answer with non-actionable noise.
- **Research validity:** the 29.2% contamination figure on
  B2-EVAL-001/002's own corpus means those evaluations' aggregate
  `Calls`/`StaticAnalysis` counts (Section B of both evaluation files)
  need an explicit erratum — not a silent retroactive edit — stating
  that a meaningful fraction of those counts are now known to be
  spurious caller-attribution duplicates, discovered after those
  documents were written and approved.
- **Severity: Important.** Not Critical: it does not corrupt which
  TARGET a call resolves to (every sampled case confirmed the target
  was always correct — this is purely a caller-attribution defect), it
  does not crash or panic, and the two previously-published Q&A answers
  checked in this finding were not themselves falsified. It IS Important
  because it is a real, now-confirmed-general production-code defect
  that inflates every `Calls`-edge-count-based claim made so far by a
  measured, non-trivial amount, and affects any future "who calls X"
  query that does not separately know to exclude container-kind
  callers.

## Solution adopted

**Implemented in the working tree, pending B2-ID-007's resolution
before final closure (see "Status update" above).** See "Proposed fix
design" below for the invariant and design questions as they stood at
approval time, and "Alternatives considered" for what was explicitly
rejected and why.

### Proposed fix design (for approval, not yet implemented)

**Proposed invariant:** a call site must be attributed to the NEAREST
executable enclosing snapshot, not to every ancestor snapshot whose
byte span happens to contain it. Concretely: `resolve_calls` should
only treat a snapshot as a caller-candidate if it represents a scope
whose own body is directly, immediately executable — and, separately,
when walking a caller's own body for nested call sites, it must stop
descending at the boundary of any OTHER known snapshot nested inside
it (so an outer function does not rediscover its own nested function's
calls, and a class does not rediscover its own methods' calls).

This is two distinct mechanisms, not one, and both are needed —
confirmed by the synthetic audit:

1. **Caller-eligibility filter** (fixes the Class/Interface/Struct
   case): a capability predicate on `SymbolKind`, e.g.
   `SymbolKind::is_executable_scope()` or
   `SymbolKind::can_originate_calls()`, used to skip ineligible
   snapshots entirely in `resolve_calls`'s own outer loop. Proposed
   classification, to be confirmed against each language's own real
   AST shapes before implementation (do not assume from the enum names
   alone):
   - **Executable (can originate calls):** `Function`, `Method`.
     (`MethodSignature` has no body by construction — see its own doc
     comment — so it should already produce zero call sites once
     re-parsed; worth an explicit regression test rather than assumed.)
   - **Non-executable container (cannot itself originate calls):**
     `Class`, `Struct`, `Interface`, `Enum`, `Module`.
   - **Needs explicit verification, not assumed either way:** `Const`,
     `Macro`, `Field`. (This finding's own contamination count observed
     6 `Field`-originated `Calls` edges in the backend corpus and 81 in
     the pytorch/examples corpus — not yet root-caused in this finding;
     a `Field`'s `signature_text` is "the whole assignment statement"
     per `extract/python.rs`'s own doc comment, which should normally
     be a single non-nesting statement, but a call expression can
     itself contain nested call expressions as arguments, e.g.
     `self.x = f(g())` — whether THAT shape is "correct" (the field
     assignment genuinely does call both `f` and `g`) or a different
     instance of the same over-broad-span problem needs its own
     dedicated check before this finding's fix touches `Field` at all).
     `HtmlIdElement`/`CssRule`/`CssKeyframes` are already excluded from
     `resolve_calls` via `walk_for_calls`'s own `Language::Html |
     Language::Css => false` branch, so they are not at risk here.
   - **Rust trait default methods specifically:** the synthetic
     reproduction shows the CURRENT extractor classifies a trait's own
     method (e.g. `Greeter::greet`) as `Function`/`Method` (via
     `function_item` inside the `trait_item`) and the TRAIT itself as
     `Interface` — so excluding `Interface` from caller-eligibility
     does fix this specific reproduction. Needs confirmation this holds
     for every trait method shape (default + required, associated
     consts/types mixed in) before relying on it as the general rule.

2. **Nested-scope boundary** (fixes the nested-function case, which
   the eligibility filter ALONE does not fix — `outer` in the synthetic
   reproduction is a legitimate `Function`, so it would still pass an
   eligibility filter, yet it must not rediscover `inner`'s own calls):
   `walk_for_calls` (or a wrapper around it) needs to stop descending
   into a child node's subtree once that child node's own byte span
   exactly matches (or is known to belong to) a DIFFERENT snapshot
   already present in the given pool — i.e., use the same
   `ByteSpan`-nesting fact `resolve_contains` already computes for
   Class→Method, generalized to any nested snapshot-to-snapshot
   relationship, not reinventing a second nesting mechanism.

**Both mechanisms are needed together:** (1) alone does not fix nested
functions (both `outer` and `inner` are legitimately `Function`); (2)
alone does not fix the Class case efficiently without also walking
the class's own body at all (though a sufficiently general (2) that
treats "class contains 3 methods, each with known spans" the same way
as "function contains 1 nested function, with a known span" WOULD
subsume (1) for the Class/Interface cases too — this equivalence
should be checked explicitly during design, since it may mean only
(2) is strictly required and (1) becomes an optimization/clarity layer
rather than a separate necessary fix. Not decided here — flagged as the
central open design question for approval.

### Open questions — resolved during implementation

- **Both mechanisms were kept, not collapsed into one.** The
  eligibility predicate (`SymbolKind::can_originate_calls`) skips
  ineligible callers before ever re-parsing their body (cheaper, and a
  clearer, independently testable statement of intent); the nested-
  scope boundary (`call_site_belongs_to_a_more_nested_caller`) is still
  required separately, since a `Function` nested inside another
  `Function` passes the eligibility predicate but still needs the span-
  boundary check to avoid the outer one rediscovering the inner one's
  calls.
- **`Field`/`Const`/`Macro` classification — resolved, not merely
  assumed:** confirmed by direct source reading
  (`extract/python.rs`'s own doc comment) that a `Field`
  (`self.X = <rhs>`) can only ever occur inside a method body (`self`
  is only bound as a parameter inside one) — so a `Field` snapshot's
  own span is ALWAYS nested inside its enclosing `Function`/`Method`.
  Confirmed empirically via the synthetic audit (`self.x = f(g())`
  inside `__init__`, itself inside class `M`): treating `Field` as
  caller-eligible would have reproduced the EXACT same defect one
  level deeper (3-way duplication: `M`, `__init__`, AND `x` all
  independently rediscovering `f`/`g`). `Field` is therefore `false` in
  `can_originate_calls`. `Const`/`Macro` remain `false` and
  undecided-pending-real-data, since neither is produced by any
  current extractor (confirmed exhaustively against
  `snapshot::kind_mapping::map_kind_hint`'s own real mapping table) —
  there is no real `SymbolSnapshot` of either kind for this predicate
  to be exercised against today, so deciding `true` for either would
  be exactly the "intuition, not evidence" classification the
  instruction explicitly forbade.
- **API surface:** no breaking change was needed. `SymbolSnapshot::span()`
  was already public (added for `resolve_contains`'s own use); the
  fix added one new field to the resolver-internal `CallSite` struct
  (`fragment_relative_start_byte`) and two new, non-public helper
  functions in `calls.rs` — no public API of any crate changed shape.

## Alternatives considered

### A. `if kind == SymbolKind::Class { skip }` (explicitly rejected, per
### instruction)

Fixes only the exact shape this finding started from. Confirmed
insufficient by this finding's own synthetic audit: the nested-function
case shows the real root cause is span-nesting generally, not
Class-as-a-kind specifically; a Class-only special case would leave the
nested-function duplication and the Rust-trait duplication completely
unfixed, and would need ad hoc extension for every future container-
shaped `SymbolKind` (Struct, Interface, Enum, Module, and any future
addition) discovered the same way, one real-repository surprise at a
time.

### B. Fix only at the extraction layer (never let a container's
### `signature_text` include nested bodies)

Would also prevent this specific symptom, but changes what
`signature_text` means for every existing caller of `promote`/
`SymbolSnapshot` across the whole codebase (e.g. would a `Class`
snapshot's own signature then just be its header line? What happens to
any OTHER resolver or future feature that currently relies on a class's
full body being present in its own signature text, if any exists?) —
a much larger-blast-radius change than fixing the ATTRIBUTION step in
`resolve_calls` specifically, which only needs to change HOW calls are
walked/attributed, not WHAT text extraction captures for other
purposes. Not chosen as the primary design direction in this finding,
but not conclusively ruled out either — recorded as a real alternative
for the approver to weigh, since it might be the more foundational fix
if nothing else legitimately depends on a container's full-body
signature text today (not yet checked).

### C. Do nothing; document as a known limitation (rejected)

Rejected because the measured magnitude (up to 29.2% of all `Calls`
edges in a real, already-published evaluation's own corpus) is too
large to leave undocumented-as-a-defect; "known limitation" framing
would understate a measured, confirmed, cross-language correctness
defect as if it were an inherent, irreducible property of static
analysis, when a concrete, scoped fix is identified and only pending
design approval, not technically infeasible.

## Literature / authoritative evidence

No single paper specific to THIS implementation pattern (container-
signature-text re-parsing causing call-site double-attribution) was
identified as genuinely on-point, and none is forced here as a
citation of convenience. The underlying principle it violates — that a
name/relationship's correct owner is determined by lexical/semantic
scope structure, not by arbitrary AST ancestor containment — has real
literature support, cited here as general SUPPORT for the principle,
not as prescribing this project's own specific fix mechanism (see
[B2-ID-007](B2-ID-007.md) for the fuller citation and the same
caveat):

- Néron, P., Tolmach, A., Visser, E., & Wachsmuth, G. (2015). *A Theory
  of Name Resolution*. ESOP 2015, LNCS 9032. Scope graphs model
  lexical nesting as an explicit relation between scopes, not as raw
  source-span containment — directly supports attributing a call site
  to its nearest enclosing EXECUTABLE scope via an explicit boundary
  check (this finding's own mechanism 2), rather than assuming every
  ancestor span is an equally valid owner.
