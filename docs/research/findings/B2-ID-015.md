# B2-ID-015: `Ctor.prototype.X = function(){...}` (ES5 prototype-method idiom) is never extracted as a candidate

**Severity:** Moderate (coverage gap, not correctness). Confirmed
honest silent drop at large magnitude — zero false edges — not a
wrong-answer defect.
**Status:** FIXED (CommonJS Extraction Checkpoint), with one documented
residual limitation. `extract/javascript.rs`'s
`commonjs_property_function_assignment` now recognizes
`Foo.prototype.X = function(){...}` (new synthetic `kind_hint`
`js_prototype_method_assignment` → `SymbolKind::Method`). A new
resolver, `edges::js_prototype_ownership::resolve_js_prototype_ownership`,
re-parses each candidate's own `signature_text` to recover the owner
name (`Foo`) and produces a `Contains` edge from `Foo`'s own real,
same-file `Function`/`Class` snapshot — FAIL-CLOSED (no edge invented)
when the owner is ambiguous, cross-file, or not a real Function/Class
at all (confirmed on the real require()-aliased-owner shape). Wired
into `resolve_all_typed_edges_with_csharp_contexts_and_negative_knowledge`
(the real production entry point), so it is live on both full and
incremental paths — confirmed via a dedicated full/incremental
equivalence test on real-shaped data.

**Real-corpus remeasurement on `request/request`: 24/27 (89%) of
`Request.prototype.X` methods now visible AND correctly owned (24/24
of the visible ones, 100%).** The remaining 3 (`init`, `start`,
`onRequestResponse`) are rejected by this pipeline's own pre-existing,
unrelated `SignatureTooLong` bound (`MAX_SIGNATURE_BYTES = 4096`) —
confirmed these three are real, unusually long method bodies (`init`
alone spans ~443 lines), not a defect in this checkpoint's own fix.
Mutation testing: 0 genuine missed after one fixed gap (an `&&`→`||`
mutant on the literal-"prototype"-text check, closed with a dedicated
regression test).

**Discovered by:** B2-EVAL-010 (JavaScript/CommonJS domain standalone
evaluation, `request/request`@`3c0cddc7c8eb60b470e9519da85896ed7ee0081e`).

## The gap

The existing JavaScript/TypeScript extractor has no rule recognizing
the ES5 "class via prototype" idiom — `Ctor.prototype.methodName =
function(...) {...}` — as a method declaration. This is the same
root-cause family as B2-ID-014 (property-assignment-to-function-expression
is invisible to the extractor), but at much larger magnitude: in
`request.js`, the real `Request` "class" is defined entirely through
this idiom (a constructor function plus a long series of
`Request.prototype.X = function(){...}` assignments), not through
`class`/`function_declaration` syntax the extractor already handles.

**Confirmed measurement: 27 real `Request.prototype.X =
function(){...}` declarations in `request.js`; 27/27 (100%) produce
zero extracted snapshots.** This corpus's single most structurally
important type has zero extracted method surface.

## Effect measured

`false_edge_count = 0` across all 27 — confirmed exhaustively, not
sampled: no call site anywhere in the corpus was found to resolve to
an incorrect target as a side effect of this gap. The failure mode is
consistently an honest silent drop (total absence, not a wrong
answer), consistent with every other finding in this evaluation round.
Any internal call from one `Request.prototype` method to another, or
any external call into one of these 27 methods, is invisible to the
Calls graph by the same mechanism as B2-ID-014's smaller-scale case.

## Fix (CommonJS Extraction Checkpoint)

Extraction: `commonjs_property_function_assignment` recognizes the
construct (see B2-ID-014's own updated status for the shared mechanism
and `is_prototype_receiver`'s exact `Identifier.prototype` shape
check). Ownership: `js_prototype_ownership.rs`'s own resolver re-parses
the candidate's full `signature_text` (deliberately captured as the
WHOLE assignment, not just the RHS function, exactly so this
resolution step can recover the LHS receiver later), resolves `Foo` by
exact name among same-file `Function | Class` candidates, and produces
no edge unless exactly one match exists. Reuses `EdgeKind::Contains`
(no new edge kind) since the semantic claim — "this constructor owns
this method" — is identical to the existing Class-contains-Method
relation, just resolved by name across sibling statements instead of
by AST span-nesting (span-nesting is structurally inapplicable here:
the method's body is a sibling statement, never nested inside the
constructor function's own span).

## Residual limitation

The 3 real methods rejected by `SignatureTooLong` (`init`/`start`/
`onRequestResponse`) remain invisible — not from this finding's own
root cause, but from a separate, pre-existing, unrelated extraction
bound this checkpoint did not touch (the same `MAX_SIGNATURE_BYTES`
limit that already affects long methods in other languages, e.g.
Polly's own C# findings). Not reopened as a new finding; documented
here for completeness.
