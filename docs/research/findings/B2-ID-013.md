# B2-ID-013: `require(...)` call sites never produce an `ImportFact`

**Severity:** Moderate (coverage gap, not correctness). No wrong edge
or wrong resolution results from this — the gap is a total absence of
data, not a misleading one.
**Status:** FIXED (CommonJS Extraction Checkpoint). `imports.rs` gained
`collect_js_require`, recognizing `require(...)` as the RHS of a
`variable_declarator` (simple binding, aliased binding, destructured
binding — one `ImportFact` per destructured name, mirroring Python's
own `from X import a, b` convention). Real-corpus remeasurement on
`request/request`: 0 → 48 ImportFacts (all `External` — a require()
alias binding's own bare name does not itself match a single real
exported symbol name, an honest, expected limitation shared with every
other language's bare-module-alias case, not a new one). Mutation
testing: 0 genuine missed (30 mutants across the diff, 4 unviable).
End-to-end golden corpus tests added
(`b2_id_013_require_simple_aliased_and_destructured_bindings_all_produce_import_facts`,
`b2_id_013_require_alias_binding_itself_resolves_external_not_internal`).

**Discovered by:** B2-EVAL-010 (JavaScript/CommonJS domain standalone
evaluation, `request/request`@`3c0cddc7c8eb60b470e9519da85896ed7ee0081e`).

## The gap

`imports.rs`'s `collect_js_import` only matches `import_statement`
nodes (ESM `import ... from '...'` syntax). It has no handling at all
for `require(...)` call expressions — confirmed by direct source
read, not inferred from behavior. On the real `request` corpus, this
means all 61 real `require()` call sites (15 relative-path, 46
package/external) produce **zero `ImportFact`s**, regardless of
corpus content.

This is structurally distinct from a corpus-specific miss: CALL-RES-A4's
import-alias resolution mechanism has literally no CommonJS data to
consult, on any CommonJS codebase, by construction — analogous in
shape to the C++ `#include`-is-a-no-op gap documented in B2-EVAL-009,
but with a different root cause (missing extraction logic, not a
deliberate scope exclusion).

## Effect measured

A `require()`-then-property-access pattern (e.g. `var helpers =
require('./helpers'); helpers.foo()`) falls back to plain
name-based heuristic/ambiguous resolution, identical to pre-CALL-RES-A4
behavior. No false edges were produced as a result (confirmed via the
zero-false-positive findings across this evaluation's own sampling),
but none of A4's import-alias precision gain is available for
CommonJS code either.

## Fix (CommonJS Extraction Checkpoint)

`collect_js_require` added to `imports.rs`, wired into `walk_for_imports`
alongside the existing `collect_js_import`. Recognizes exactly
`require(<string>)` (callee is the bare `identifier` "require", never
a member-expression call like `foo.require(...)`) as the direct RHS of
a `variable_declarator`. Deliberately narrow, per this checkpoint's
own scope: a bare `require('./x');` with no binding, or `require(...)`
nested inside another call, produces no fact — both confirmed by
dedicated tests.
