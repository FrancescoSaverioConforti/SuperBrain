# B1 — Deterministic Search (trigrams, BM25, citations, time filters)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the vault a deterministic retrieval path — exact-match (trigram) and ranked (BM25) search over committed note content, with correct citations, project/type/status/trust/date filters, and the C4 time-range contract — exposed through a new `index` crate and the `api` crate's `search`/`retrieve`. No embeddings, no tree-sitter, no code graph: those are B2/B3. No generative model: that is Fase D. This plan closes the spec's Fase B item 2 (trigram+BM25 baseline), item 5 (partial: `search`/`retrieve` only, `graph_query`/`get_code_context` are B2), item 6 (partial: the `eval/rag/` split exists but B3 freezes thresholds and runs the final benchmark), and the "Ricerca per periodo" section (C4 time modes).

**Explicit non-goals (do not implement, do not design beyond the integration seam):** tree-sitter parsing, the code graph (`symbol_snapshot_id`/`symbol_lineage_id`), `graph_query`, `get_code_context`, incremental reindexing by commit hash for code symbols, embeddings, the MCP server transport, B3's frozen-threshold benchmark run. Where B1's design must leave a seam for these (e.g. the `index` crate's module boundary, the `api` crate's operation list), the seam is named but not built.

**Architecture:** A new `index` crate (`domain`, `storage` -> `index`, matching the spec's crate table) owns two independent structures over committed note content — a trigram postings index for exact substring/identifier search, and a BM25 postings index for ranked search — plus the C4 date-resolution function and the citation/filter logic that both indexes feed into through one `index::Index` facade. A new `api` crate (`index` plus everything beneath it -> `api`) exposes `search` and `retrieve` as plain Rust functions (no transport yet — the spec's MCP/REST surface is explicitly "trasporto" only and is not this plan's concern; B1 ships the callable core the transport will later wrap).

**The hard integration problem this plan must solve, stated up front:** `storage::Vault`'s write pipeline already has an `Indexer` trait hook (`crates/storage/src/vault.rs`, `pub(crate) trait Indexer { fn mark_current(&self, note_id: &str, version: u64); fn state_for(&self, note_id: &str) -> IndexState; }`), called synchronously from inside the per-note write lock right after `GitCommitted`, with `NullIndexer` as the only implementation today. `index` cannot depend on `storage`'s *internals* (`Journal` is `pub(crate)`, not walkable from outside the crate) — it can only reach committed note content through `Vault`'s existing public read API (`read_note`, `current_version`) or a full-root directory walk plus `Vault::read_note` per id. This plan's Task 1 is deciding and documenting exactly how `index` plugs into that seam without `index` depending on `storage`'s private state and without `storage` depending on `index`'s concrete type (the dependency arrow in the spec's crate table is one-directional: `storage` does not depend on `index`). Two sub-problems fall out of this:

1. **Incremental update on write — resolved (consolidation round, 2026-10-30): no callback, ever.** Re-reading `write_record_unchecked`'s actual body (`crates/storage/src/vault.rs:924-1109`) rather than inferring from the trait signature alone: by the time step 7b calls `self.mark_index_current(note_id, operation_id, new_version)` (line 1105), the function already holds, as local variables in scope, `buffer` (the exact serialized record bytes just written and hash-verified on disk at line 1048/1062-1063) and `new_version` (line 1026) — both computed *before* `GitCommitted`, both still under the one `_guard` (`note_lock`, acquired at line 963, held through line 1107's documented drop point). There is no missing data that would require a second read: `Indexer::mark_current`'s signature must change from `(&str, u64)` to carry the already-in-hand committed bytes directly (e.g. `(&str, u64, &[u8])`, or a small `IndexableRecord` struct built from `buffer`/`new_version`/the already-parsed `NoteMetadata`), and the call site passes what it already has. This eliminates the deadlock question entirely rather than merely proving it exists and routing around it: the real indexer's `mark_current` never calls `Vault::read_note`, so there is no second lock acquisition on the write path to reason about at all. Version ordering is trivial by construction — the per-note lock already serializes every write to a given note id, so `mark_current` calls for the same note id arrive in strictly increasing `new_version` order, one at a time, never concurrently. Task 1 must still decide and pin: (a) the exact enriched signature and what `index` builds from it (parse `NoteMetadata` once, inside `mark_current`, from the bytes it's handed — never re-parsing twice if `write_record_unchecked` already parsed; check whether reusing the already-parsed `NoteMetadata` from earlier in the function, rather than re-parsing the buffer, is feasible without further signature changes); (b) what happens if the real indexer's in-process update (tokenizing, inserting into the trigram/BM25 postings) itself fails *after* receiving the bytes — this is a pure in-memory operation with no I/O, so "failure" here means a logic bug or an allocation failure, not a transient I/O error, but the contract must still be: `mark_current` must not panic and must not propagate an error through `write_record_unchecked` (the spec's own rule that `index_current` is never claimed when the index is behind, combined with B1 consegna 4's "reindicizzazione incrementale," means an indexing failure degrades `state_for` to `Stale` for that note and leaves a gap a background rebuild closes, never a write failure).
2. **Cold start / full rebuild:** `index` has no event log of its own and `storage::Journal` is private, so a from-scratch index build cannot "replay history" — it can only enumerate every current note id (by walking the vault root for `*.record` files, or via a new small public listing function this plan adds to `storage` if a directory walk is judged unsafe/insufficient — Task 1 decides which) and call `Vault::read_note` once per id. This must be safe against the vault being written to concurrently (an in-progress write is invisible until its own `JournalCommitted`, so a racing read sees either the old or new committed version, never a partial one — `read_note` already guarantees this) and must tolerate `StorageError::Deleted`/`NoteDeleted` (a deleted note's id must never be enumerated into the index — Task 1 must specify how the rebuild walk filters these out, since the deletion log lives beside the `PiiStore` and a non-PII vault may have no deletion log to consult at all). The rebuild path is the *only* place `index` calls `Vault::read_note` directly (never from inside `mark_current` — see point 1) — and that call is always made outside any write's per-note lock (the rebuild walk runs either at startup, before any writer exists yet for a given note, or racing an in-flight write that the per-note lock already serializes against `read_note` itself), so no new deadlock risk is introduced by the rebuild path either.

**Consistency invariant this plan must state explicitly (consolidation round, point 2): a search result is never served as a read until it has passed through `Vault::read_note`'s existing gates.** `storage::vault::read_note` (line 705) already enforces, on *every* call regardless of `IndexState`: (a) the deletion-log check via `refuse_read_if_deleted` (line 709/1768), run unconditionally — a deleted note is `StorageError::Deleted`/`NoteDeleted` whether or not any index entry for it still exists or is stale; (b) the content-hash check against the journal's committed row (`read_note_locked`, line 717-744) — a corrupted or mismatched record is `StorageError::Inconsistent`, never silently served. This means `index`'s own postings (trigram/BM25) are allowed to be stale or to still reference a since-deleted note's id *in memory* — that staleness is bounded and made harmless by construction, not by a new invariant this plan must separately enforce, **provided** `index::Index::search` and `api::retrieve` never serve a result's content/excerpt from the index's own cached copy without re-confirming it through `Vault::read_note` (or, for a snippet/excerpt shown in a `SearchResponse`, by re-deriving the excerpt from a freshly re-read record, not from a postings-time-cached string) before returning it to a caller. Task 6/Task 7 must make this the literal last step of both operations: resolve candidate note ids from the index, then call `Vault::read_note` per candidate as the authoritative content source, silently dropping (not erroring) any candidate that comes back `Deleted`/`NotFound`/`Inconsistent` — a deleted note simply has no result, exactly as if it were never indexed. The relationship between `state_for`'s `IndexState` and this gate is one of *completeness*, not *correctness*: `Stale` means a recently-written or recently-deleted note might be missing from or lingering in the index's candidate set a little longer than ideal, but it can never mean a wrong or forbidden result is actually returned, because the final `read_note` gate is classification/deletion-state-blind to how the candidate was found. Task 3's fault-injection test (Step 2) and a new Task 6 test must together cover: a note deleted after being indexed is never in a search response's results (the candidate surfaces, `read_note` rejects it, the response silently omits it); a note's content changed after being indexed still returns the *current* committed version's excerpt (never the stale indexed-time snippet), proven with a test that indexes v1, updates to v2, searches, and asserts the excerpt matches v2's content byte-for-byte, not v1's.

**Security boundary this plan must not weaken ([n2io], the open Continuity item from A3):** A3's evidence file explicitly deferred the index/embedding/cache confidentiality audit (5 of C3's 10 surfaces) because no such subsystem existed yet. It now does. Every test A3 wrote for "no `sensitive` content in git/journal/before-images/logs/backups" needs a sibling test here for "no `sensitive` content in the trigram postings, the BM25 postings, or any index-build log line" — a `Sensitive` note's *pointer* (`pii://<note_id>` plus gate-accepted frontmatter) is indexable exactly like any other note's frontmatter (project, type, status, trust, dates — none of that is secret), but its *body* must never reach the index, because the body is never in the Markdown record `read_note` returns for a sensitive note in the first place: `storage::propose.rs`'s own doc comments (the `Sensitive` write branch, describing the record it builds) document that the record body is literally `pii://<note_id>`, independent of deletion state — this is the stronger, more precise source for the universal claim than A3 §5's deletion-specific line (which only establishes the pointer-only behavior for a *deleted* sensitive note). This plan's job is to confirm that non-deleted sensitive notes behave the same way (pointer only, never plaintext, through the exact same `read_note` call the indexer uses) and add a dedicated adversarial test proving it, not to design new confidentiality machinery. `Secret` classification never reaches storage at all (A1/A3), so it is a non-issue for indexing by construction.

**Indexable-metadata allowlist for `Sensitive` notes (consolidation round, point 4; corrected after targeted review found it non-exhaustive, then corrected again in the second consolidation round to distinguish two different things "indexed" had been conflating) — an explicit enumeration against every actual `NoteMetadata` field, not "frontmatter is safe by definition."** C3 classifies by *surface*, not by field name, and a field being frontmatter rather than body does not make it automatically indexable. `crates/domain/src/note.rs`'s `NoteMetadata` has exactly twelve fields: `id, schema_version, r#type, status, trust, classification, project, source, created, updated, event_period, relations`. The allowlist must dispose of every one of them explicitly, not just the ones that were top-of-mind when first drafted (the targeted review's Finding 1: the first version of this paragraph silently dropped `schema_version` and `classification`).

**"Indexed" is not one category — `Document` (Task 2) keeps two distinct kinds of data, and the allowlist's exclusion applies to only one of them:**

- **Structured metadata** — typed values `Document` retains for exact filter matching, sorting, and response display, consulted directly rather than through a trigram/BM25 term search. For a `Sensitive` note, ALL TEN of these are retained, with no restriction: `id`, `type`, `status`, `trust`, `project`, `created`, `updated`, `event_period`, `schema_version`, `classification`. None carries free-text confidentiality risk, and every one is load-bearing for `search`'s own filters (`type_filter`/`status_filter`/`trust_filter`/`date_filter`/`ProjectScope`) and for `classification`-aware logic (including the very gating this allowlist describes) to work for every note regardless of its own classification — excluding any of them would silently break a filter for an entire classification.
- **Text-searchable content** — what actually gets tokenized into `TrigramIndex`/`Bm25Index`'s postings, where a query term can match. For a `Sensitive` note this is restricted to the STRING FORMS of the ten structured fields above ONLY, and explicitly excludes: the body, `source` (schema example values like `agent:coder@prompt-v3` are free text that could carry an identifying detail depending on what an agent/user puts there — C3's "anche i metadati" clause names this exact risk class, and unlike the ten structured fields, `source`'s content is not a closed enum/date/id — it is actual free text, which is why it is excluded from text search despite being, like the others, a plain frontmatter string), and every `relations.*` target (a relation target is a `NoteId` string chosen by whoever wrote the note — low risk today given `NoteId`'s restrictive syntax, but not allowlisted for text search without a dedicated test proving no identifying text can be smuggled through a target, which this plan does not write).

For `Internal`/`Public` notes there is no restriction on either category: the body, `source`, and `relations` are all text-searchable exactly as the ten structured fields are — only `Sensitive` classification narrows what's *text-searchable*, never what's retained as *structured metadata*.

Task 2's `Document` constructor must implement exactly this two-category split (see Task 2's own restatement for the binding detail), and Task 4's confidentiality audit (Step 1) must enumerate all twelve `NoteMetadata` fields explicitly by name against this disposition and test that `source` and `relations` specifically do not leak into any TEXT-SEARCH index surface — not just that the body doesn't, and not implying either field must be absent from `Document`'s structured-metadata side or from a direct `retrieve` (see the next paragraph).

**This allowlist governs the SEARCH/INDEX surface only, not `retrieve` (targeted review Finding 3 — stated explicitly here to close a gap the first consolidation left implicit).** `api::retrieve` on a note id the caller already has permission to read is a direct, authorized read of that note's existing record — not a surface this plan's confidentiality concern is about. `source` (and `relations`) being excluded from what `TrigramIndex`/`Bm25Index` can be searched by does NOT mean `RetrieveResponse` must redact them: `storage::propose.rs`'s own doc comments confirm a `Sensitive` note's pointer record keeps its full frontmatter (only the body becomes a `pii://` pointer), so `Vault::read_note` already returns `source`/`relations` as part of that frontmatter today, independent of B1. `api::retrieve`'s response may legitimately surface `source` as provenance, exactly as it does for `Internal`/`Public` notes; Task 7 does not need to add redaction logic. Task 4's Step 2b test (`source` must not leak) is scoped to the search/index surfaces and the `SearchResponse` shape only — it must NOT be read as requiring `RetrieveResponse` to omit `source`, and Task 4/Task 7 must say so in their own text, not leave readers to infer it.

**Tech Stack:** Pure Rust, no new external search/IR crate — the spec's own acceptance bar is a from-scratch deterministic baseline ("Fase B deve passare con la sola baseline deterministica"), and a hand-rolled trigram index plus a textbook BM25 implementation keep the dependency surface identical to A1-A3's SPDX-allowlist discipline with zero new entries to vet. `chrono` or `time` (whichever A1-A3 already pulled transitively, else `time` — smaller, already MIT/Apache-2.0) for C4's calendar-month/ISO-week arithmetic and `Europe/Rome` timezone handling; this is the one new dependency this plan may need, checked against `cargo deny` before being added, same discipline as every A3 addition.

**Spec:** `docs/Spec_mvp.md` — Fase B consegne 1 (deferred to B2 except the crate-boundary seam), 2 (trigram+BM25 baseline, this plan's core), 5 (partial: `search`/`retrieve`), 6 (partial: `eval/rag/` split exists, thresholds frozen in B3); "Ricerca per periodo" section (C4); contratto C4 (date resolution) and contratto C6 (link states, already implemented in `domain::classify_links` — B1 only *reads* `LinkState`/`Pending` for citation display, does not change link validation).

## Review Focus

- **The `Indexer` trait seam (Task 1) is the single highest-risk design decision in this plan** — get the crate-boundary wrong and either `storage` ends up depending on `index` (breaking the spec's one-directional crate table) or `index` ends up reaching into `storage` internals (breaking the journal's privacy boundary A1-A3 built). Pin the exact signatures, the exact lock-scope guarantees at the call site, and the exact cold-start enumeration mechanism before any indexing logic is written — a plan that writes BM25 math first and "wires it up" last has already made this decision by accident, probably wrong.
- **Indexing must never be able to fail a write, and must never silently claim `index_current` when it hasn't actually indexed the committed content** (spec: "l'indice... non viene mai dichiarato corrente se è indietro"). A naive implementation that calls `mark_current` unconditionally regardless of whether the real indexing work (tokenizing, inserting into the trigram/BM25 postings) actually succeeded would violate this exactly like A2's `GitPending` distinction protects against a premature "committed" claim. Task 2/Task 3 must pin the failure path: indexing error -> `state_for` keeps reporting `Stale` for that note -> a background/retriable rebuild closes the gap -> no error surfaces to the `propose_and_commit` caller.
- **A `Sensitive` note's body must never reach either postings index, proven by a dedicated adversarial test, not inferred from `read_note`'s existing contract.** Write a test that stages a sensitive note with an extremely distinctive body string, indexes the vault, and asserts a search for that exact string returns zero hits — not just "the frontmatter indexes fine," which proves nothing about whether the body leaked.
- **Project scoping is a filter the `search` operation applies, not a property the index itself encodes exclusively** — the spec's own line ("a meno di una richiesta esplicita di consultare quel progetto, che il sistema rende visibile") requires an *explicit opt-in* to cross-project search that is visible in the response, which means the index must still be *able* to return cross-project hits when asked, and the "active project" default-exclusion logic belongs in `api::search`/`index::Index::search`, not baked into what gets indexed in the first place. A design that indexes only the active project's notes would make the explicit-opt-in requirement impossible to satisfy later without a reindex.
- **C4's date resolution (Task 5) is a pure function with zero ambiguity in its own test suite** — every test bullet in the spec's C4 table (end of month, year omitted, year rollover, leap year, DST transition on 2026-10-25, inclusive/exclusive boundaries) is a named test case with the reference date as an explicit parameter, not a property inferred from a chrono/time library's default behavior. Verify the DST test actually exercises `Europe/Rome`'s real transition, not UTC math that happens to look right.
- **Citation correctness (Task 6) means "the result actually contains what was searched for," not "the result is topically related"** (spec: "un risultato è corretto solo se contiene davvero l'elemento cercato, non se parla dello stesso tema") — this is a precision bar on the retrieval layer itself (exact substring/identifier match for trigram results is correct by construction; BM25's ranked results need the returned excerpt to be checked against the query terms, not just ranked and returned). Task 6/Task 7 must write tests that would fail a topically-similar-but-non-matching result, not just tests that confirm an exact match ranks first.

## Task 6: `search` — filters, project scoping, and citation construction

**Files:**
- New: `crates/index/src/search.rs`.

**Interfaces:**
- Consumes: `TrigramIndex`, `Bm25Index`, `time_range::resolve_time_expression`, `Document` (for filter fields: project, type, status, trust, classification), `storage::Vault::read_note` (the mandatory final resolution step — see below).
- Produces: `Index::search(query: &str, filters: SearchFilters, k: usize) -> SearchResponse` where `SearchFilters` includes `project: ProjectScope` (`ActiveOnly` default / `Explicit(project_id)`, satisfying the spec's opt-in-and-visible requirement), `type_filter`, `status_filter`, `trust_filter`, `date_filter: Option<(TimeField, TimeExpression)>` (`TimeField` = `created_at`/`updated_at`/`event_period`/`any`, per the spec's explicit-mode requirement), and `SearchResponse` carries, per result: note id, excerpt, score, provenance (trust/classification/project/source), and — critically — whatever flag or field makes the active-project exclusion *visible* when it applied (spec: "il cambio di contesto viene mostrato").

**Mandatory resolution discipline — re-reading is necessary but not sufficient (consolidation round, point 2; strengthened per second consolidation round, 2026-10-30, after the user flagged that a fresh `read_note` call alone does not prove the result still matches the query).** `Index::search` resolves candidates from `TrigramIndex`/`Bm25Index` first, then — before building any `SearchResponse` entry — calls `Vault::read_note` for every surviving candidate and performs a **full re-validation against the current committed version**, not merely a re-read used to decorate an excerpt:

1. **Re-derive the candidate's `Document` from the freshly-read `VaultRecord`** (same construction Task 2 uses at index time, including the `Sensitive`-classification allowlist from the Architecture section applied to the record's *current* classification, never the classification cached on the stale candidate/`Document` from index time — this is the same point Task 6 Step 7's review bullet already requires for the reclassification case, now generalized to every field, not only classification).
2. **Re-run the query match against this freshly-derived `Document`'s indexable fields** — re-check the trigram/BM25 term match against whatever text is actually indexable for the record's *current* classification and content, not against the stale postings-time match that surfaced the candidate. If the current version no longer contains the matched terms (content changed, or classification narrowed what's searchable), the candidate is excluded, full stop — it is not demoted, not returned with a note, simply absent from the response, identical to never having been indexed.
3. **Re-apply every active filter** (`type_filter`, `status_filter`, `trust_filter`, `date_filter`, `ProjectScope`) against the freshly-derived `Document`'s current field values. A candidate that passed a filter at index time but whose current version no longer satisfies it (reclassified, reprojected, date fields changed) is excluded by the same rule as step 2.
4. **Re-compute the score from the current content**, never reuse or re-present the postings-time score as if it reflects the current version — a stale score presented against current content would misrepresent what was actually matched.
5. A candidate whose `read_note` call itself returns `Deleted`/`NotFound`/`Inconsistent` is excluded before steps 1-4 even run (unchanged from the first consolidation round).

This is the mechanism, not an optional hardening pass, that keeps a `Stale` `IndexState` from ever producing a wrong, obsolete, or forbidden result; see the Architecture section's consistency-invariant paragraph. `Stale` still means **incompleteness** (a result the current index hasn't caught up to yet may be briefly missing), never **incorrectness** (nothing re-validated against stale state is ever returned) — this distinction stays explicit in the response: there is no field anywhere claiming "fully current," only the absence of any result this re-validation would have rejected.
