# B2-ID-008 fix: `ImplFact` — Rust `impl` blocks as a structural fact, not a symbol

**Spec:** [docs/research/findings/B2-ID-008.md](../../research/findings/B2-ID-008.md)
(the finding, including corpus evidence, grammar probe, and the 4
design alternatives) is the binding spec for this plan. The user's own
explicit design-decision message (not separately filed, but summarized
in [[d114xk]] in Continuity) approved **Option B** specifically:
`ImplFact` as a non-symbol structural fact, reusing the already-
precedented `ImportFact` pattern (`crates/codegraph-index/src/imports.rs`,
from [B2-ID-005](../../research/findings/B2-ID-005.md)). **Option A
(`SymbolKind::ImplBlock`) is explicitly rejected for now** — not
implemented, kept as a documented future option.

## Context for implementers (read this, not just the task brief)

This project (SuperBrain / B2 Code Graph) builds a real, production
Rust pipeline that parses source code (via tree-sitter) across 9
languages and builds a typed graph of symbols (`SymbolSnapshot`) and
edges (`Edge`) between them — `Calls`, `Contains`, `Extends`/
`Implements`, `Instantiates`, `TestsFor`. [B2-ID-008](../../research/findings/B2-ID-008.md)
found that Rust's `impl` blocks are NEVER extracted as symbols at all
(`extract/rust.rs` only recognizes `struct_item`/`enum_item`/
`trait_item`/`function_item`/`function_signature_item`), so
`resolve_extends_implements`'s own Rust-specific logic
(`collect_rust_impl_trait` in `edges/extends_implements.rs`) is
structurally unreachable — it is correct code that can never actually
run against real Rust source, because nothing ever gives it an
`impl_item` to find. The fix follows the EXACT architectural pattern
`imports.rs` already uses for `ImportFact`: a raw, per-file,
syntax-only extraction step (reusable across incremental updates for
untouched files) followed by a separate, always-recomputed semantic
resolution step against the full current snapshot pool. Read
`crates/codegraph-index/src/imports.rs` end to end before writing any
code — it is the template this plan's `impls.rs` module must mirror in
spirit (not copy verbatim; `ImplFact` has different fields and a
different derived-edge story).

**A critical grammar fact, already confirmed by a throwaway probe
during B2-ID-008's own investigation (do not re-derive, use directly):**
tree-sitter-rust's `impl_item` node exposes two NAMED fields via
`child_by_field_name`:
- `"trait"` — `None` for an inherent `impl Type { ... }`, a
  `type_identifier` node for a trait impl's trait name (`impl Matcher
  for RegexSet` → `child_by_field_name("trait")` is a `type_identifier`
  with text `"Matcher"`).
- `"type"` — ALWAYS present. Its node KIND varies: `type_identifier`
  for a plain type (`impl DirEntry { ... }` → `"DirEntry"`), but
  `generic_type` for a parameterized type (`impl<'a, W: Write>
  ReceiverBuffer<'a, W> { ... }` → a `generic_type` node whose own
  FIRST child is a `type_identifier` with text `"ReceiverBuffer"` — the
  base type name, ignoring the `<'a, W>` type-argument list).

**Use these named fields directly** (`node.child_by_field_name("trait")`,
`node.child_by_field_name("type")`). Do NOT search positionally for a
`type_identifier` child the way the existing (unreachable, and
therefore never caught) `collect_rust_impl_trait` function in
`edges/extends_implements.rs` does — that positional search is ITSELF
part of the bug [B2-ID-008](../../research/findings/B2-ID-008.md)
documents (it would silently extract the wrong/no type name for any
generic impl, since `generic_type` is not `type_identifier`). This
plan's new extraction code replaces that approach; it does not reuse
`collect_rust_impl_trait` at all (that function and its registration in
`base_names_in`/`edge_kind_for`'s Rust arm become dead code this plan
removes — see Task 3).

## Global Constraints

- **`ImplFact` is not an `Edge` and not a `SymbolSnapshot`.** It is a
  new, separate structural-fact type living in its own module
  (`crates/codegraph-index/src/impls.rs`), analogous to `ImportFact` in
  `imports.rs`. It is never inserted into `CodeGraph` directly and
  never has a `SymbolSnapshotId` of its own.
- **Raw extraction vs. semantic resolution stay separate**, exactly
  like `imports.rs`: `extract_impl_statements(tree: &ParseTree) ->
  Vec<RawImplStatement>` is pure syntax, callable on one file's tree
  alone, no snapshot pool involved. `resolve_impl_facts`/
  `resolve_raw_impl_statements` resolve already-extracted raw facts
  against a snapshot pool (the SAME `&[SymbolSnapshot]` pool every
  `edges` resolver and `imports.rs` already take).
- **Derived edges, not the fact itself, connect to the rest of the
  graph.** Per the approved design: when an `ImplFact` is a trait impl
  (`trait_type_text: Some(_)`) AND both the self-type and the trait
  name each resolve to EXACTLY ONE `SymbolSnapshot` in the given pool,
  emit one `Edge { kind: EdgeKind::Implements, from: <self-type's
  SymbolSnapshotId>, to: <trait's SymbolSnapshotId>, .. }` — the SAME
  `EdgeKind::Implements` variant `resolve_extends_implements` already
  produces for C#/C++/TS today (confirm this variant already exists in
  `codegraph_domain::EdgeKind` before adding anything; do not add a
  second one). An inherent impl (`trait_type_text: None`) never
  produces an `Implements` edge — but its `ImplFact` is still extracted
  and kept, because it still carries real information (associated
  items, generics) a future query may need, per the approved design's
  explicit "conserva però l'ImplFact perché serve a rappresentare
  inherent impl e associated items" instruction.
- **Unresolved/ambiguous self-type or trait name never fabricates an
  edge.** If the self-type resolves to zero or more-than-one candidate,
  or the trait name (when present) resolves to zero or more-than-one
  candidate, record that in the `ImplFact`'s own resolution status
  (see Task 1's exact shape) and emit NO `Implements` edge for that
  fact — "no edge beats a false edge," the same discipline every
  existing resolver and `imports.rs` already follow. This is not a
  new invariant; it is the project's standing one, applied here.
- **Associated-item handling is NOT invented casually.** The approved
  design is explicit: "Non fingere che tutti i methods dentro un impl
  appartengano semanticamente al trait... Se collegare i method
  all'impl/type richiede un nuovo edge o un design non banale, fermati
  e proponilo invece di inventare una relazione." Task 2 defines
  EXACTLY what `ImplFact` records about its own associated items
  (names + whether each one is a default-trait-method override or an
  inherent/associated function) and explicitly does NOT create any new
  `Edge` connecting a method to its impl block or to the trait method
  it may override — that remains future work, not silently implied by
  this plan. If, while implementing, a task's assigned implementer
  believes a non-trivial new edge is actually required to satisfy a
  task's own test list, it must stop and report via NEEDS_CONTEXT
  rather than invent one — the controller will rule on it.
- **Identity is deterministic, never a random UUID.** Per the approved
  design: derive identity from (repository/file/commit identity +
  impl's own `ByteSpan` + self-type text + optional trait-type text).
  `FileIdentity` already carries repository+commit+path; combine it
  with the `impl_item`'s own span and the two type-name strings. Do not
  introduce a new UUID-based id type — a stable hash (reusing whatever
  deterministic hashing convention `SymbolSnapshotId`/`ImportFact`'s
  own neighbors use, e.g. a stable, explicit hash function, not
  `Uuid::new_v4()`) is sufficient for THIS fact's own narrower identity
  needs (no cross-commit lineage is required for `ImplFact` — it is
  recomputed fresh every observe, like `ImportFact`).
- **No persistence, no `CodeGraph` API, no MCP surface.** Exactly like
  `ImportFact` — an in-memory `Vec<ImplFact>` a caller queries directly
  (or that feeds `resolve_implements_from_impl_facts`, a pure function
  this plan adds — see Task 2), with the SAME publication/atomicity
  discipline `ImportFact` already has in `incremental/indexer.rs`
  (`ObserveOutcome`/`RepositoryState` gain an `impl_facts: Arc<Vec<ImplFact>>`
  field alongside the existing `import_facts` field — mirror it
  exactly, field by field, including the incremental-reuse-vs-always-
  recompute split).
- **`cargo clippy --workspace -- -D warnings` must be run and pass
  before any task is reported DONE.** (Standing project constraint,
  [[c11mp]].)
- **Every task's own new/changed function needs real regression tests
  built from REAL extraction** (`extract_symbols_reporting_rejections`
  / real tree-sitter parses), never only hand-written placeholder
  signature strings — this is the exact synthetic-fixture blind spot
  [B2-ID-006](../../research/findings/B2-ID-006.md) and
  [B2-ID-008](../../research/findings/B2-ID-008.md) itself both
  identified as the reason earlier gaps went undetected. A test that
  builds an `ImplFact`/`SymbolSnapshot` from a literal string instead
  of parsing real source is acceptable ONLY for testing the pure
  resolution-logic functions in isolation (mirroring `imports.rs`'s own
  test style), never as the SOLE test of the extraction path itself.
- **Mutation testing (`cargo mutants`) runs per-module, scoped to the
  new/changed files** (`impls.rs`, the Rust-impl portions of
  `edges/extends_implements.rs`, the `impls`-related additions to
  `pipeline.rs`/`indexer.rs`) — not combined with any other resolver's
  own mutation campaign, per [[c23xp]]'s own standing instruction to
  treat each significant resolver change as its own measured
  experiment.
- **No merge, tag, or push.** This plan executes entirely inside the
  existing `b2-code-graph` worktree/branch — no new worktree is needed
  (B2 work is already isolated there). Do not create a PR or merge to
  `main`.

## Task 1: `ImplFact`/`RawImplStatement` extraction — raw syntax only

**Scope:** new module `crates/codegraph-index/src/impls.rs` (sibling to
`imports.rs`), registered in `lib.rs`/`mod.rs` exactly the way
`imports` is. Implements:

- `pub struct RawImplStatement` — the raw, unresolved shape extracted
  directly from one `impl_item` node: `self_type_text: String` (the
  text of the `type` named field's own relevant identifier — for
  `generic_type`, the base type name only, e.g. `"ReceiverBuffer"`, NOT
  the full `"ReceiverBuffer<'a, W>"` text; for `type_identifier`, its
  own text directly), `trait_type_text: Option<String>` (the `trait`
  named field's text when present, `None` for an inherent impl),
  `has_generics: bool` (whether the `impl_item` has a
  `type_parameters` child — generics are recorded as a flag for now,
  not a full generic-parameter list, since no query in this plan's own
  scope needs more), `has_lifetime_params: bool` (same idea, specific
  to whether any `type_parameters` child is a `lifetime_parameter` —
  confirm the exact node kind by direct parse, do not assume), `span:
  ByteSpan` (the whole `impl_item`'s own span), `associated_items:
  Vec<AssociatedItemFact>` (see below).
- `pub struct AssociatedItemFact { name: String, kind: AssociatedItemKind, span: ByteSpan }`
  — `AssociatedItemKind` is an enum with exactly two variants for this
  plan's scope: `Method` (a `function_item` with a body, taking a
  receiver — i.e., its own `parameters` child has at least one
  `self_parameter`-shaped child; confirm the exact node kind by direct
  parse) and `AssociatedFunction` (a `function_item` with a body but NO
  receiver parameter — the `DirEntry::normal`/`CommandSet::new` shape
  from B2-ID-008's own corpus evidence). Do NOT add a third variant for
  "default trait method" here — that distinction belongs to the
  TRAIT's own declaration, not to what's inside one specific `impl`
  block satisfying it; this plan's own associated-items list is
  scoped to "what's declared inside THIS impl block," full stop,
  consistent with the Global Constraints' own "don't invent extra
  relationships" instruction. If, while implementing, there turns out
  to be a real need to distinguish more shapes here, STOP and report
  via NEEDS_CONTEXT rather than add a variant unilaterally.
- `pub fn extract_impl_statements(tree: &ParseTree) -> Vec<RawImplStatement>`
  — walks the WHOLE file's tree (mirroring `extract_import_statements`'s
  own whole-file scope, not one symbol's signature text — this is
  exactly the granularity B2-ID-005 already established as correct for
  a file-level fact, and `impl` blocks are equally file/module-level,
  never symbol-owned) looking for `impl_item` nodes, extracting each
  via the named-field approach described in this plan's "Context for
  implementers" section above. Only wires up `Language::Rust` in its
  own language dispatch (mirror `imports.rs`'s own `walk_for_imports`
  language-dispatch shape) — do not attempt to generalize to any other
  language's own impl/trait-implementation syntax in this plan; that is
  explicitly out of scope (B2-ID-008 is Rust-specific).

**Tests required** (build each from REAL Rust source via
`crate::parse::RustParser.parse(...)`, never a hand-written
`impl_item` string pretending to be a parse result):
1. `impl Trait for Type` — one `RawImplStatement` with
   `trait_type_text: Some("Trait")`, `self_type_text: "Type"`.
2. Inherent `impl Type { ... }` — one `RawImplStatement` with
   `trait_type_text: None`.
3. Generic impl, e.g. `impl<T> Container<T> { fn get(&self) -> &T {...} }`
   — confirm `self_type_text == "Container"` (the base name, generic
   args stripped) and `has_generics == true`.
4. Impl with a lifetime parameter, e.g. `impl<'a> Holder<'a> { ... }`
   — confirm `has_lifetime_params == true`.
5. Multiple impl blocks for the same type (e.g. two separate `impl Foo
   { ... }` and `impl Bar for Foo { ... }` in one file) — confirm TWO
   separate `RawImplStatement`s are extracted, never merged into one.
6. Multiple traits implemented by the same type across SEPARATE impl
   blocks (`impl A for Foo {...}` and `impl B for Foo {...}`) — confirm
   two separate facts, each with its own correct `trait_type_text`.
7. One trait implemented by multiple DIFFERENT types (`impl Shape for
   Circle {...}` and `impl Shape for Square {...}`) — confirm two
   separate facts, each with its own correct `self_type_text`.
8. Associated items are correctly classified: a method (with a `&self`
   or `&mut self` receiver) is `AssociatedItemKind::Method`; a
   receiverless constructor-shaped function (`fn new() -> Self`) is
   `AssociatedItemKind::AssociatedFunction`.
9. Named-field extraction regression: a generic trait impl, e.g. `impl<T: Display> Describe for Wrapper<T> { ... }`
   — confirm BOTH `trait_type_text == Some("Describe")` AND
   `self_type_text == "Wrapper"` are extracted correctly (this is the
   exact shape the OLD positional-search bug would have gotten wrong —
   this test must fail if the extraction regresses to a positional
   search instead of the named-field approach).
10. Deterministic extraction: parsing the same source twice produces
    identical `Vec<RawImplStatement>` output (mirror `imports.rs`'s own
    `resolving_the_same_tree_twice_produces_deterministic_identical_facts`
    test shape).

**Deliverable:** `impls.rs` with `RawImplStatement`/`AssociatedItemFact`/
`AssociatedItemKind` and `extract_impl_statements`, fully tested per
above, `cargo test -p codegraph-index` green, `cargo clippy --workspace
-- -D warnings` clean.

## Task 2: `ImplFact` semantic resolution + derived `Implements` edges

**Scope:** extends `impls.rs` with:

- `pub struct ImplFact` — the resolved shape: `defining_file:
  FileIdentity`, `span: ByteSpan`, `self_type_text: String`,
  `trait_type_text: Option<String>`, `has_generics: bool`,
  `has_lifetime_params: bool`, `associated_items:
  Vec<AssociatedItemFact>` (carried through unchanged from the raw
  statement), `self_type_resolution: ImplTargetResolution`,
  `trait_resolution: Option<ImplTargetResolution>` (`None` exactly when
  `trait_type_text` is `None` — an inherent impl has no trait to
  resolve at all, not an unresolved one).
- `pub enum ImplTargetResolution` — mirrors `ImportResolution`'s own
  three-variant shape: `Resolved(SymbolSnapshotId)` (exactly one
  candidate in the given pool), `Unresolved` (zero candidates — e.g.
  the trait/type is external, imported from another crate, exactly
  like `ImportResolution::External`'s own meaning, though NAMED
  differently here since "External" specifically connotes imports in
  this codebase's existing vocabulary and `ImplFact` is a different
  context — confirm this naming choice doesn't collide with
  `ImportResolution`'s own variant names in a way that's confusing;
  rename if a clearer name emerges during implementation, but keep the
  three-way Resolved/Unresolved/Ambiguous shape), `Ambiguous` (more
  than one candidate — never arbitrarily picked).
- `fn deterministic_impl_fact_id(fact: &ImplFact) -> u64` (or similar;
  exact return type is an implementation choice) — the identity
  function per this plan's Global Constraints: a stable hash over
  `(defining_file, span, self_type_text, trait_type_text)`. Used
  internally for deduplication if ever needed; not necessarily exposed
  publicly unless Task 4's incremental-reuse logic needs it as a public
  comparison key (implementer's own judgment, document the choice).
- `pub fn resolve_impl_facts(defining_file: &FileIdentity, tree: &ParseTree, snapshots: &[SymbolSnapshot]) -> Result<Vec<ImplFact>, ImplFactError>`
  and `pub fn resolve_raw_impl_statements(raw_statements: &[(FileIdentity, RawImplStatement)], snapshots: &[SymbolSnapshot]) -> Result<Vec<ImplFact>, ImplFactError>`
  — mirror `resolve_import_facts`/`resolve_raw_import_statements`'s own
  two-function shape (one convenience wrapper over one file's tree, one
  the real global-resolution entry point taking already-extracted raw
  facts from potentially many files). Resolution: look up
  `self_type_text`/`trait_type_text` by NAME against `snapshots`
  (`s.name().as_str() == text`), exactly the same lookup convention
  every other resolver and `imports.rs` already use. `ImplFactError`
  mirrors `ImportFactError`'s own `DuplicateSnapshotId` shape (reuse
  the identical rejection check — do not write a second, slightly
  different duplicate-detection function; consider whether to literally
  reuse `imports.rs`'s own `reject_duplicate_ids` private helper by
  making it `pub(crate)`, rather than duplicating it).
- `pub fn resolve_implements_from_impl_facts(facts: &[ImplFact]) -> Vec<Edge>`
  — the derived-edge step per this plan's Global Constraints: for each
  `ImplFact` where `trait_resolution == Some(ImplTargetResolution::Resolved(trait_id))`
  AND `self_type_resolution == ImplTargetResolution::Resolved(self_id)`,
  emit one `Edge { kind: EdgeKind::Implements, from: self_id, to:
  trait_id, .. }` using the EXACT construction shape Task 0 confirmed.
  Deduplicate by `(from, to)` — per [B2-ID-002](../../research/findings/B2-ID-002.md)'s
  own already-established "one edge per semantic relation, never one
  per syntactic occurrence" discipline: if the SAME type implements the
  SAME trait via more than one impl block (not expected in real Rust —
  that would be a compile error — but defensive code should not assume
  the input is always compiler-valid, since this pipeline parses
  source that may not compile), collapse to one edge, not two. Inherent
  impls (`trait_resolution == None`) never produce an edge from this
  function — confirm this with a dedicated test (see below).

**Tests required** (extend Task 1's real-parse test style; these may
resolve against hand-built `SymbolSnapshot`s via `promote`, mirroring
`imports.rs`'s own `test_snapshot` helper, SINCE the thing under test
here is resolution logic, not extraction):
1. A trait impl where BOTH the self-type and trait name resolve to
   exactly one real snapshot each → `ImplFact` has both resolutions
   `Resolved`, and `resolve_implements_from_impl_facts` produces exactly
   one `Implements` edge with the correct `from`/`to`.
2. An inherent impl (no trait) → `trait_resolution` is `None`, and
   `resolve_implements_from_impl_facts` produces ZERO edges for this
   fact (dedicated test, not just absence-by-omission in another test).
3. An unresolved external trait (e.g. `impl Display for MyType` where
   `Display` is never in the given snapshot pool — it's from
   `std::fmt`) → `trait_resolution` is `Unresolved`, no edge produced.
4. An unresolved self-type (the implementing type itself is not in the
   given pool — e.g. implementing a trait for an external type like
   `impl MyTrait for String`) → `self_type_resolution` is `Unresolved`,
   no edge produced.
5. An ambiguous trait name (two different snapshots in the pool share
   the trait's name) → `trait_resolution` is `Ambiguous`, no edge
   produced — never an arbitrary pick.
6. No duplicate `Implements` edges when the same `(Type, Trait)` pair
   would otherwise produce two edges (construct this defensively, e.g.
   two `ImplFact`s with identical self/trait text — confirms the
   dedup logic, independent of whether real compiler-valid Rust could
   produce this input).
7. Deterministic resolution: resolving the same raw statements twice
   against the same pool produces identical `ImplFact`/`Edge` output.
8. `ImplFactError::DuplicateSnapshotId` is returned when the given pool
   itself contains a duplicate id (mirror `imports.rs`'s own equivalent
   test).

**Deliverable:** full `impls.rs` module as above,
`resolve_implements_from_impl_facts` added, all tests green, clippy
clean. Report must include Task 0's confirmed `Edge`-construction shape
actually used, and explicit confirmation that inherent impls produce
zero edges (not just that trait impls produce one).
