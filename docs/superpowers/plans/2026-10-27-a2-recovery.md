# A2 — Recovery (Fase A) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every `storage` write a persistent, crash-recoverable state machine — SQLite journal, before-image preservation, idempotent git commit, and a declared (never falsely "current") index state — so that a crash at any point leaves the vault either recovered or explicitly `failed`/inconsistent, never silently wrong, and so that `propose_and_commit` becomes the single, journal-backed entry point A1 only sketched the signature for.

**Architecture:** `storage` gains a `journal` module (SQLite via `rusqlite`, bundled) that persists one row per write operation keyed by `operation_id`, and a `git` module (`git2`) that commits each completed write. `propose_and_commit`'s signature is unchanged from A1 (`operation_id: Uuid` was already threaded through, unused); its body now drives `domain::WriteState` through the real C1 chain — `intent_recorded → content_persisted → journal_committed → git_committed → index_current`, with `recovering`/`failed` as the two side states — persisting each transition to the journal before performing the step's filesystem/git effect, exactly mirroring A1's existing `write_record_unchecked` critical-section discipline but now durable across process restarts. A `Vault::recover()` entry point runs at every `Vault::new()`-equivalent startup path (a new `Vault::open` constructor) and reconciles every non-terminal journal row against the C1 fault-matrix table before any other `storage` call is permitted to proceed; if reconciliation itself cannot establish a consistent state, `Vault::open` returns an error state rather than a usable `Vault` — the core's "fail closed" rule applies to startup, not just to individual operations. Reads (`read_note`, `current_version`) are re-pointed to resolve through the journal's last `journal_committed` row for that note (verified by content hash against the on-disk file or that exact operation's own before-image, never a different operation's), and now share the writer's per-note lock so a read can never observe a file mid-rename before its writer's journal advance makes the new version official — never by opening whatever file currently sits at the record path — closing the gap A1 left open ("mai il file più recente per percorso"). `domain::WriteState::valid_transition` is tightened to match C1's table exactly (Continuity [c10b3]): `Recovering`'s outgoing set is narrowed to only the transitions C1's recovery table actually describes, dropping the broader placeholder set A1 shipped. A crash-injection harness (a `FaultPoint` enum plus a storage-internal hook invoked at each of the 8 named points in the fault matrix) lets tests deterministically interrupt a write after any step without needing an actual process crash, and is the single source every crash-recovery test is built from, matching the spec's requirement that the C1 fault matrix is "l'unica fonte dei test di crash della Fase A."

**Tech Stack:** Rust (stable), existing `domain`/`policy`/`storage` crates (no new crates created — `index`, `agent`, `api` remain untouched, A2 does not touch them beyond the `IndexState` stub type in `domain`). New dependencies in `storage`: `rusqlite` (bundled SQLite, MIT — allowlist-compatible) for the journal; `git2` (libgit2 bindings, MIT) for commits; `sha2` (MIT/Apache-2.0, already a transitive dependency via `policy`'s secret hashing — promote to a direct `storage` dependency) for content-hash verification. No async runtime; crash-injection tests use the same `std::thread`/explicit-synchronization discipline A1 established (no wall-clock sleeps).

**Spec:** `docs/Spec_mvp.md` (sections: "Fase A — Vault affidabile" consegna 3–4 and every Fase A test bullet involving crash/retry/recovery; "Appendice contrattuale" C1 in full — state table, fault matrix, before-image, `failed`-is-terminal rule; "Ordine di implementazione" item 2 defines A2's exact boundary as "journal a stati, crash injection, indice ricostruibile... regola sui retry di C1 e la matrice stato × guasto già tradotta in test.")

## Global Constraints

- No encryption, no deletion registry, no backup/restore in this plan — those are A3 (spec item 5–6 of Fase A consegne, Continuity [d1ec]).
- No real index (trigrams, BM25, tree-sitter) — that is B1. A2 adds only `domain::IndexState { Current, Stale }` as a reported-state stub. **No A2 code may ever return `IndexState::Current`** (correction, user architectural review point 1): `WriteState::IndexCurrent` is a write-pipeline completion marker ("nothing further for this phase to do"), strictly distinct from `domain::IndexState`, which is a claim about index freshness that stays honestly `Stale` throughout A2 because no indexer exists yet. Conflating the two — as the plan's first draft did by having `NullIndexer` return `Current` — would itself violate C1's "mai dichiarato corrente se è indietro."
- `domain::WriteState::valid_transition` must be tightened to C1's exact table (Continuity [c10b3]) as part of this plan, not left as the broader A1 placeholder. Two edges beyond the original A1 table are added here for correctness, not left implicit: `ContentPersisted -> Failed` (a rolled-back write; see the Task 7 rollback correction) and the `Recovering`-related edges needed for `reconcile` to genuinely mark and resume from `Recovering` (Task 7).
- The new version of `read_note`/`current_version` must never return content from a file that has not reached `journal_committed` in the journal — a reader must resolve through the journal, verified by hash, not by opening "whatever is at the path right now" (spec C1: "le API leggono la versione indicata dal journal, verificata per hash... mai il file più recente per percorso"). Hash verification alone is not sufficient to guarantee this: `read_note`/`current_version` must also share the writer's per-note lock (Task 4), closing the race where a reader opens a path mid-rename before the writer's own journal advance makes the new version official.
- A rolled-back write (before-image restored because the new content failed hash verification) must never be indistinguishable from a successful write: the triggering operation's row ends at `Failed`, never at a committed state, its `new_version` field is preserved as a truthful record of what it failed to commit (not reinterpreted as success), and no git commit is made under its `operation_id` (Task 7 correction).
- Git-commit idempotency for a given `operation_id` must not depend solely on a bounded history scan. The journal's own `git_commit_oid` column is the primary (O(1), authoritative) idempotency source; a history scan is retained only as a defensive repair mechanism for the crash-between-git-commit-and-journal-update window, and any value it finds must be written back onto the journal row so it does not need to be re-derived (Task 5 correction). Each operation's git staging must also be isolated from any other staged-but-uncommitted content in the repository — commits are built via `TreeBuilder` from `HEAD` plus this operation's one blob, never via the shared `.git/index` (Task 5 correction).
- A bounded Tier 2 history scan can return `None` for a commit that genuinely exists (if it sits beyond the scan depth), and that ambiguity must never be allowed to trigger a second `commit_operation` call for the same `operation_id` — doing so during recovery would create a real duplicate commit, since `HEAD` has moved since the original. `find_commit_for_operation` takes an explicit `ScanDepth`; the normal write-path chain extension uses `Bounded` purely as a performance bound (the commit it's checking for, if any, was just made and is always near `HEAD`), while `reconcile` (the recovery path) always uses `Unbounded`, so it can definitively prove existence rather than guess (second independent review, Task 5 correction).
- **Fifth-review correction (user's explicit "precisazione Git"):** an `Unbounded` scan walking every commit reachable from `HEAD` proves the operation's commit does not exist among *reachable* commits — it does not prove the commit was never made. A commit `reconcile` is looking for can become unreachable from `HEAD` without A2 ever touching it (a manual `git reset`/rebase/force-push by the vault's own user between the original write and recovery, per this repo's own one-user/one-laptop threat model) — the C1 "walked the whole history and found nothing" guarantee this plan originally claimed for `Unbounded` therefore does not hold unconditionally, because reachability is itself a mutable fact. `find_commit_for_operation` and `reconcile`'s row-3 handling (Task 5/Task 7) must treat this as a distinct outcome from a journal row that has simply never been committed: the two cases are indistinguishable by an `Unbounded` scan alone, so this plan does not attempt to tell them apart (doing so would require storing out-of-band proof of commit attempts, which is new journal state this plan does not add). Instead, `reconcile`'s row-3 fix-up stays exactly as specified below — on an unbounded miss, it calls `commit_operation` and accepts the small residual risk of a duplicate commit in the specific scenario where the vault's own git history was rewritten out-of-band after A2's original commit — and this residual risk is documented verbatim in `eval/results/A2/evidence.md` (Task 10) as a known, accepted limitation of history-reachability-based idempotency, not silently absorbed. This plan does NOT invent a new "fail closed on scan miss" behavior for row 3, because doing so would make every ordinary, legitimate "git was never committed yet" case (the overwhelming majority of row-3 hits) indistinguishable from the rare rewritten-history case and would block `Vault::open` on the common case to guard against the rare one — the fail-closed posture already required elsewhere (Task 7 row 2's `Inconsistent` return) is reserved for cases this plan's own fault matrix enumerates, and out-of-band history rewriting is explicitly outside that matrix.
- **Accepted, documented tradeoff (third independent review):** `reconcile`'s `Unbounded` scan only triggers for a row actually sitting at `JournalCommitted` with no `git_commit_oid` yet (i.e. a crash in the narrow window between a successful git commit and the journal recording it) — not on every ordinary `Vault::open`. When it does trigger, it walks to the true end of `HEAD`'s reachable history, which is finite and therefore terminates, but has no stated worst-case latency bound; on a vault whose git repo has accumulated years of commits, this could make that one `Vault::open` call noticeably slow. This plan accepts that tradeoff deliberately (correctness over speed in the rare recovery case) and does not implement a timeout or a larger-but-still-bounded first pass — if this proves too slow in practice, it is explicitly flagged in `eval/results/A2/evidence.md` (Task 10) as a known limitation to revisit, not silently absorbed.
- `read_note`/`current_version` have NO before-image fallback: a primary hash mismatch against the journal's resolved committed row is unconditionally `StorageError::Inconsistent`. A read must never substitute a different operation's before-image and relabel it with the resolved row's version — doing so pairs content and version from two different operations and presents it as one coherent current state. Only `reconcile` (Task 7, row 2) has the authority to perform a rollback, by correctly demoting the affected operation to `Failed` as a journal state transition (second independent review, Task 4 correction).
- Every test that exercises `pub(crate)` or `#[cfg(test)]`-gated internals lives in an inline `#[cfg(test)] mod` inside the relevant `src/*.rs` file, never in a separate `tests/*.rs` integration file — an integration test compiles the crate as an ordinary external, non-`cfg(test)` dependency and cannot see either kind of item (Task 8 correction).
- An adversarial or characterization test must assert a concrete, falsifiable outcome — never merely print a result and pass unconditionally. A test with no assertion cannot distinguish the behavior it claims to characterize from its opposite (Task 9 correction).
- `commit_write`'s success code path requires `git_committed`; if git fails, the result is `git_pending` — a response code for an operation parked at `journal_committed` without `git_committed`, not a persisted `WriteState` variant — and that operation resumes at the next `Vault::open`/explicit retry, per spec C1.
- A retry with the same `operation_id` against a `failed` operation returns the same `failed` outcome without re-applying anything — `failed` is terminal (spec C1, "failed è terminale"). A retry with the same `operation_id` against a recoverable (non-terminal) state continues with that same id and returns the outcome already reached, never double-applying.
- The before-image of the previous version is durably persisted before the rename that replaces it, and is deleted only after `git_committed` — never before (spec C1 "Before-image").
- Every crash-recovery test must be derived from the C1 fault-matrix table (the 8 rows in `docs/Spec_mvp.md` under "Matrice stato × guasto") — this plan treats that table as the single source of crash tests, per the spec's own framing, not an inspiration for inventing additional ad hoc scenarios.
- SEC-001 (TOCTOU/symlink race), SEC-002 (intra-vault record aliasing via symlink), SEC-003 (hard-link aliasing) are re-evaluated against the actual journal/recovery design this plan implements, per Continuity [d5b9] and the user's explicit instruction. Hash verification added by this plan must NOT be treated as proof that any of the three is resolved — a hash check only detects aliasing/TOCTOU after the fact (the wrong content was already read or written); it does not prevent the race. Each of SEC-001/002/003 stays open unless a task adds an adversarial test that reproduces its exact exploit scenario against the new recovery code and shows it is now rejected or safely contained — not merely "harder to hit." Where a debt is not closed, the plan's final task records why, with the specific residual exploit still possible, and reaffirms the mandatory re-evaluation before Fase D (Continuity [d5b9]).
- `storage`'s only `pub` write entry point remains `propose_and_commit` (Continuity [c1p2]) — the journal and git modules this plan adds are `pub(crate)`, reachable only through `propose_and_commit` and the new `Vault::open`/`Vault::recover` startup path, never as new public write primitives.
- `cargo clippy --workspace -- -D warnings` must be run and pass before any task is reported done (Continuity [c11mp]).
- Every acceptance-criterion artifact goes in `eval/results/A2/` (commit hash, command run, raw output, verdict) — matching A1's evidence discipline.
- Do not report A2 as providing anything beyond what this plan implements — A3's encryption/backup/deletion-registry guarantees, and B1's real index, are separate, unimplemented work (Continuity [c5ja] extended to A2's own boundary).

## Review Focus

- **A crash between `content_persisted` and `journal_committed` where the renamed file's hash does NOT match what was intended to be written** (e.g. partial write before a crash, or a concurrent unrelated corruption) — the spec's fault matrix requires falling back to the before-image and verifying *that* hash too; a reasonable implementer expects a clean `failed`/inconsistent state if even the before-image is unreadable, not a silent "best effort" recovery. Covered in the crash-matrix task as the "nuova versione con hash non valido" row.
- **Two sequential crashes on the same `operation_id`** — first crash leaves the op at `journal_committed` (git pending), recovery resumes and crashes again before `git_committed` completes — the retry/idempotency rule must still hold on the *second* recovery attempt, not just the first. Not explicitly enumerated as a separate fault-matrix row but implied by "ogni passo di recovery è idempotente"; covered by a dedicated double-crash test in the recovery task.
- **`Vault::open` itself failing to reconcile** (e.g. journal present but unreadable/corrupt, or a journal row referencing a note whose file is missing with no before-image either) — the spec's fail-closed rule ("si ferma in uno stato dichiarato inconsistente") applies at startup, not only mid-operation; a reasonable implementer expects `Vault::open` to return a typed error rather than quietly starting with gaps. Covered by its own task with a corrupted-journal fixture.
- **A read request arriving concurrently with an in-progress write that has reached `content_persisted` but not yet `journal_committed`** — per C1, this read must never observe the file that was just renamed onto disk before the journal says so. A1's per-note mutex only protected writer-vs-writer; this plan extends it to guard reader-vs-writer too (Task 4), so a concurrent read blocks until the writer's critical section — including `journal_committed` — completes, rather than racing past it. Covered by a dedicated test in Task 4 (lock sharing, barrier-timed) and a forced-window version in Task 8 (fault-injector pause, proving the read actually blocks rather than returning early).
- **Git available at commit time but the repository itself is in an unexpected state** (e.g. a previous *manual* `git commit` by the user landed between A2's `journal_committed` and its own `git_committed` step, so the working tree isn't what the write pipeline last left it) — the spec only tests "git non disponibile," but a real laptop-with-one-user environment makes a manually-dirtied repo plausible, and idempotent-by-`operation_id` commit logic must not corrupt or silently skip in that case. Covered in the git-integration task with a test that commits an unrelated change via `git2` directly between `journal_committed` and the commit step, then runs recovery.

## Task 4: Wire the journal and before-image into the write path; journal-resolved reads (storage)

**Files:**
- Modify: `crates/storage/src/vault.rs`
- Modify: `crates/storage/src/propose.rs`

**Correction (user architectural review, point 2).** The original version of this task gave `write_record_unchecked` the per-note lock for its own critical section but left `read_note`/`current_version` reading the filesystem *without* taking that lock. That is unsound: C1 requires a read to "mai [leggere] il file più recente per percorso," but between step 4 (the rename lands new bytes on disk) and step 6 (`journal.advance(..., JournalCommitted)`) below, a concurrent `read_note` call — if it does not share the writer's lock — resolves `last_committed_for_note` to the *previous* row (correctly, since the new one isn't committed yet) but then opens "the file at that row's recorded path," which is the **same path the writer has already renamed onto**. The reader ends up hashing the writer's brand-new bytes against the *old* row's `content_hash`, gets a mismatch, and incorrectly falls into the corruption/rollback path for a note that was never corrupted — the race is real, not hypothetical. The fix: `read_note`/`current_version` acquire the exact same per-note `Mutex` that `write_record_unchecked` holds for its whole critical section, so a read can never observe the filesystem mid-write; this turns A1's writer-vs-writer mutex into a full reader-vs-writer exclusion for the duration of one operation (still process-local/in-memory, same scope as A1 — this does not change the mutex's documented cross-process limitations). A second, independent gap the review raised — "verifica la corretta associazione delle before-image alle operazioni" — is that no test proved a before-image fallback inside `read_note` actually belongs to the exact `operation_id` of the row being verified, as opposed to some other row's before-image. - Consumes: `Journal`, `AdvanceFields` (Task 2); `persist_before_image`, `delete_before_image`, `read_before_image`, `content_hash` (Task 3); `FaultInjector::none()` (Task 1 — production call sites only, see below).

(2) acquire the per-note lock (A1 behavior, now ALSO shared with reads — see below) and read the actual current version the same way A1 did, compare to `expected_version`, return `Conflict` on mismatch (the journal row for this failed attempt is advanced to `Failed` before returning, per C1's `failed`-is-terminal framing for a rejected attempt); ## Task 5: Idempotent git commit per operation (storage)

**Files:**
- Create: `crates/storage/src/git.rs`
- Modify: `crates/storage/src/vault.rs` (extend the chain from `JournalCommitted` to `GitCommitted`)
- Modify: `crates/storage/src/propose.rs` (surface `git_pending` as a response variant)

- Test: inline `#[cfg(test)]` in `git.rs`, using a `git2::Repository::init` on a fresh `unique_test_dir()` for each test (never the real SuperBrain repo)

**Correction (user architectural review, point 5).** The original version of `commit_operation` called `index.add_path(record_path)` then `index.write_tree()` against the repository's shared, on-disk `.git/index`. `Index::write_tree()` writes a tree from the **entire current index**, not just the one path just staged — so if any other staged-but-uncommitted change exists in that shared index (another concurrent operation mid-commit, or leftover staged state from an interrupted prior attempt), this operation's commit would silently include it, which is precisely "isola lo staging di ogni operazione dalle modifiche staged preesistenti" failing. The fix: never touch the repository's shared index at all. Build the new tree directly from `HEAD`'s tree via `git2::TreeBuilder`, updating (or inserting) only this operation's single blob, and construct the commit from that tree — the on-disk `.git/index` is never read or written by `commit_operation`, so no other operation's staged state (past, concurrent, or future) can leak into this commit, and this commit cannot leak into anyone else's. The second half of the review's point 5 — "non basare una garanzia di idempotenza esclusivamente su una scansione arbitrariamente limitata della cronologia Git" — is fixed by making the *journal* the primary idempotency source (via the new `git_commit_oid` column from Task 2), with the history scan demoted to a defensive consistency check only, never the deciding mechanism; see below. Point 5 also raised "crash tra commit Git e aggiornamento journal" — this is handled identically to the pre-existing JournalCommitted-row-3 recovery case in Task 7: a crash after `git2`'s commit succeeds but before `journal.advance(op, GitCommitted, ...)` runs is exactly what the two-tier idempotency check below is for.

**Interfaces:**
- Consumes: `Journal`/`OperationRow` (Task 2, now including `git_commit_oid`); the vault root path.
- Produces:
  - `pub(crate) enum GitError { Git2(git2::Error), NoRepository }` (derive `thiserror::Error`).
  - `pub(crate) fn commit_operation(repo_path: &Path, operation_id: Uuid, note_id: &str, record_path: &Path) -> Result<git2::Oid, GitError>` — opens the repo at `repo_path` (the vault root, which the plan assumes IS a git repository — if `git2::Repository::open` fails with "not found," return `GitError::NoRepository`, which `propose_and_commit` maps to the `git_pending` response code per spec C1, not a hard failure). Isolated staging (the point 5 fix): reads `HEAD`'s current tree via `repo.head()?.peel_to_tree()`, builds a `git2::TreeBuilder` seeded from that tree, inserts a blob for `record_path`'s current on-disk contents at its path relative to `repo_path` (`TreeBuilder::insert`), and calls `TreeBuilder::write()` to get a new tree `Oid` — the shared `.git/index` is never opened, read, or written by this function, so no other operation's staged-but-uncommitted state (if the shared index were ever used elsewhere, which this plan's design avoids entirely) can affect this commit. Creates a commit from that tree with `HEAD` as its sole parent, whose message embeds `operation_id` verbatim (e.g. `format!("vault: update {note_id} [operation_id={operation_id}]")`) as a defensive, secondary identification string — not the primary idempotency mechanism (see `find_commit_for_operation` below) — and updates the branch reference `HEAD` points to, to the new commit.
  - `pub(crate) enum ScanDepth { Bounded(usize), Unbounded }` and `pub(crate) fn find_commit_for_operation(journal: &Journal, repo_path: &Path, operation_id: Uuid, scan: ScanDepth) -> Result<Option<git2::Oid>, GitError>` — **two-tier lookup, journal-first, with a caller-chosen scan depth.** Tier 1 (primary, O(1), the point 5 fix): if `journal.get(operation_id)` returns a row with `git_commit_oid` set, parse and return that `Oid` directly — no history walk needed, and this is authoritative because it is this exact operation's own durably-recorded commit reference, not an inference from commit-message text. Tier 2 (defensive fallback only, used when the journal row has no `git_commit_oid` recorded yet — e.g. the crash-between-commit-and-journal-update scenario the review raised): walk history from `HEAD` looking for a commit message containing `[operation_id={operation_id}]`, stopping either after `scan` commits (`ScanDepth::Bounded(n)`) or only at the end of history (`ScanDepth::Unbounded`); if found, this is the "git2's commit succeeded, but the journal update that would have recorded `git_commit_oid` never ran" case — the caller (Task 7's `reconcile`) must still write the found `Oid` back onto the journal row via `journal.advance` so Tier 1 becomes authoritative for any future lookup of this same operation, rather than re-walking history every time.

    **Correction (second user architectural review, issue 3).** The original version of this function always used a bounded scan (e.g. 500 commits) for Tier 2, with no distinction between "scanned to the true end of history and found nothing" and "hit the depth cap before reaching the end." If a real commit for `operation_id` exists but sits beyond that bound (plausible after many manual commits accumulate), a bounded-only Tier 2 returns `None` indistinguishably from the genuine "no commit exists" case. The caller (Task 7's row 3) would then call `commit_operation` again, which — because `HEAD` has moved since the original commit — produces a genuinely different commit (different parent, different `Oid`) under the SAME `operation_id`'s message marker: a real duplicate, not an idempotent re-entry. The fix: `find_commit_for_operation` takes an explicit `ScanDepth`, and the two call sites choose differently by how much they can tolerate ambiguity. The normal write-path chain extension (below) is the hot path, runs immediately after a write whose commit — if it exists at all — was *just* made and is therefore always at or extremely near `HEAD`; it uses `ScanDepth::Bounded(500)` purely as a performance bound, never trading correctness for it, because a commit this fresh cannot be beyond a 500-commit bound. Task 7's `reconcile` (the recovery path, which runs rarely and where correctness matters far more than speed) always uses `ScanDepth::Unbounded`, so it can always definitively prove whether `operation_id`'s commit exists anywhere **reachable from `HEAD`** — removing the ambiguous "beyond the bound" case entirely rather than trying to detect and special-case it.

    **Fifth-review correction (user's explicit "precisazione Git," documented here verbatim per the Global Constraints entry above).** "Reachable from `HEAD`" is not the same as "exists." `Unbounded` proves the former, not the latter: a commit can be made unreachable (reset, rebase, force-push) by activity outside A2's own write/recovery paths — this vault's own threat model already treats the user as a trusted single operator who can touch the repository directly (see the Review Focus item on a manually-dirtied repository), and a rewrite of reachable history is the same class of out-of-band action, just more disruptive. `find_commit_for_operation` does not attempt to detect this case — doing so would require the journal to record "a commit attempt was made" as its own fact, independent of `git_commit_oid`, which is new persisted state this plan does not add — so an `Unbounded` miss is treated by `reconcile` (Task 7, row 3) exactly as "no commit was ever made," and `commit_operation` is called. The residual risk (a duplicate commit, only in the specific case where the vault's history was rewritten out-of-band after the original commit) is accepted deliberately and recorded in `eval/results/A2/evidence.md` (Task 10) as a known limitation of reachability-based idempotency — not a silent gap.
  - `Vault`'s chain extension: after `JournalCommitted` (Task 4's stopping point), call `find_commit_for_operation(journal, repo_path, op, ScanDepth::Bounded(500))` first; if it returns `Some(oid)` via either tier, ensure the row's `git_commit_oid` is set to that `oid` (writing it if Tier 2 found it) and advance to `GitCommitted` (idempotent re-entry); if `None`, call `commit_operation`, and on `Ok(oid)`, advance to `GitCommitted` with `AdvanceFields::git_oid(oid)` (recording the `Oid` on the SAME journal write that advances the state — not a separate write, so there is no window where the state says `GitCommitted` but `git_commit_oid` is still unset) and then call `delete_before_image` (per spec: "La before-image si elimina solo dopo git\_committed"); on `Err(GitError::NoRepository)`, do NOT advance the journal state past `JournalCommitted` and return a new `StorageError::GitPending { note_id }` variant instead of an error — this is the spec's `git_pending` *response code*, distinct from a persisted `WriteState` (the row legitimately stays at `JournalCommitted` until a later retry succeeds); on any other `GitError`, return `StorageError::Io`-equivalent (fold via a new `#[error("git error: {0}")] StorageError::Git(#[from] GitError)` variant) without advancing — same "stays recoverable at JournalCommitted" behavior. This chain extension is only ever reached for a row AT `JournalCommitted` — Task 7's rollback case (row 2's correction) ends a failed operation at `Failed` directly, never passing through `JournalCommitted`, so this chain never attempts to git-commit rolled-back content under the failed operation's `operation_id`; nothing in this task needs to special-case rollback, because a `Failed` row is structurally unreachable from here.
  - `propose_and_commit`'s return type gains the distinction the spec requires: introduce `pub enum CommitResult { Committed(CommitOutcome), GitPending { note_id: String, operation_id: Uuid } }`, and change `propose_and_commit`'s `Ok` type from `CommitOutcome` to `CommitResult` (this is the one signature change in the whole plan, and it is required: the spec states `commit_write` must distinguish a full success from "git_pending, not a successo," and A1's `Result<CommitOutcome, ProposeError>` had no way to express that). `ProposeError::Storage(StorageError::GitPending { .. })` is caught inside `propose_and_commit` and converted to `Ok(CommitResult::GitPending { .. })` rather than propagated as an error — git unavailability is an expected, non-error outcome per spec, not a failure of the proposal itself.

## Task 6: `IndexState` stub and the final `IndexCurrent` chain step (domain, storage)

**Files:**

**Correction (user architectural review, point 1).** The original version of this task had `NullIndexer::mark_current` unconditionally return `IndexState::Current`, and treated `WriteState::IndexCurrent` and `domain::IndexState::Current` as the same fact. They are not: C1's `WriteState::IndexCurrent` is a *write-pipeline* completion marker ("this operation has nothing further for `storage` to do"), while `domain::IndexState` is a claim about whether a *real index* reflects a note's current content — a claim that, pre-B1, is **always false**, because no indexer exists. Spec C1 is explicit that the index "non viene mai dichiarato corrente se è indietro," and before B1 the index is permanently behind by definition (it doesn't exist). Declaring `IndexState::Current` here would be exactly the kind of false "index is current" statement C1 forbids, even though the state is a stub. The fix: `NullIndexer::mark_current` always returns `IndexState::Stale`, never `Current` — there is no code path in A2 that can honestly produce `IndexState::Current`, because that requires a real indexer, which doesn't exist until B1. The write pipeline's journal row still advances to `WriteState::IndexCurrent` (the pipeline step is genuinely done — there is nothing further for A2's stub to do), but `Vault` separately exposes the indexer's own verdict via a new `pub(crate) fn index_state_for(&self, note_id: &NoteId) -> IndexState` so a caller asking "is the index current for this note" always gets the honest answer (`Stale`) regardless of what the journal's pipeline-completion state says. This is the distinction the Global Constraints section already states in words ("A2 adds only `domain::IndexState { Current, Stale }` as a reported-state stub... never a real rebuild") but the original Task 6 code contradicted by wiring `NullIndexer` to always say `Current`. `WriteState::IndexCurrent` is renamed in this task's doc comments (not its enum variant name, which C1 fixes) to be described as "index step of the write pipeline completed (trivially, since A2 has no indexer to fall behind)" — never as "the index is up to date."

**Interfaces:**
- Produces:

**Interfaces:**

- Produces:
  - `pub(crate) enum ReconcileError { Inconsistent { operation_id: Uuid, reason: String }, Interrupted(FaultPoint), Journal(JournalError), Io(std::io::Error) }` — `Interrupted` is used only by `FaultInjector::trigger_at` in tests (see the row-5 test below and Task 8's double-crash test); production `reconcile` calls, which always pass `FaultInjector::none()`, can never produce it.
  - `pub(crate) fn reconcile(root: &Path, journal: &Journal, repo_path: &Path, indexer: &dyn Indexer, injector: &FaultInjector) -> Result<ReconcileReport, ReconcileError>` — fetches every row from `journal.non_terminal_operations()` and, for each, applies exactly the C1 fault-matrix row matching its current `state`, advancing it via `journal.advance` through to a terminal state (`IndexCurrent` or `Failed`) or returning `ReconcileError::Inconsistent` for that operation if even recovery cannot establish a safe state — per spec, one unrecoverable operation blocks `Vault::open` entirely rather than letting the vault start with a silently-skipped gap (this is the "fail closed at startup" requirement). The five rows and their handling, directly from the spec's table:
    1. `IntentRecorded` (crash before any write) → `journal.advance(op, Failed, ...)`. The caller must retry with a new `operation_id`.
    2. `ContentPersisted` with no verifiable hash match (neither the new content's hash nor, on fallback, the before-image's hash can be confirmed against what's on disk) → attempt before-image restore via `read_before_image` + `atomic_write` + `content_hash` verification; on success, advance **this operation's own row** to `Failed` (not `JournalCommitted` — see the correction below) and delete its before-image (the restore is complete, nothing further to preserve for this operation); on failure of the restore too, return `Inconsistent` for this operation (this is the sole row where reconciliation can legitimately fail the whole `Vault::open`).

       **Correction (user architectural review, point 3).** The original version of this row advanced the *rolled-back* operation to `WriteState::JournalCommitted` — the same terminal-looking state a genuinely successful write reaches — with the row's `new_version` field still holding the version the operation *failed* to commit. That makes a rolled-back write indistinguishable from a committed one by inspecting the row alone, and it is wrong against C1 on its own terms: C1's fault-matrix entry for this exact row says only "Ripristino della before-image" (restore the before-image) — it never says the original operation becomes linearized. The operation's intended content never validly reached a verifiable state; the vault's visible content is the *previous* version, already linearized by whichever earlier operation produced that before-image. There is nothing new for THIS operation to commit — it failed. The fix: a rollback advances the triggering operation's row straight to `Failed` (an allowed `ContentPersisted -> Failed` transition — add this edge to `domain::WriteState::valid_transition` in Task 1 as part of this correction, since A1's table never needed it and the original Task 7 text relied on a transition, `ContentPersisted -> JournalCommitted`, that is valid in general but wrong for THIS case specifically). The vault's current, visible version after a rollback is whatever `last_committed_for_note` already resolves to from the **prior** operation's row (unaffected by this one) — reconciliation does not need to construct a new committed row for the restored content, because that content was already linearized when the prior operation committed it; restoring the bytes on disk merely makes the filesystem match what the journal already says is current. No git commit is owed for a rollback either (Task 5/9 below do not call `commit_operation` for a `Failed` row) — the content being "re-affirmed" was already committed by an earlier operation, so re-committing it under this operation's `operation_id` would misattribute provenance, which is exactly the ambiguity the review flagged.
    3. `JournalCommitted` (git never ran, or ran and crashed before being recorded) → call `find_commit_for_operation(journal, repo_path, op, ScanDepth::Unbounded)` first (idempotent re-entry: a commit may already exist even though the journal never recorded `GitCommitted`, e.g. a crash between `git2::Repository::commit` returning and the journal `advance` call — this is exactly Task 5's Tier 2 case). **`reconcile` always passes `ScanDepth::Unbounded`, never `Bounded`** (Task 5 correction, second review issue 3): recovery must be able to definitively prove a commit does or does not exist, since calling `commit_operation` on a false "not found" (one that only means "not found within an arbitrary bound") would create a genuine duplicate commit under the same `operation_id`'s message marker, with `HEAD` having moved since the original commit. If found via Tier 2 (the journal row had no `git_commit_oid` yet), `reconcile` itself writes that found `Oid` back onto the row via `journal.advance(op, GitCommitted, AdvanceFields::git_oid(oid))` in the SAME step that advances the state, so Tier 1 is authoritative for this row from now on, and delete the before-image; if not found at all — which, with an unbounded scan, is now a definitive fact, not a guess — call `commit_operation` (same as the normal chain) and advance with its new `Oid` on success; if git is unavailable, leave the row at `JournalCommitted` (this one operation does NOT block `Vault::open` — it is `git_pending`, an explicitly allowed resting state, not an inconsistency).
    4. `GitCommitted` (the write pipeline's final step never ran) → call `indexer.mark_current` (a no-op for `NullIndexer`, per Task 6's correction) and advance the journal to `IndexCurrent` — this is purely "the pipeline has nothing further to do," not a claim that indexing happened. `Vault::index_state_for` independently and always reports `IndexState::Stale` regardless of this transition, matching the spec's "l'indice ... non viene mai dichiarato corrente se è indietro." Never blocks `Vault::open`.
    5. `Recovering` (a crash occurred *during a previous recovery attempt*) → re-dispatch to whichever of rows 1–4 matches what `Recovering`'s stored `state`-before-crash would have been. This requires a schema addition, `previous_state TEXT` (added to Task 2's schema as part of this task), written whenever `reconcile` marks a row `Recovering`.

The fix: `reconcile` now genuinely writes `Recovering` itself, as its *first* step for each non-terminal row it processes — `journal.advance(op, Recovering, AdvanceFields::previous_state(row.state))` runs BEFORE `reconcile` does any of that row's fix-up work (rows 1–4's logic), and only on completing that row's fix-up does it advance to the row's actual resolved target (`Failed`, `JournalCommitted`, `GitCommitted`, or `IndexCurrent`). - [ ] **Step 5: Write the forced-window concurrent-read-during-write test (Review Focus item 4), proving the Task 4 lock fix makes a read BLOCK rather than observe a half-committed state**

**Correction (user architectural review, point 2, continued).** Because Task 4 now has `read_note` share the writer's per-note lock, a reader that calls `read_note` while the writer is paused *inside its own critical section* cannot proceed at all until the writer finishes — it blocks on the lock, it does not race past it. #[test]
fn read_blocks_behind_a_paused_writer_holding_the_same_note_lock_and_then_sees_the_fully_committed_result() {
    let (root, journal_path) = fresh_root_and_journal_path();
    let vault = Arc::new(Vault::open_with_default_indexer(root, &journal_path).unwrap());
    let id = NoteId::parse("note-a").unwrap();
    vault.write_record_unchecked(&id, "v1", Version(0), Uuid::new_v4()).unwrap();

    let (pause_tx, pause_rx) = std::sync::mpsc::channel();
    let (resume_tx, resume_rx) = std::sync::mpsc::channel();
    let injector = FaultInjector::pause_at(FaultPoint::AfterRenameBeforeJournalCommitted, pause_tx, resume_rx);
    let writer_vault = Arc::clone(&vault);
    let writer_id = id.clone();
    let writer = std::thread::spawn(move || {
        writer_vault.write_record_unchecked_with_injector(&writer_id, "v2", Version(1), Uuid::new_v4(), &injector)
    });

    pause_rx.recv().unwrap(); // writer has renamed the file but is paused BEFORE releasing its per-note lock

    // Start a reader now. It must not be able to acquire the lock while the
    // writer holds it, so prove it hasn't completed yet by racing it against
    // a short timeout BEFORE resuming the writer.
    let reader_vault = Arc::clone(&vault);
    let reader_id = id.clone();
    let (reader_done_tx, reader_done_rx) = std::sync::mpsc::channel();
    std::thread::spawn(move || {
        let result = reader_vault.read_note(&reader_id);
        reader_done_tx.send(result).unwrap();
    });
    assert!(
        reader_done_rx.recv_timeout(std::time::Duration::from_millis(200)).is_err(),
        "reader must still be blocked on the per-note lock while the writer holds it"
    );

    resume_tx.send(()).unwrap();
    writer.join().unwrap().unwrap();
    let record = reader_done_rx.recv().unwrap().unwrap();
    assert_eq!(record.content, "v2", "reader unblocks only after the writer's full critical section, including journal_committed, completes");
}

#[test]
fn sec_001_toctou_window_between_path_check_and_write_still_exists() {
    // This test is EXPECTED to demonstrate the race still succeeds (NOT a
    // regression to fix in this task) — it is the adversarial proof that
    // hash verification alone does not close SEC-001, because the hash check
    // happens AFTER the write, not before the path resolution race.

    let vault = Arc::new(Vault::open_with_default_indexer(root.clone(), &fresh_journal_path()).unwrap());
    let id = NoteId::parse("note-a").unwrap();
    let outside = unique_test_dir();

    let (pause_tx, pause_rx) = std::sync::mpsc::channel();
    let (resume_tx, resume_rx) = std::sync::mpsc::channel();
    // Pause AFTER record_path_checked's canonicalization has already run and
    // returned "inside root", but BEFORE atomic_write's own open/rename.
    let injector = FaultInjector::pause_at(FaultPoint::AfterPathCheckedBeforeAtomicWrite, pause_tx, resume_rx);
    let writer_vault = Arc::clone(&vault);
    let writer_id = id.clone();
    let writer = std::thread::spawn(move || {
        writer_vault.write_record_unchecked_with_injector(&writer_id, "content", Version(0), Uuid::new_v4(), &injector)
    });

    pause_rx.recv().unwrap();
    // Swap the now-checked-safe path for a symlink pointing outside, during the window.
    let _ = std::fs::remove_file(root.join("note-a.record"));
    symlink_file(&outside.join("victim"), &root.join("note-a.record"));
    resume_tx.send(()).unwrap();
    let _ = writer.join().unwrap();

    // Correction (user architectural review, point 6): the original version
    // of this test ended on a bare eprintln! with no assertion — it could
    // never fail, so it could not actually distinguish a correct outcome from
    // a defective one, which is exactly what an adversarial/characterization
    // test must do to be worth running under CI. The fix asserts the ACTUAL

    // assertion FAILS, which is correct — it means the verdict in Step 5 must
